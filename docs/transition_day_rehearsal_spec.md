>

> 아래 §0·§3은 *"전환일에 770명이 한꺼번에 들어온다"* 를 전제로 썼다. **틀렸다.** 실제 확산은 **모듈별로 서서히** 일어난다 — 생활지도가 먼저 시트에서 넘어오고, 시간표는 일과계 중심이다. 기관 결정으로 채택하더라도 **사용이 한 시점에 몰리지는 않는다.**
>
> **그래서 두 가지가 바뀐다.**
>
> **① §0의 근거가 무너진다.** *"일괄 전환에는 점진적 발견 기회가 없다"* 가 이 리허설의 존재 이유였는데, 확산이 점진적이면 **문제가 자연히 드러날 시간이 있다.** 리허설은 여전히 유용하지만 **긴급하지 않다.**
>
> **② 숫자를 다시 계산하면 지금 규모에서는 위험이 없다.** 근시일 사용을 넉넉히 잡아 **하루 300요청**이라 해도:
> ```
> 읽기 = 300 × 2 + (300 × R) × 85 = 600 + 25,500 × R
> ```
> **R = 1(캐시가 전혀 안 도는 최악)이어도 26,100** — 무료 한도 50,000 안이다. 즉 **지금은 캐시가 안 돌아도 버틴다.**
>
> **개정된 판정 기준**: R 측정은 그대로 의미가 있으나(구조를 아는 것은 값싸다), **하루 요청이 1,000을 넘기 시작할 때부터 §3의 임계선이 실질 의미를 갖는다.** 그 전에는 참고값이다.
>
> **실행 권고 변경**: 부하 스크립트는 만들어 두되 **단계 0~1(1건·30건)까지만 돌린다.** 단계 2·3은 사용 규모가 실제로 커진 뒤에 한다 — 지금 돌리면 답이 이미 정해진 측정에 할당량만 쓴다.
>
> *교훈으로 남긴다*: 채택 모델("기관 일괄 결정")과 **사용 곡선**("한꺼번에 몰리는가")을 같은 것으로 읽었다. 결정은 일괄이어도 사용은 점진일 수 있다. 전제를 사용자에게 확인하지 않고 스펙 전체를 그 위에 세웠다.

## 0. 왜 이게 필요한가 — 일괄 전환에는 리허설이 유일한 안전장치다

채택 모델이 기관 일괄 전환이라 **점진적으로 문제를 발견할 기회가 없다.** 전환일에 수백 명이 한꺼번에 들어오고 그날 처음으로 모든 경로가 동시에 밟힌다. 지금까지 관측된 사용 패턴은 로그인 28명이 만든 것뿐이다.

[`weekly_synthesis_cache_spec.md:8`](./weekly_synthesis_cache_spec.md)이 스스로 경고를 남겼다 — *"채택 성공이 곧 장애가 되는 구조"*. 캐시로 막았다는데 **그 히트율은 프로덕션에서 측정된 적이 없다.**

## 1. 코드를 읽고 나서 — 문제의 형태가 통념과 다르다

### 1-1. 캐시 키에 학급이 들어가지 않는다

`viewCache.ts`의 메모 키는 셋뿐이다:

| 키 | 형태 | 개수 |
|---|---|---|
| `ctx` | `ctx:{domain}:{version}:{termId}` | 사실상 **1개** |
| `grids` | `grids:{domain}:{version}:{termId}:{weekId}` | **주 개수만큼** (현재 8) |
| `basegrids` | `basegrids:{domain}:{version}:{termId}` | **1개** |

`getWeekGridsCached`는 **한 주의 전 학급 그리드를 통째로** 담는다(`loadBaseGridsForWeek` → 30학급). 즉 **같은 주를 보는 학생 700명이 캐시 항목 하나를 공유한다.**

→ **사용자 수가 늘어도 키는 늘지 않는다.** `MAX_ENTRIES = 40`은 넉넉하고, 키 다양성에 의한 캐시 미스는 사실상 없다.

### 1-2. 그러므로 남는 변수는 **인스턴스 분산** 하나다

`const store = new Map()` 은 **모듈 스코프**다. Vercel 서버리스는 인스턴스마다 별도 프로세스이므로 **인스턴스가 늘면 그 수만큼 캐시를 따로 채운다.** 콜드 스타트도 마찬가지다.

### 1-3. 요청당 읽기 — 캐시와 무관하게 깔리는 바닥이 있다

| 항목 | 읽기 | 캐시 가능? |
|---|---|---|
| `verifyAuthAccess` → `users/{uid}` (`admin.ts:124`) | **1** | ❌ 요청마다 |
| `getTimetableCacheVersion` → `timetable_cache_meta/{domain}` | **1** | ❌ 설계상 캐시 안 함(무효화 정확성의 원천) |
| `ctx` + `grids` + `basegrids` 채움 | **~85** | ✅ 인스턴스당 1회 |

### 1-4. 그래서 총 읽기는 이 식이다

```
총 읽기 ≈ (요청 수 × 2) + (인스턴스 수 × 85)
```

**이게 이 리허설의 전부다.** 두 항 중 앞은 확정값이고, 뒤가 미지수다. 그리고 미지수는 사용자 수가 아니라 **인스턴스 수**다.

> **통념 교정**: "사용자가 늘면 읽기가 폭증한다"가 아니다. 사용자가 700명이어도 인스턴스가 10개면 읽기는 `요청×2 + 850`이다. 위험한 경우는 **요청마다 새 인스턴스가 뜨는 것**뿐이다.

## 2. 측정 — 인스턴스 분산을 밖에서 판별하는 법

핵심 난점: **캐시 적중은 서버 안에서 일어나고 응답 본문에 흔적이 없다.** 지연 시간은 대리 지표라 잡음이 크다.

### 2-1. 계측 (구현 완료 — `viewCache.ts` + `view/route.ts`)

**모듈 스코프에서 한 번 생성되는 난수 id가 곧 인스턴스 신원이다.** 같은 인스턴스가 응답하면 같은 id가 나온다.

응답 헤더 4종:

| 헤더 | 뜻 |
|---|---|
| `x-tt-instance` | 인스턴스 id (프로세스 수명 동안 고정) |
| `x-tt-cache` | 이 요청의 캐시 판정 — `hit` / `miss` / `off` |
| `x-tt-hits` / `x-tt-misses` | 이 인스턴스의 누적 적중·실패 |

개인정보·비밀값이 없고 인증된 요청에만 나가므로 상시 켜 둔다. **설정 없이 언제든 다시 잴 수 있어야 한다** — 리허설이 1회성 이벤트가 아니라 정례 점검이 되려면 그렇다(bus factor).

> **⚠️ `x-tt-cache`는 동시 발사 구간에서 신뢰하지 않는다.** 판정 표식이 모듈 스코프 변수라 **같은 인스턴스에서 동시 처리되는 요청끼리 섞인다.** 단계 0(요청 1건)에서만 정확하다.
> **R은 반드시 `x-tt-instance`의 distinct 개수로 계산한다** — 인스턴스 id는 동시성과 무관하게 정확하고, 누적 카운터(`x-tt-hits`/`x-tt-misses`)도 정확하다. 이 구분을 놓치면 *"적중률이 높다"는 잘못된 결론*이 나오고, 그건 전환일에야 드러난다.

### 2-2. 측정 지표

| 지표 | 계산 | 의미 |
|---|---|---|
| **R (냉시작 비율)** | `distinct(x-tt-instance) / 요청 수` | **이 리허설의 핵심 수치** |
| 캐시 적중률 | `hit / (hit+miss)` | R의 다른 표현 |
| 인스턴스당 요청 수 | `요청 수 / distinct(instance)` | 재사용 정도 |
| 실측 읽기 | 리허설 전후 Firestore 사용량 차 | 위 식의 검산 |

## 3. 판정 기준 — 숫자를 미리 정한다

전환일 부하 가정(보수적):
- 교직원 70 + 학생 700 = **770명**
- 1인당 시간표 조회 **5회/일** → **약 3,850 요청**

식에 대입:

```
읽기 = 3,850 × 2 + (3,850 × R) × 85 = 7,700 + 327,250 × R
```

무료 일일 읽기 한도 50,000. **다른 기능(로그인·생활지도·쪽지·크론)이 함께 쓰므로 시간표에는 40,000까지만 허용**한다.

| R | 예상 읽기 | 판정 |
|---|---|---|
| 0.02 (2%) | 14,245 | 🟢 여유 |
| 0.05 (5%) | 24,063 | 🟢 통과 |
| **0.099** | **40,100** | **← 한계선** |
| 0.20 | 73,150 | 🔴 초과 |
| 1.00 (매번 콜드) | 335,000 | 🔴 즉사 |

> **판정: R < 0.10 이면 통과. 0.10 이상이면 채택 전 구조 수정 필요.**
>
> 부수 조건 — R이 통과여도 **인스턴스당 요청 수가 10 미만**이면 경고로 본다. 부하 패턴이 조금만 달라져도 R이 넘어갈 수 있다는 뜻이다.

## 4. 리허설 자체의 읽기 예산 — 이게 안전 설계의 핵심이다

**리허설이 할당량을 태울 수 있다.** 최악(R=1)이면 1,000 요청 = 87,000 읽기로 **그날 서비스가 죽는다.** 2026-08-08에 실측 스크립트가 할당량을 소진해 전면 401이 난 전례가 있다(`AGENTS.md` 규율표 3번).

→ **단계적으로 하고, 각 단계 뒤에 멈춰서 외삽한다.**

| 단계 | 요청 수 | 최악 읽기(R=1) | 하는 일 |
|---|---|---|---|
| **0** | 1 | 87 | 헤더가 나오는지만 확인 |
| **1** | 30 | 2,610 | R 1차 추정 |
| **2** | 150 | 13,050 | R 확정. **여기서 대부분 판정 난다** |
| **3** | 600 | 52,200 | **단계 2에서 R < 0.10일 때만 실행** |

- **각 단계 사이에 사람이 판단한다.** 스크립트가 자동으로 다음 단계로 넘어가지 않는다.
- **단계 3은 조건부다.** 단계 2에서 R이 높게 나오면 3을 하지 않는다 — 이미 답이 나왔는데 할당량만 태운다.

## 5. 부하 재현 — 무엇을 흉내 내야 하는가

### 5-1. 인증

`/api/timetable/view`는 `token` 쿠키(Firebase ID 토큰)를 요구한다. Admin SDK로 `createCustomToken(uid)` → REST `signInWithCustomToken`으로 ID 토큰을 얻는다.

**토큰 1개면 충분하다.** 캐시 키에 사용자가 안 들어가므로(§1-1) 사용자 다양성은 캐시 거동에 영향이 없다. 다만 `users/{uid}` 읽기는 요청마다 발생하므로 **바닥 2읽기는 그대로 재현된다.**

> 단, `role`은 교사/super_admin으로 한다. 학생 역할은 `resolveStudentClass`가 추가로 읽고 본인 반으로 강제되어 요청 다양성을 못 만든다.

### 5-2. 동시성이 관건이다

**순차 요청은 이 리허설의 목적을 달성하지 못한다.** 순차로 보내면 Vercel이 인스턴스 하나를 재사용해 R이 인위적으로 낮게 나오고, *"괜찮다"는 잘못된 결론*이 나온다. 그건 전환일에야 드러난다.

- **동시 발사**를 쓴다. 동시성 20~50으로 짧은 시간에 몰아친다.
- 전환일의 실제 형태(1교시 시작 직전 수백 명이 동시에 여는 것)와 같아야 한다.

### 5-3. 요청 다양성

주(week)를 섞는다 — `grids` 키가 주별이므로 키 다양성은 여기서만 나온다. 현재 주 8개.

### 5-4. 배포 대상

**프로덕션에서 잰다.** 로컬 `npm run dev`는 단일 프로세스라 R이 항상 0에 수렴해 **측정 자체가 무의미하다.** 이게 이 리허설이 로컬에서 못 하는 유일한 이유다.

## 6. 결함이 나왔을 때 — 대안을 미리 정해 둔다

R ≥ 0.10이면 채택 전에 고쳐야 한다. 후보 셋을 값싼 순으로.

### 대안 A — 합성 결과를 쓰기 시점에 문서로 굳힌다 (권장)

시간표를 **바꿀 때** 주별 합성 결과를 문서 하나로 저장하고, view는 그 문서 1개만 읽는다.

```
timetable_view_snapshots/{domain}/weeks/{weekId}  ← 합성된 30학급 그리드 1문서
```

- 읽기: 인스턴스 수와 **무관하게** 요청당 1 (+바닥 2) = **3읽기 고정**
- 쓰기: 시간표 변경 시에만. 변경은 드물다
- 인스턴스 분산 문제가 **원인 단계에서 사라진다** — 인메모리 캐시는 있어도 그만 없어도 그만이 된다
- 기존 `cacheVersion` 무효화 구조를 그대로 재사용할 수 있다(버전을 문서에 같이 저장)
- 주의: 문서 1MB 한도. 30학급 × 7교시 × 5일 그리드가 들어가므로 **크기를 먼저 실측**한다

### 대안 B — 바닥 2읽기를 1로 줄인다

`users/{uid}`와 `timetable_cache_meta/{domain}`를 `getAll`로 묶는다. 읽기 수는 그대로지만 왕복이 준다. **효과가 작다** — R이 문제일 땐 무의미하다.

### 대안 C — 콜드 채움 비용(85)을 줄인다

`basegrids`(~51읽기)는 교사 드롭다운용이다. 학생 요청에는 필요 없을 수 있다 — 역할별로 지연 로드하면 학생 경로의 콜드 비용이 크게 준다. **A보다 효과가 작지만 A와 함께 쓸 수 있다.**

> **선택 기준**: R이 0.10~0.20이면 C로 충분할 수 있다. 0.20을 넘으면 A로 간다 — 인스턴스 분산이 심하다는 뜻이고, 그건 캐시를 아무리 싸게 만들어도 해결되지 않는다.
