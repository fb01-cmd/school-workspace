# 쪽지 서식·이모지·GIF 갈래 스펙 (memo_richtext_spec)

2026-08-18 Claude(Fable) 작성. 로드맵 §2 「쪽지 서식·이미지·이모지·GIF」(2026-08-13 사용자 발상 + 모바일 호환 우려 동시 제기)의 확정 스펙. 상위 문서 = [`memo_spec.md`](./memo_spec.md)(모델·발송), [`memo_attachment_spec.md`](./memo_attachment_spec.md)(첨부·Drive).

## §0 배경·원칙

- **채택 논리**: 쿨메신저·카톡에 익숙한 교사에게 "글자만 되는 쪽지"는 퇴보로 읽힌다(내선번호 §11-6과 같은 계열). 목표는 화려함이 아니라 **업무 메신저의 상식선** — 굵게·목록·링크가 되는 것.
- **모바일 우려의 정확한 정체 (로드맵 ⓪ 판정 승계)**: 문제는 "폰에서 서식이 안 보인다"가 아니라 ⓐ 작성이 어렵다(→ 작성은 PC 전용, `/m`은 열람 — mobile_m_spec 원칙 그대로) ⓑ 푸시 미리보기가 태그로 깨진다 ⓒ 좁은 폭 가로 스크롤. **ⓑ는 현행 코드 실측으로 이미 소멸**: `notifyMemo`(webpush.ts)는 푸시에 **제목만** 싣고 본문을 싣지 않는다 — 서식은 body에만 허용하므로(§2) 푸시는 무변경. ⓒ는 v1 요소가 전부 세로 흐름(표 없음)이라 원천 미발생.
- **저장은 하나, 표시는 경로별 강등**: 원본은 한 형식(§2), 서식 렌더(§4)·평문 발췌(§5)는 그 원본에서 파생. 상태 단일 원본 원칙의 본문판.
- **XSS는 정제가 아니라 구조로 차단한다 (이 스펙의 핵심 보안 결정, §4)**: HTML을 저장하지도, 주입하지도 않는다. 저장소에 `dangerouslySetInnerHTML` 사용은 현재 0건(2026-08-18 grep 실측)이며 이 스펙 이후에도 0건이어야 한다.

## §1 갈래 판정 (로드맵 4단계의 확정판)

| 갈래 | 판정 | 근거 |
|---|---|---|
| ① 이모지 | **추가 개발 없음 — 이미 성립** | body는 유니코드 텍스트로 저장·표시됨(`<pre>` 렌더 실측). OS 이모지 입력(Win `⊞+.`, ChromeOS `🔍+Shift+Space`)이 지금도 동작. 남는 것은 입력 편의(피커)뿐 — §7 편집기 툴바와 같은 사이클, 별도 단계 아님 |
| ② 서식 | **v1 본체 — 이 스펙 §2~§7** | 제한 마크다운 서브셋 `md1` 저장 + React 노드 렌더 |
| ③ 이미지 | **완결 (2026-08-18)** | memo_attachment_spec 구현·실기기 통과 — 이 스펙 범위 밖 |
| ④-a GIF 첨부 | **설계 확정 (§9), 착수는 소품 우선순위(STATUS 사용자 결정 대기 행) 따름** | 기존 첨부 파이프라인의 형식 1개 확장 — 소규모 |
| ④-b Tenor GIF 검색 | **후순위 별건 — 감점 논거 철회 (2026-08-18 사용자 반증)** | 학교 도메인 구글 챗에 GIF 검색(Tenor)이 내장·일상 사용 중(실기기 스크린샷 확인) — "학교 업무 메신저에 GIF 검색은 채택 감점"이라는 조직 문화 논거는 같은 Workspace 안의 전례로 무효. Tenor는 구글 소유 서비스라 위탁 상대도 기존 구글 계약 생태계 안. 남는 실비용 = 처리 위탁 고지(검색어 외부 전송)·API 키 발급·무료 한도 확인 — 전부 경미·1회성. **선행 = ④-a GIF 첨부(받는 그릇)**, 착수 시 별건 스펙(이 스펙에서 설계하지 않는 것은 유지) |

## §2 저장 모델 — `md1` 서브셋 + `contentFormat` 필드

`memos` 문서 확장 (규칙·색인 무변경 — memo_reply_spec의 필드 추가 전례와 동일 패턴):

| 필드 | 타입 | 설명 |
|---|---|---|
| body | string | **기존 필드 그대로.** md1 토큰을 포함한 원문. 길이 제한 ≤10,000자(토큰 포함) 기존 값 유지 |
| contentFormat | `"md1"` (선택) | **부재 = 평문(현행)**. 발송 시 편집기가 서식을 실제 사용한 경우에만 서버가 스탬프 |

- **하위호환의 핵심**: `contentFormat` 부재 문서는 **절대 md1로 재해석하지 않는다.** 옛 쪽지 본문의 `*`·`-` 같은 문자가 어느 날 기울임·목록으로 둔갑하는 것(본문 유령의 서식판)을 원천 차단. 마이그레이션 0건.
- 서버 검증: `contentFormat`은 값 화이트리스트(`"md1"`만 허용, 그 외 400). body는 여전히 텍스트이므로 추가 정제 불요 — 이것이 HTML 저장안 대비 결정적 단순성.
- 답장(memo_reply_spec)·회수·삭제·파기 크론·별표/검색 모델은 body 필드를 그대로 쓰므로 **전부 자동 승계, 무변경**.

## §3 md1 문법 (닫힌 정의 — 여기 없는 것은 문법이 아니다)

인라인 4종 + 블록 3종 + 링크 1종. GFM 전체를 들이지 않는다(표·코드·이미지 문법·헤딩 제외 — 좁은 폭 안전과 파서 단순성).

| 토큰 | 의미 |
|---|---|
| `**텍스트**` | 굵게 |
| `*텍스트*` | 기울임 |
| `__텍스트__` | 밑줄 |
| `~~텍스트~~` | 취소선 |
| 줄 시작 `- ` | 글머리 목록 항목 |
| 줄 시작 `1. `(임의 숫자) | 번호 목록 항목 |
| 줄 시작 `> ` | 인용 |
| `[라벨](https://…)` | 링크 — **https만**(memo_spec §1 links의 기존 원칙 승계), 2048자 이하. 그 외 프로토콜은 토큰 불성립 → 평문 표시 |

- **이스케이프**: `\*` `\_` `\~` `\[` `\\` — 백슬래시 뒤 해당 문자는 리터럴. 편집기는 사용자가 입력한 리터럴 특수문자를 직렬화 시 자동 이스케이프할 의무(§7).
- **중첩 규칙(단순성 우선)**: 인라인 토큰끼리 중첩 미지원 — 먼저 열린 토큰이 이긴다. 블록(목록·인용) 내부의 인라인은 지원. 목록 들여쓰기 중첩 미지원.
- 닫히지 않은 토큰은 토큰이 아니다 — 여는 표시 그대로 평문 출력(조용한 오해석 금지).

## §4 렌더 — 파서는 노드를 만들고, HTML은 어디에도 없다

- **단일 소재지 `src/lib/memo/richtext.ts`**: `parseMd1(body): RichNode[]` — React 무의존 순수 함수(노드 타입: text·bold·italic·underline·strike·link·bullet·ordered·quote·paragraph). 순수라서 셀프테스트 가능(§11).
- 렌더 컴포넌트(`MemoRichBody`)는 노드 트리를 React 요소로 얇게 매핑. 문자열은 전부 React children으로만 흐른다 → **주입 표면 자체가 없다.** `dangerouslySetInnerHTML` 사용 금지 명문화(리뷰 관문).
- 링크 렌더 안전: `target="_blank"` + `rel="noopener noreferrer"`, href는 파서가 https를 보장한 값만.
- 적용 지점 3곳(현행 `<pre>{memo.body}</pre>` 교체): `MemoSection.tsx` 상세(1곳)·`MobileMemoSection.tsx` 상세(1곳)·인쇄/기타 상세 뷰가 있으면 동일 컴포넌트. `contentFormat !== "md1"`이면 현행 `<pre>` 평문 경로 유지(분기 1줄).

## §5 평문 강등 — `stripMd1(body): string`

- 같은 파일의 순수 함수. 토큰 제거 + 링크는 라벨만 + 공백 정리. 소비처: ⓐ 목록·대시보드 발췌(`DashboardMemoPanel`·쪽지함 목록 미리보기) ⓑ 향후 본문을 싣는 알림이 생길 경우의 강등 원본.
- 푸시는 §0 실측대로 제목만 실으므로 **현행 무변경** — stripMd1을 푸시에 배선하는 작업은 없다(유령 방지: 이 문장은 "안 해도 된다"는 확정이지 할 일이 아니다).
- 검색(memo_star_search)은 body 원문 대상 그대로 — 토큰이 낀 문자열도 부분일치가 성립(`**회의**`는 "회의"를 포함)하므로 v1 무변경. 토큰 문자 자체를 검색하는 극단 사례는 수용.

## §6 웹 푸시·알림 센터 — 무변경 (근거 명기)

- `notifyMemo`는 `새 쪽지 / {발신자} 선생님: {제목 60자}`만 발송(2026-08-18 코드 실측). 제목은 서식 비허용(§7 편집기가 제목 입력엔 툴바 없음)이므로 깨질 표면이 없다.
- 알림 센터 쪽지 항목도 제목·발신자만 쓰는 현행 유지.

## §7 편집기 — **즉시 반영(WYSIWYG)으로 개정 (2026-08-18 사용자 확정: "가능하면 안 갈 이유가 없다")**

v1 토큰 삽입형(버튼이 `**` 표시를 끼우고 미리보기 토글로 확인)은 하루 완성용 최단 경로였고 실기기까지 갔다. 사용자 결정으로 **누르는 즉시 서식이 보이는 방식**으로 전환한다. 저장·발송·렌더·규칙은 전부 불변 — 바뀌는 것은 입력창뿐이다.

- **구조**: `MemoSection` 작성부의 textarea를 `contenteditable` 입력창으로 교체(PC 전용 원칙 유지, 제목은 평문 그대로). 발송 직전(및 글자 수 계산용 입력 시) **`serializeDomToMd1`(`src/lib/memo/richtext_dom.ts`, 단일 소재지·직접 재구현 금지)**로 md1을 뽑아 기존 경로(글자 수 1만·`bodyHasMd1Formatting` 관문·send 페이로드)에 그대로 태운다.
- **이스케이프는 이제 의무이고, 직렬화기가 진다**: 즉시 반영 방식에선 사용자가 원문을 못 보므로, 사용자가 친 리터럴 `*`가 서식으로 둔갑하면 안 된다 — `serializeDomToMd1`이 텍스트 노드를 전부 이스케이프한다(셀프테스트 ②·⑦).
- **서식 적용**: 툴바 8버튼 + Ctrl/⌘+B·I·U 단축키는 브라우저 편집 명령(`document.execCommand` — 폐지 예고 상태지만 크롬 실동작, 학교 PC 전제)으로 즉시 반영. 명령이 만드는 어떤 DOM이 와도 직렬화기가 md1 서브셋으로 눌러 담는다(중첩 마크는 바깥만, 알 수 없는 태그는 투명 통과 — 결정론).
- **붙여넣기 = 평문만**: paste 이벤트를 가로채 `insertText`로 평문 삽입. 외부 서식(워드·웹의 색·표·글꼴)이 들어오면 md1 밖 요소가 조용히 유실되는 혼란 + 정제 부담이 생기므로 원천 차단. 이미지 붙여넣기는 기존 첨부 경로 그대로.
- **미리보기 토글 폐지**(입력창이 곧 결과), 이모지 피커·내장 상수·외부 요청 0·UI 생활어 원칙(마크다운 용어 노출 금지)은 유지.
- **발송 페이로드 불변**: 직렬화 결과에 토큰이 없으면 `contentFormat` 미포함(평문 발송) — 기존 관문 그대로.
- 링크 버튼: 선택 영역을 `[라벨](https://…)`로 만드는 대신 execCommand `createLink` 후 직렬화기가 https 검증(아니면 라벨 강등) — 주소 입력 UI는 재량.
- **번호 목록 UX**: 브라우저 목록 편집이 Enter마다 다음 번호를 자동으로 잇는다 — v1의 "계속 1.만 나온다" 불편(2026-08-18 사용자 질문)이 구조적으로 소멸. 직렬화기는 번호를 DOM 순서로 다시 매긴다.

- Firestore 읽기·쓰기 증가 0(필드 1개, 문서 수·구독 동일). 번들 증가는 파서 수 KB 수준.

## §9 GIF 첨부 — 설계 확정판 → **구현 완결 ✅ (2026-08-18 사용자 결정으로 소품 큐에서 앞당김)**

기존 파이프라인의 형식 1개 확장. 로드맵 [2026-08-18 사용자 관찰]의 구현 스펙화. 아래 1~3 전부 구현·셀프테스트 통과(GIF 4케이스 포함). **한계(명시)**: 첨부 목록 미리보기는 Drive 정지 썸네일이라 움직이지 않고, 클릭해 원본을 열면 재생된다 — 글자 사이에서 바로 움직이는 표시는 §13(인라인 이미지)의 몫.

1. **서버** (`attachment_logic.ts` 단일 소재지): `MEMO_ATTACHMENT_MIME_WHITELIST`에 `"image/gif"` 추가 + `sniffImageMime`에 GIF 바이트 서명 분기(`47 49 46 38 37|39 61` = GIF87a/GIF89a) — 선언 MIME 위장 차단 기존 구조 그대로.
2. **클라이언트** (`client_attachments.ts`): **GIF는 캔버스 리사이즈를 타지 않는다** — 캔버스는 첫 프레임만 남겨 움직임을 죽인다. 원본 통과 분기: ≤3.5MB 원본 그대로 업로드(Vercel 4.5MB 본문 한도 내 기존 상한 재사용), 초과 시 업로드 거부 + 눈높이 안내("움직이는 이미지는 3.5MB까지").
3. 폴더·권한·파기·인벤토리 = attachment spec 그대로(형식 추가일 뿐, 이미지 범주 내). 인벤토리 문구에 "GIF 포함" 1단어 반영.
4. Tenor 검색은 §1 판정대로 이 확장에 얹지 않는다.

## §10 명시적 범위 제외 (v1)

표·헤딩·코드 블록·이미지 문법(`![]()` — 단 인라인 이미지의 v1.1 설계 방향은 §13에 확정) · bare URL 자동 링크(v1.1 후보 — 피싱 표면·파서 복잡 대비 편익 재평가 후) · 목록/인용 중첩 · 서식 있는 답장 인용 · `/m` 작성.

## §11 검증 — `scripts/verify_memo_richtext.ts` (순수, Firestore 0회)

파서·strip 왕복 케이스: ① 인라인 4종 각 파싱 ② 미닫힘 토큰 평문 보존 ③ 이스케이프 리터럴 ④ 링크 https만 성립·`javascript:` 불성립 ⑤ 중첩 시 선점 규칙 ⑥ 블록+인라인 조합 ⑦ stripMd1 발췌(토큰 제거·라벨 보존) ⑧ 10,000자 경계 ⑨ 평문 body를 parseMd1에 넣지 않는 분기 확인(contentFormat 부재 경로). 서버부는 `contentFormat` 화이트리스트 400 케이스 1건.

## §12 분업·순서

1. **코어 (Claude)**: `richtext.ts`(parseMd1·stripMd1·노드 타입) + send 경로 `contentFormat` 스탬프·검증 + §11 셀프테스트.
2. **화면 (Antigravity)**: `MemoRichBody` 매핑 컴포넌트 + 상세 뷰 2곳 분기 교체 + 편집기 툴바·피커 + 목록 발췌 stripMd1 배선. §7 산출 계약 준수.
3. **실기기 (사용자)**: PC에서 서식 쪽지 작성·발송 → 폰(`/m`)에서 열람 확인 + 옛 쪽지 1건이 그대로(재해석 없음)인지 확인.
4. **GIF 첨부 (§9)**: 소품 우선순위 확정 시 별도 사이클. → **구현 완결 (2026-08-18, §9 참조)**
5. **즉시 반영 편집기 전환 (§7 개정, 2026-08-18 사용자 확정)**: 직렬화기 코어(`richtext_dom.ts`+셀프테스트 20케이스) = Claude ✅ → contenteditable 배선·붙여넣기 평문화·미리보기 토글 제거 = Antigravity → 실기기 재확인 = 사용자.

## §13 인라인 이미지 — v1.1 (2026-08-18 사용자 발상 → 같은 날 착수 확정, 코어·서버부 구현 완결)

**[구현 확정 노트 — 설계 방향에서 달라진·구체화된 것]**
- **표시 경로 = 자체 바이트 프록시** `GET /api/memo/attachment?memoId=&attId=` 신설: Drive thumbnailLink는 만료되고 GIF가 정지 프레임이라 본문 표시용으로 부적합(코드 실측). 인증은 기존 쿠키(token)를 `<img>`가 자동 동봉 — 새 인증 기계 0. 열람 자격 = 그 쪽지의 발신자·수신자만(`resolveAttachmentViewEligibility` 순수 함수, 셀프테스트 5케이스) — 회수로 수신 목록에서 빠지면 이미지 접근도 함께 잃는다(의도된 정합). 응답은 업로드 때 바이트 서명으로 검증된 mimeType + nosniff + private 캐시 1일(첨부 불변이라 안전). **GIF가 본문에서 실제로 움직이는 경로가 이것이다.**
- **비용**: 이미지 1회 로드 = Firestore 2읽기(인증 1+쪽지 1) + Drive 다운로드 1. 브라우저 캐시 1일로 재열람 무료. 교사 규모에서 무시 가능.
- **외부 URL 강등의 정확한 형태**: `![x](https://…)`는 이미지 노드가 절대 생기지 않고(외부 이미지 요청 0) `!`+일반 링크로 강등된다 — 링크 의도는 보존, 추적 픽셀 표면은 없음.
- 토큰 `![라벨](att:첨부ID)` 파싱·직렬화(IMG `data-att-id`만 성립, 외부 src IMG는 버림)·strip(라벨 또는 "[이미지]")·`collectMd1AttachmentIds`(그리드 중복 숨김용) 전부 코어 반영, 상세 뷰 2곳(PC·/m)은 `MemoRichBody memoId` 전달 + 참조 첨부 그리드 숨김까지 배선 완료.
- 남은 배선 = **작성기(Antigravity)**: 업로드·붙여넣기 완료 시 커서 위치에 `<img data-att-id previewUrl>` 삽입, 작성 중 첨부 목록에서 본문 참조분 구분 표시, 편집기에서 이미지 삭제 시 참조만 제거(첨부는 목록에 잔류).

(아래는 원 설계 방향 기록)

사용자 관찰: 쿨메신저·경기도교육청 메신저 모두 이미지가 **글 쓰는 박스 안에 줄글처럼** 들어간다 — 특히 GIF는 글자 사이에 끼어야 의미가 있지, 본문 아래 별도 칸은 반쪽이다. 실무 감각이 맞고, 모바일도 걸림돌이 아니다(근거 아래). 설계 방향을 여기 확정해 두고 착수만 사용자 결정에 건다.

- **모바일 판정 — 문제 없음**: 원래 우려 셋(§0) 중 작성은 PC 전용 원칙으로, 푸시는 제목만 실어서 이미 소멸했고, 남는 좁은 폭은 이미지 최대 폭 100% 규칙이면 끝(세로 흐름 유지, 가로 스크롤 미발생). `/m` 열람은 같은 렌더러라 추가 작업 없음.
- **핵심 원칙 — 인라인 이미지는 첨부의 참조다**: 저장·권한·파기는 기존 첨부(attachment spec — Drive·staging 대조·개별 reader·크론)를 **그대로** 쓰고, 본문에는 그 첨부를 가리키는 토큰 하나만 얹는다: `![라벨](att:첨부ID)`. 새 저장소·새 권한 경로·새 파기 대상이 생기지 않는다.
- **임의 URL 이미지는 문법 불성립(보안 확정)**: `![](https://…)` 류 외부 이미지는 열람자 브라우저가 외부 서버로 요청을 보내게 만들어 추적 픽셀·IP 유출 표면이 된다. 인라인은 `att:` 참조만 성립 — 파서 수준 차단이라 정제 불요(§0 구조 차단 원칙의 연장).
- **렌더**: `MemoRichBody`가 해당 쪽지의 `attachments`를 컨텍스트로 받아, 참조 ID가 실재할 때만 기존 첨부 이미지 컴포넌트를 그 자리에 표시(폭 100% 제한). ID가 없으면 "[이미지]" 평문 강등. 본문에 참조된 첨부는 하단 그리드에서 숨겨 중복 표시 방지, 참조 안 된 첨부만 그리드 유지.
- **편집기**: 업로드·클립보드 붙여넣기 완료 시(기존 staging 업로드 경로 그대로) 커서 위치에 토큰 삽입.
- **strip**: 라벨 있으면 라벨, 없으면 "[이미지]".
- **GIF와의 결합**: §9(GIF 첨부)가 붙는 순간 GIF도 같은 참조 구조로 **자동으로 글자 사이에 들어간다** — 이 항목이 사용자 원 취지("GIF는 끼어 있어야 의미")의 완성 지점.
- **코어 변경 규모**: `parseInlineMd1`에 이미지 참조 토큰 1종 추가(소규모, Claude) + 렌더·편집기 삽입(Antigravity). 순서 = §12의 v1 화면 완료 뒤 v1.1로.
