# 로드맵 "상태 대장 / 작업 일지" 분리 스펙

> 작성 2026-08-13 (Claude — Opus 5). 사용자 지시 "1번 하자"로 착수 확정.
> 대상: `development_roadmap.md`. 실행: Antigravity(대량 편집), 판정 규칙은 이 문서가 정한다.

## 1. 왜 하는가 — 유령은 우연이 아니라 구조의 산물이다

2026-08-13 하루에만 상태 표기 유령이 **4건** 나왔다(로드맵 31행·164행, 트리아지 §3-1, `AGENTS.md` 71행). 그 전날 트리아지 §5에서도 6건 중 3건이 유령이었다. 원인을 실측했다:

| 측정 | 값 |
|---|---|
| `development_roadmap.md` | 194줄 / **89,544자** |
| 최상위 항목(`* `로 시작) | **80개** |
| 1,000자 넘는 줄 | 28줄 |
| 2,000자 넘는 줄 | 6줄 (최장 **4,672자**) |
| 최근 12커밋의 변경 | **10건이 삭제 0줄** = 순수 덧붙이기 |

생산 경로는 이렇다.

1. 상태는 **줄 앞 제목 괄호**에 박혀 있다 — `(2026-08-09 사용자 요청 확정, 스펙 미착수)`
2. 진행은 **줄 뒤에 덧붙는다** — `… → 매핑 스펙 확정 ✅`
3. 앞 괄호를 고치는 사람이 없다(최근 12커밋 중 10건 삭제 0줄)
4. → **한 줄 안에서 앞뒤가 모순되는 상태**가 정상 동작으로 생산된다
5. 읽는 쪽은 4,672자를 끝까지 안 읽는다. **먼저 만나는 것이 거짓**이다

여기에 `AGENTS.md` **④-2(append-only, 2026-08-13 Claude 신설)** 가 겹친다. 기록 유실 4회를 막은 좋은 규칙이지만, **낡은 제목을 지우는 것도 함께 막는다.** 그래서 유령이 늘어난다.

**근본 원인**: 로드맵 하나가 **"현재 상태 대장"과 "작업 일지"를 겸한다.** 일지는 덧붙이기가 맞고(지우면 역사가 사라짐) 대장은 덮어쓰기가 맞은데(안 고치면 거짓말이 됨), 둘이 **한 줄에** 섞여 있어 어느 규칙도 제대로 작동하지 못한다.

## 2. 설계 — 파일을 쪼개지 않는다. 한 줄을 쪼갠다

파일 분리(대장 파일 / 일지 파일)는 **채택하지 않는다.** 상태와 근거가 멀어져 두 번 읽어야 하고, `project_notes.md`가 이미 일지 역할이라 3파일이 되며, 링크 관리 부담이 이행을 좌초시킨다.

대신 **항목마다 「상태 줄」을 한 줄 위에 새로 붙인다.** 기존 줄은 **한 글자도 건드리지 않는다.**

```markdown
- ✅ **보호 계정 가드** — 1·2차 + deleteAuthUserByEmail 가드까지 완결 · `be35aba`
* **보호 계정 가드 — fb01·hmnotice·admin 정지/삭제 원천 차단 (1차 구현 ✅ …)**: …기존 4,672자 그대로…
```

이 구조가 갖는 성질:

- **이행이 순수 추가다.** 삭제 0줄 → ④-2와 충돌하지 않는다. 기록 유실 4회 전례가 재현될 여지가 없다.
- **먼저 만나는 것이 참이 된다.** 낡은 제목은 아래 남지만, 눈이 먼저 닿는 줄이 항상 최신이다. 이것이 이 작업의 전부다.
- **진척이 숫자로 보인다.** "상태 줄 없는 항목 수" = 80 → 0.

### 2-1. 상태 줄 문법

```
- <토큰> **<제목>** — <한 문장 요약> · <근거>
```

- 한 줄, **개행 금지**, 요약은 **120자 이내**. 길어지면 그건 본문이다.
- `<토큰>`은 아래 5종 중 하나. 늘리지 않는다 — 종류가 많아지면 판정에 시간이 들고, 시간이 들면 안 붙인다.

| 토큰 | 뜻 | 붙이는 조건 |
|---|---|---|
| ✅ | 완료 | **근거를 댈 수 있을 때만.** 커밋 해시 또는 `파일:행` |
| 🔜 | 다음에 할 것 | 실제로 착수 예정인 것만. "언젠가"는 💡다 |
| ⏸ | 명시적 보류 | 안 하기로 정한 것. 사유 한 조각을 요약에 넣는다 |
| 💡 | 아이디어 | 착수 미정. §2 아이디어 메모의 기본값 |
| ❓ | **확인 필요** | 실물을 확인하지 못했다 |

### 2-2. ❓가 이 스펙의 핵심이다

**확인하지 않은 항목에 ✅·🔜·⏸를 붙이는 것을 금지한다. 전부 ❓다.**

오늘 유령 4건은 전부 *추측 판정*이었다. 파일명을 알고 있다고 해서 그 기능이 온전한 것은 아니다 — Phase 5.8이 정확히 그 형태였다(파일도 커밋도 있는데 드라이브 단계가 통째로 죽은 채 "완료" 보고가 나갔다).

**❓는 부끄러운 상태가 아니라 정상 상태다.** 80개를 다 판정할 필요가 없다. 확인한 것만 판정하고 나머지는 ❓로 두면, 그 자체가 "여기는 아직 모른다"는 정확한 정보다. 지금은 그 정보조차 없다.

**✅에는 근거를 반드시 붙인다** — 커밋 해시 하나 또는 `파일:행` 하나. `AGENTS.md` §1-1 2단계 요건의 경량판이다. 근거를 쓰려면 그 줄을 실제로 열어야 하므로, 사후 검증(비싼 자원)이 사전 자기검열(공짜)로 옮겨간다.

### 2-3. `AGENTS.md` ④-2 개정 (이행 완료 후 반영)

> **④-2 append-only (2026-08-13 개정)**: 공유 문서의 기존 줄은 지우지 않는다. 커밋 전 `git diff --numstat`의 삭제 열이 0이 아니면 정지한다.
> **예외 — 상태 줄 1줄**: `development_roadmap.md`의 **상태 줄(`- <토큰> **제목** — …`)은 덮어쓰기가 의무다.** 상태가 바뀌었는데 이 줄을 안 고치면 그것이 규칙 위반이다. 본문(그 아래 모든 줄)은 예외 없이 append-only를 유지한다.
> 즉 **대장은 덮어쓰고 일지는 쌓는다.** 한 줄만 예외이므로 `--numstat` 확인은 계속 유효하다(상태 줄 갱신 1건당 삭제 1줄이 정상).

## 3. 기계 점검 — 규칙만 두면 죽는다

이 프로젝트에는 전례가 있다. `project_notes.md` 최상단 **🔒 현재 작업 중 파일** 목록은 1년 가까이 규칙으로만 존재했고 실측 결과 **파일에 아예 없었다**(`🔍 0건`). 아무도 갱신하지 않았다. 그래서 이 스펙은 **실행 가능한 명령**을 함께 정한다.

기존 `scripts/check_roadmap_status_drift.sh`(모순 탐지, `26c1767`에서 결함 2건 수정됨)에 **점검 하나를 추가**한다.

**신설 점검 — 상태 줄 없는 최상위 항목**
- `^\* ` 로 시작하는 줄 중, **바로 위 줄이 상태 줄(`^- [✅🔜⏸💡❓] `)이 아닌** 것을 센다.
- 이행 중에는 실패시키지 않고 **진척만 출력**한다: `상태 줄 없는 항목: 43 / 80 (이행률 46%)`
- 이행 완료(0건) 후에 `exit 1`로 승격한다 → 이후 새 항목은 상태 줄 없이 추가될 수 없다.

**부산물 — 로드맵 한 장 요약 (실질적으로 이게 제일 큰 이득)**

```bash
grep -E '^- [✅🔜⏸💡❓] ' development_roadmap.md
```

80줄짜리 현황표가 나온다. **지금은 현황을 알려면 89KB를 훑어야 한다.** `package.json`에 `"roadmap"` 스크립트로 등록한다. 세션 시작 시 로드맵 전문 대신 이 요약만 읽으면 되므로 **토큰 비용도 같이 내려간다**(`CLAUDE.md`의 비용 주의 항목과 정합).

## 4. 이행 순서 — 한 번에 하지 않는다

80개를 한 커밋에 처리하면 diff가 거대해지고, 거대한 diff는 아무도 검토하지 않으며, 검토되지 않은 대량 편집이 기록을 잃은 전례가 이 저장소에 4회 있다.

| 단계 | 범위 | 규모 | 비고 |
|---|---|---|---|
| **1** | 문법·스크립트·규칙 확정 | — | 이 문서 + 점검 스크립트 확장 |
| **2** | §1 Phase 1~11 | 최상위 ~25개 | **유령이 전부 여기서 나왔다.** 여기부터 |
| **3** | §2 아이디어 메모 | ~50개 | 대부분 💡 일괄이라 싸다 |
| **4** | §3 보안 감사 권장 | ~5개 | |
| **5** | ④-2 개정 반영 + 점검 `exit 1` 승격 | — | 0건 도달 후 |

**단계마다 지킬 것**
- `npm run check:docs` 통과
- `git diff --numstat`의 **삭제 열 0** (상태 줄을 새로 붙이기만 하므로 반드시 0이어야 한다. 0이 아니면 본문을 건드린 것이다 → 정지)
- 단계별로 **커밋을 나눈다**

## 5. 하지 않는 것 (명시)

- **본문 요약·정리·재작성 금지.** 이번 작업에서 기존 줄의 내용을 건드리지 않는다. 유혹이 크지만(4,672자짜리 줄을 보면 정리하고 싶다) 그게 기록 유실 4회의 경로였다.
- **기존 제목 괄호의 낡은 표기를 지우지 않는다.** 상태 줄이 위에 있으므로 실해가 없고, 지우면 append-only 위반이다.
- **본문을 하위 항목으로 들여쓰기 금지.** 렌더링은 나아지지만 그건 삭제를 동반하는 편집이다. 이행이 끝난 뒤 별건으로 판단한다.
- **80개 전건 판정 금지.** 확인한 것만 판정하고 나머지는 ❓. (§2-2)
