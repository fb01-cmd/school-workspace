# 공동교육 계정 포털 접속 차단 스펙 v1 (2026-08-11, Claude)

> 배경: 로드맵 §2 "공동교육 학생 계정 → 포털 접속 원천 차단" (2026-08-07 발견 → 2026-08-11 사용자 방향 확정).
> 공동교육과정 OU(`/학생/공동교육`, `/학생/공동교육과정(26)` 등)의 계정(s10@, ch_01@ …)은
> **타교 학생용 계정이라 이 포털의 대상이 아니다.** 현재는 비학번 이메일이라 로그인 시
> teacher(승인 대기)로 분류돼 승인 대기열을 오염시키고, 오승인 시 교사 화면이 열린다.

## 0. 위험 실측 (이 스펙의 근거)

1. **역할 오분류**: sync-user는 "5자리 숫자@" 외 이메일을 전부 교사 후보로 취급 — 공동교육 계정이 로그인하면 `role: "teacher", isApproved: false` 문서가 생성된다.
2. **Firestore 규칙 관통 (더 중요)**: 배포 규칙의 `isTeacher()`는 `role in ['teacher','super_admin']`만 보고 **isApproved를 보지 않는다** — 승인 대기 상태여도 규칙상 교직원으로 통해 `settings/{domain}` 쓰기, `teacher_profiles` 읽기 등이 열린다. 공동교육 계정이 한 번 로그인하면 이 상태가 된다.
3. 차단 없이 두면 승인 대기열에 정체불명 계정이 쌓여 오승인(사람 실수) 확률이 누적된다.

## 1. 데이터 모델

- `settings/{domain}` 문서에 필드 추가: **`blockedOuPaths: string[]`** — 차단할 OU 경로 목록 (예: `["/학생/공동교육", "/학생/공동교육과정(26)"]`).
- **매칭 규칙 (하위 OU 포함)**: 계정의 `orgUnitPath`가 목록 항목과 ① 정확히 같거나 ② `항목 + "/"`로 시작하면 차단. 비교 전 양쪽 trim, 후행 `/` 제거 정규화.
- 저장 위치를 settings로 두는 이유: 환경설정 화면의 기존 저장 흐름(`setDoc merge:true`) 재사용, OU 경로는 민감정보 아님(전 구성원 읽기 무해). 쓰기 권한은 기존 settings와 동일(규칙 변경 없음). 하드코딩 금지 — OU 개편 시 관리자가 직접 조정.

## 2. 서버 차단 관문 — sync-user (Claude 소관: 인증 가드)

`src/app/api/auth/sync-user/route.ts` 개편:

1. `checkIsWorkspaceAdmin` → **`getWorkspaceProfile`**로 확장: 기존 `users.get(projection: "basic")` 호출 **그대로**에서 `isAdmin`과 함께 **`orgUnitPath`를 같이 반환** — 추가 API 호출 0.
2. 비학번 이메일 경로에서, GWS 조회 후 settings의 `blockedOuPaths`와 매칭(§1 규칙). 매칭 시:
   - users 문서 **생성·갱신하지 않는다.**
   - 같은 이메일의 기존 users 문서가 있으면 **삭제한다** (과거 teacher 잔재의 재로그인 자연 정리 — §0-2 구멍이 로그인 시도만으로 닫힘).
   - `403` + `{ error: "이 포털은 효명고등학교 구성원 계정만 사용할 수 있습니다.", blocked: true }` 반환.
3. **fail-open 수용 기록**: GWS 조회 실패(자격증명·일시 장애) 시 orgUnitPath를 알 수 없음 → 현행 isAdmin 판정과 동일하게 통과(teacher 승인 대기行). 차단이 가용성보다 우선할 만큼의 위협 모델이 아님(오승인 관문이 뒤에 있음). 단 조회 실패 로그는 남긴다(현행 유지).
4. **학번 형식(5자리@) 경로는 검사하지 않는다** — 이 경로는 GWS 조회 자체가 없어(호출 0 유지) 검사하려면 신규 호출이 필요한데, 학번 규약은 본교 학생 전용이고 공동교육 계정은 전부 비학번 형식(실측 s10@·ch_01@)이라 실익이 없다. 차단 OU에 5자리 이메일 계정이 생기는 경우 통과하는 한계는 수용하고 여기 기록해 둔다.
5. **보호 계정 3종(fb01@·hmnotice@·admin@)은 차단 판정 대상에서 제외** (AGENTS.md 인프라 계정 규칙 4 — 잘못된 OU 등록으로 인프라 계정이 잠기는 사고 방지. 이 3계정은 blockedOuPaths와 무관하게 항상 통과).

## 3. 클라이언트 — 차단 응답 처리 (Claude 소관, 소규모)

현행 실측: sync-user 실패 시 `handleUserRoles`가 throw만 하고 **로그인 세션은 남는다.**
게다가 `AuthContext`의 자가 치유(users 문서 없으면 sync-user 재호출)가 차단 계정에서
**매 페이지 로드마다 403 재시도 + 로딩 잔류**가 된다. 따라서:

1. `handleUserRoles`: 응답이 `blocked: true`면 **`signOut()` 후** 전용 에러(예: `BlockedAccountError`)를 던진다 — 세션 잔류·재시도 루프 원천 제거.
2. 로그인 화면: 이 에러를 받으면 서버가 준 눈높이 메시지를 그대로 표시(기존 에러 표시 경로 재사용, 신규 UI 불요).
3. AuthContext 자가 치유 경로의 catch도 동일 — blocked면 signOut (콘솔 에러만 남기고 방치 금지).

## 4. 환경설정 UI (Antigravity)

- `OUConfiguration.tsx`에 "**포털 접속 차단 조직단위**" 섹션 신설 — 기존 OU 선택 UI 문법(프리페치된 `useAuth().orgUnits` 드롭다운) 재사용, 목록에 추가/삭제, 저장은 기존 `handleSaveSettings`에 `blockedOuPaths` 병합(merge:true 유지 — 다른 필드 보존 주석 준수).
- 안내 문구(개발 용어 금지): "여기에 등록한 조직단위와 그 하위 조직단위의 계정은 이 포털에 로그인할 수 없습니다. 공동교육과정처럼 우리 학교 구성원이 아닌 계정을 막는 용도입니다."
- 위험 안내 1줄: "교직원·학생 조직단위를 등록하면 해당 구성원 전체가 로그인할 수 없게 되므로 주의하세요." (서버는 보호 계정 3종만 예외 — 광범위 오등록은 관리자 책임 영역, 별도 가드 없음. 등록 시 확인 다이얼로그 1회면 충분.)

## 5. 기존 오염 일회 정리 (Claude 소관)

- §2-2의 재로그인 자연 정리는 "로그인을 다시 해야" 작동 — 로그인 안 하는 잔재 문서는 남는다.
- inspect 스크립트(읽기 전용): users 전수(현재 ~20건)에서 비학번·`isApproved: false` teacher 문서를 나열하고 GWS `orgUnitPath` 대조 → 차단 OU 소속 목록 출력.
- cleanup 스크립트: inspect 결과를 눈으로 확인 후 해당 users 문서만 삭제(이메일 명시 배열, 보호 계정 3종 제외 가드 포함 — fail-safe 전례 구조). Firebase Auth 레코드는 삭제 불요 — users 문서가 없으면 규칙상 아무 권한이 없다.

## 6. 검증

1. 매칭 함수는 순수 함수로 분리(`isBlockedOuPath(path, list)`) — 자가 테스트 스크립트에 단위 케이스(정확 일치·하위 포함·후행 슬래시·비매칭·빈 목록).
2. 서버 실측: 차단 OU의 실계정(s10@ 등)으로 sync-user 직접 호출(admin SDK 커스텀 토큰 또는 기존 테스트 계정 패턴) → 403·문서 미생성·기존 문서 삭제 확인.
3. 회귀: 정상 교사·학생·수퍼어드민 로그인 무영향(자가 테스트 + 배포 후 실사용 자연 확인). 보호 계정 3종 통과 확인.
4. 실기기: 차단 계정 로그인 시 메시지 표시 + 세션 미잔류 — 실사용 첫 회 또는 사용자 직접 확인(증상 소멸 기준).

## 8. 비차단 후속 (별도 판단, 이 스펙 범위 밖)

- **firestore.rules `isTeacher()`에 `isApproved == true` 조건 추가 검토** — §0-2의 구멍(승인 대기 교사가 규칙상 교직원 통과)은 공동교육 계정만의 문제가 아니라 신규 부임 교사 승인 대기 중에도 존재. 다만 승인 전 화면 흐름(프로필 제출 등)이 어디까지 규칙에 기대는지 전수 조사가 선행돼야 하므로 **별도 Claude 리뷰로 분리** — 이 스펙에서 손대지 않는다.
