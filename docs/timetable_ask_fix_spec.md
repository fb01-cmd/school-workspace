## 0. 발안 원문과 요구의 핵심

> *"일과계가 '이경호 선생님 1교시가 5일 연속인데, 너무 많은 것 같아. 이걸 해결할 방법은?' 이라고 AI에게 물어보면, AI가 맞교환 체인으로 해결할 수 있는 수준에서 방법을 알려주는 거. 누구랑 누구를 바꾸고 … 바꾸면 해결됩니다. 대신 추가로 생기는 감점 요소들을 다 알려주고 일과계가 수락하면 고고. 지금 자동작성 메뉴에 붙은 시간표 설명이나 개선제안 따위보다 훨씬 실용적. 저 메뉴들은 해결책을 말 안 해주기 때문에 무쓸모야."*

요구를 셋으로 가른다:

1. **질문이 자유문이다** — 감점 목록에 없는 불만("1교시가 5일 연속")도 받는다.
2. **답이 실행 가능해야 한다** — "누구랑 누구를 바꾸라"까지, 부작용(새 감점) 전부와 함께.
3. **수락하면 그대로 적용된다** — 보고서가 아니라 버튼이다.

## 1. 대원칙 — AI는 통역, 수(手)는 엔진

**AI는 질문을 해석만 하고, 교환 수는 절대 만들지 않는다.** AI는 그리드 전문을 볼 수 없고 자기 제안이 새 하드 위반을 만드는지 검증할 수 없다(fix_assist_spec §2-1 — 이 저장소의 확립된 철칙). 수는 해결안 탐색 엔진(fixFinder — v1 학급 내, v2 학급 간 `swap_pair`, 본 스펙의 v3 체인)이 만들고, **검사기(validateTimetable)가 전수 채점**한다. 그래서 "추가로 생기는 감점"이 추정이 아니라 **정확한 수치**로 나온다.

역할 분담:

```
질문(자유문) ──AI(가명화·해석 1회)──▶ 정형 목표(§2) ──엔진(체인 탐색 §3)──▶ 계획+부작용 ──사람 수락──▶ 기존 draft_op 순차 적용
```

적용 경로를 새로 만들지 않는다 — 미리보기는 기존 `analyzeOpImpact`, 적용은 기존 `draft_op`(fix_assist_spec §2-5 철칙 유지).

## 2. 질문 해석 — 정형 목표 어휘 (AI의 출력 공간을 좁힌다)

AI가 자유문을 아래 **목표 어휘 중 하나**로 번역한다. 어휘 밖 요구는 "이 질문은 아직 못 알아듣습니다 + 알아듣는 질문의 예"로 정직하게 반환한다(할루시네이션 봉쇄 — E2와 같은 방식).

```ts
export type AskFixGoal =
  | { kind: "teacher-period-days"; teacherEmail: string; period: number; maxDays: number }
    // "T의 p교시가 주 N일을 넘지 않게" — 발안 예시("1교시 5일 연속")가 정확히 이것
  | { kind: "teacher-day-hours"; teacherEmail: string; day: number; maxHours: number }
    // "T의 d요일 수업을 N시간 이하로" (S1의 일반화 — 임계값을 질문이 정한다)
  | { kind: "subject-rotation"; grade: number; classNum: number; subjectName: string }
    // "c반 s과목이 매번 같은 교시인 것 좀" (S7과 동일 판정 재사용)
  | { kind: "move-cell"; grade: number; classNum: number; day: number; period: number }
    // "c반 d요일 p교시 수업을 다른 데로" (가장 원초적 — 목표는 '그 셀이 비거나 다른 수업')
  | { kind: "existing-detail"; code: SoftCode; key: string; day: number };
    // 질문이 기존 감점과 일치하면 기존 표적 경로로 (F-1 목록과 같은 입력)
```

- **성공 판정은 목표별 순수 함수다** (엔진 구현, AI 무관): 적용 후 그리드에서 목표 조건 충족 여부를 계산한다. 예: `teacher-period-days` → 그 교사가 그 교시에 서는 요일 수 ≤ maxDays.
- 해석 파이프라인은 **E2(말로 입력)와 동일 골격**을 재사용한다: 실명·이메일은 전송 전 가명(T01…) 치환, 응답 역치환, 치환표는 요청 생명주기 안에서만(phase9c_e_spec §2 — **가명화 제거 변경은 Claude 재검토 필수**). 과목명·학급번호는 개인정보가 아니므로 치환 대상이 아니다.
- AI 호출은 **질문당 1회**(해석만). 모델은 기존 사다리(`GEMINI_MODEL_LADDER`) 그대로. 해석 결과는 "이렇게 이해했습니다: ○○" 확인 문장으로 화면에 먼저 보여준다 — 오해석 상태로 탐색부터 돌지 않게.

## 3. 체인 탐색 (v3) — 2~3수 연쇄

### 3-1. 탐색 구조 — 빔 서치 + 예산 상한

1수 후보 생성은 기존 그대로(이동·학급 내 맞교환·학급 간 `swap_pair`). 체인은 그 위에 얹는다:

```
후보₁ = 목표 원인 셀들의 1수 전개 (기존 생성기)
각 후보를 (목표 충족 여부, 신규 하드=0, 검사기 총점)으로 채점
목표 충족 후보가 있으면 → 종료 (1수 해답)
없으면 → 상위 K개(빔 폭, 기본 8)만 남기고 각 상태에서 다시 1수 전개 → 재채점 → …
중단 조건: 깊이 3 도달 / 검사기 평가 예산(기본 600회) 소진 / 목표 충족
```

- **모든 접두 상태가 신규 하드 0을 유지한다.** 3수 계획의 1수만 적용된 순간에도 유효한 시간표여야 한다 — 적용이 기존 `draft_op` 순차(수 단위 undo 가능)이기 때문이고, `swap_pair`가 교사 겹침을 1수 안에서 상쇄하는 원자 프리미티브라 이 조건이 현실적이다.
- 비용: 검사기 1회 ≈ 5.4ms 실측(fix_assist_spec §2-6) → 예산 600회 ≈ 3.2초. **동기 금지, 청크 실행**(`findFixCandidatesAsync` 패턴 — 25회마다 양보 + 진행률). 예산 소진 시 "찾은 데까지" 최선 계획을 부분 답으로 내되 `resolvesGoal: false`를 명시한다.
- 같은 상태 재방문 제거: 연산 정규화 키(opKey)의 집합으로 지문을 만들어 중복 상태를 버린다.

### 3-2. 반환 형태

```ts
export interface FixPlan {
  goalText: string;            // "이경호 선생님의 1교시를 주 3일 이하로" (역치환 완료)
  steps: FixCandidate[];       // 수순 — 각 수는 기존 FixCandidate 그대로 (desc·delta·sideEffects)
  resolvesGoal: boolean;
  finalSoftTotal: number;      // 전 수 적용 후 공식 점수
  newPenalties: TermPenaltyDetail[]; // 적용 후 "새로 생기거나 커진" 감점 전부 — 수락 전 고지용 (요약 아님)
}
```

**부작용 고지는 전수다.** 기존 카드의 "최대 3건" 요약과 달리, 수락 버튼 앞에서는 새 감점 전부를 보여준다 — 발안 원문의 *"추가로 생기는 감점 요소들을 다 알려주고"* 가 요구 그 자체다.

## 4. 화면 — 자동 작성 탭의 「물어보고 고치기」

- **위치**: 초안 화면(DraftAutoTab)의 AI 카드 자리. **E-4(개선 제안)는 이 기능이 서면 제거한다** — 사용자 판정(*"해결책을 말 안 해주기 때문에 무쓸모"*)이 확정이고, fix_assist_spec §4도 이미 "탐색기가 대체한다"고 적어 두었다. E-3(설명)은 유지.
- **흐름**: 질문 입력 → ①해석 확인 문장(오해석이면 여기서 끝) → ②탐색 진행률 → ③답 카드:
  - 수순을 사람 문장으로: *"1) 2학년 3반 월요일 1교시(미적Ⅰ·이경호)와 목요일 5교시(영Ⅱ·권성민)를 맞바꿉니다. 2) …"* (기존 desc 재사용)
  - **새로 생기는 감점 전부** + 최종 점수 변화
  - [한 수씩 미리보기] → 기존 미리보기 모달 / [모두 적용] → draft_op 순차 / 적용 후 개별 undo 가능 안내
- 실패 문구는 출구를 단다(AGENTS ui-copy 5): 못 푼 경우 "어디까지 시도했고 무엇에 막혔는지"(예: "이경호 선생님의 1교시 5칸 중 3칸은 옮길 수 있었지만 나머지 2칸이 동시수업 밴드에 묶여 있습니다").
- 문구에 "체인"·"빔"·"엔진" 금지 — "여러 번 맞바꿔서", "찾아보기" 계열로.

## 5. 비용·개인정보 (AGENTS ⑪ 읽기량 1줄 포함)

- **AI**: 질문당 1회 (해석만). 탐색·채점은 호출 0회. 현행 Gemini 선불 키 기준 해석 1회 ≈ 프롬프트 1~2k 토큰 — 하루 수십 질문 수준이면 비용 무시 가능. 무료 키로 회귀 시 20회/일 한도 안에서 동작(질문당 1회라 감당).
- **읽기량**: Firestore 추가 읽기 **0건** — 초안·모델은 화면이 이미 들고 있는 것을 쓴다. 적용 시 쓰기는 기존 draft_op 경로 그대로.
- **개인정보**: E2 가명화 파이프라인 재사용(§2). AI 전용 쓰기 경로 없음(spec §0 철칙 — AI 출력은 표시 전용 + 사람 확인 후 정규 API).

## 6. B6 합류 — 말로 넣는 「부탁성 희망」 (soft 금지)

지금 등록부는 확정 금지(assign/move)뿐이라 *"금요일 오후는 되도록 비워 주세요"* 같은 부탁을 담을 곳이 없다. 질문지 회수(§3 서열 확정)로 대기가 풀린 항목.

- **저장 모델**: `TeacherSlotBan`에 `soft?: boolean` 추가 (기본 false = 현행 하드 금지와 완전 호환, 마이그레이션 없음). soft 항목은 솔버의 `bannedSlots`(하드)에 넣지 않는다.
- **새 감점 코드 S8 「교사 희망 위반」**: soft 금지 슬롯에 그 교사 수업이 배치되면 1점/건. 검사기 집계 + 화면 표시 + fixFinder 표적(원인 셀 = 그 슬롯의 그 교사 수업). 절대치는 11월 리허설 조정 대상(S6·S7과 함께).
- **말로 입력(E2) 확장**: 해석 어휘에 셋째 kind — 문장이 "되도록·가능하면·피해 주세요"면 soft. 확인 다이얼로그에 "부탁(어길 수 있음)"임을 명시.
- **솔버 반영은 실측 관문을 통과해야 채택한다.** ⚠️ S7에서 배운 것: 낮은 가중 목표도 탐색 지형을 흔들어 금기(S4)를 되살릴 수 있다(2026-08-21 실측 — S7을 목적함수에 넣자 전 시드 S4 재발, 결국 검사기 전용으로 확정). S8도 같은 위험이 있으므로 **①검사기 전용으로 먼저 출시 → ②slotCost 반영 실험은 백지 벤치마크에서 S4=0·총점 기준선 이하 유지를 확인한 것만 채택.** 실험 없이 목적함수에 넣지 않는다.

## 7. 하지 않는 것

1. **AI가 수를 제안하는 경로** — §1 대원칙 위반. 영구 금지.
2. **자동 수락** — 사람이 수락해야 적용된다(9c-D 자동 교정 금지 철칙).
3. **깊이 4+ 체인** — 예산 제곱 증가. 3수로 못 푸는 것은 "학급 전체 편성 조정" 안내가 정직하다.
4. **활성(운영 중) 학기 직접 수정** — 대상은 초안(draft)뿐. 운영 중 시간표는 기존 개정·주간 오버레이 경로.
5. **질문 이력 저장** — 저장할 이유가 없고 읽기·쓰기 예산만 쓴다. 세션 내 상태로만.
