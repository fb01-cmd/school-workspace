# 쪽지 즐겨찾기·검색 스펙 (피드백 덤프 ⑧·⑨)

> 2026-08-18 작성 (Claude Fable 5). 근거: development_roadmap.md §2 피드백 덤프 ⑧⑨.
> **사용자 확정 (2026-08-18)**: 검색은 최근분 로컬 필터가 아니라 **본인 쪽지 전체(보존 기간 내) 검색** — *"최근 50건이면 선생님들은 그냥 50개를 눌러보면서 찾지."*

## §1 즐겨찾기 (⑧)

### 1-1. 저장 구조 — `starredBy` 맵, 값은 `true`

```
memos 문서에 추가: starredBy?: Record<email, true>
```

- `hiddenBy`·`reads`와 같은 본인별 맵 패턴. **값이 시각(ms)이 아니라 `true`인 이유**: 즐겨찾기함 조회가 이 필드의 **등호(==) 쿼리**여야 하기 때문(§1-3). 시각을 넣으면 범위(>) 쿼리가 되고, 맵 키가 사용자마다 달라 **복합 색인을 사용자별로 만들 수 없어** 조회가 성립하지 않는다. 별표 시각은 표시에 안 쓰므로 저장하지 않는다.
- 키에 점(.) — 갱신은 `FieldPath("starredBy", email)` 필수(기존 규약).

### 1-2. API — `star` 액션 (서버 경유, 기존 쓰기 규약)

```
POST /api/memo { action: "star", memoId, on: boolean }
```

- 자격 = **당사자**(발신자 또는 수신자). 비당사자 403. **읽음 여부 무관** — 별표는 수신확인 의미론을 건드리지 않는다(hide와 다른 점).
- `on: true` → `starredBy.{email} = true`, `on: false` → 키 삭제(FieldValue.delete). 멱등.
- 순수 자격 로직 `resolveStarEligibility(memo, email)` — hide와 달리 읽음 조건 없음. selftest 대상.

### 1-3. 즐겨찾기함 조회 — 등호 전용 쿼리 2개 (rules 통과·복합 색인 0 목표)

목록 밖으로 밀린 오래된 별표 쪽지 문제(로드맵 ⑧ 갈림길)의 해법. 최근 50건 구독과 별개로, **즐겨찾기 탭을 열 때 1회 조회**:

```
받은 별표: where("recipientEmails","array-contains", me)
           .where(FieldPath("starredBy", me), "==", true)
보낸 별표: where("senderEmail","==", me)
           .where(FieldPath("starredBy", me), "==", true)
```

- **firestore.rules 통과**: 두 쿼리 모두 기존에 실측 검증된 규칙 통과 조건(array-contains 본인 / senderEmail 본인)을 그대로 포함 — 규칙 무변경.
- **색인**: 등호 필터끼리는 Firestore가 단일 필드 색인 병합으로 처리하므로 **복합 색인 불요가 예상**(맵 하위 키는 자동 단일 색인). 단 §3의 정정 전례("복합 색인 1건 필요"가 실측으로 틀림)의 역방향 오류를 막기 위해 **검증 스크립트로 실측 확정이 구현 조건**이다. 실측에서 색인 요구가 뜨면 그때 색인을 만드는 것이 아니라 — 맵 키가 사용자별이라 만들 수 없으므로 — **폴백 설계로 전환**한다: 즐겨찾기 탭이 ⑨의 전량 조회를 재사용해 로컬 필터(비용은 검색과 동일, 탭 열 때만).
- `orderBy`를 붙이지 않는다(붙이면 사용자별 복합 색인 문제 재발) — 결과는 클라이언트에서 `createdAt` 정렬. 별표는 수십 건 규모라 무해.
- 읽기 비용: 탭 열 때 별표 문서 수만큼만. `hiddenBy` 필터는 결과에도 적용(삭제한 쪽지는 즐겨찾기에도 안 보임 — 단 starredBy는 남으므로 삭제 취소 개념이 생기면 자연 복원).

### 1-4. 파기와의 관계 — **별표도 365일 파기 대상 (확정, 사용자에게 묻지 않음)**

- 근거: 보존 기간은 **문서 단위의 단일 약속**이다. 쪽지에는 발신자와 다른 수신자들이 있고, 내 별표 하나가 남의 쪽지 파기를 막으면 상대방의 "1년 뒤 사라진다"는 기대(인벤토리·/privacy 고지)를 **개인이 무력화**하게 된다. 예외를 만들면 고지·인벤토리 전면 개정이 딸려온다.
- 별표의 의미 = "보존 기간 내 자주 찾는 쪽지의 바로가기"이지 영구 보관함이 아니다.
- UI에 별도 경고 문구는 두지 않는다(과잉 고지 — 보존 정책은 이미 /privacy가 고지). 장기 보관 실수요가 생기면 "내 문서로 복사" 같은 **별도 기능**으로 판단(§4 범위 제외).

### 1-5. 화면 (Antigravity)

- 목록 행·상세 헤더에 별(☆/★) 토글 — 클릭 시 `star` 액션, 낙관적 갱신 + 실패 롤백.
- 탭 확장: [받은쪽지함 | 보낸쪽지함 | **즐겨찾기**]. 즐겨찾기 탭 = §1-3 쿼리 2개 fetch(1회, onSnapshot 아님) → 합집합·중복 제거·시간순 정렬·hiddenBy 필터. 행 클릭 → 상세(받은/보낸 판정은 senderEmail로).
- 빈 목록 문구: "별표를 눌러 자주 찾는 쪽지를 모아두세요."
- 모바일: 별 표시 + 토글은 포함 가능(본인 화면 조작이라 열람 전용 원칙과 충돌 없음 — 삭제 전례), 즐겨찾기 별도 탭은 데스크톱 우선·모바일은 후순위.

## §2 검색 (⑨)

### 2-1. 방식 — 검색 실행 시 전량 조회 + 로컬 필터

Firestore에 전문 검색이 없으므로(외부 검색 서비스는 무료 원칙 위반), **검색을 실행하는 순간에만** 본인 쪽지 전량을 내려받아 브라우저에서 거른다:

- 조회 = 기존 두 목록 쿼리 형태 그대로(받은: array-contains 본인 / 보낸: senderEmail 본인) + `orderBy("createdAt","desc")` — **규칙·색인 기존 실측 그대로, 신규 0**. `limit(300)` 페이지네이션(`startAfter`)으로 끝까지.
- **세션 캐시 필수**: 결과 전량을 clientCache(TTL 5분)에 담아 연속 검색·키워드 수정 시 재조회 0. 캐시 유효 중 재검색은 읽기 0.

### 2-2. 읽기 비용 추산 (읽기 예산 규율 — 전수 조사 전 추산 의무)

- 교사 1인의 연간 쪽지 규모 추정: 전 교직원 공지 주 3~5건(연 150~250) + 부서·개인 연 100~200 수신, 발신 연 50~150 → **검색 1회 ≈ 300~600 reads** (보존 365일 상한).
- 발생 조건: **검색 실행 시에만**. 상시 구독 확장 아님. 5분 캐시로 연타 흡수.
- 최악 가정(교직원 80명 전원이 하루 1회 검색): ~4만 reads/일 — 무료 한도(5만/일)의 80%. 그러나 검색은 필요할 때 쓰는 기능이라 실제 빈도는 일 수십 회 규모(수천~1만 reads)로 추정 — **판정: 허용**. 개학 후 실사용에서 한도 근접 신호(할당량 소진 경고)가 보이면 그때 조회 상한(최근 6개월 등)을 논의한다 — 선제 제한은 두지 않는다(사용자 확정: 전체 검색).

### 2-3. 매칭 규칙

- 대상 필드: **제목·본문·발신자 표시 이름**(문서의 `senderName` 스탬프 + 현재 표시 이름 둘 다 — 이름이 GWS에서 바뀐 경우 양쪽 어느 쪽으로 찾아도 나오게) + 수신자 요약(`recipientSummary`, 보낸쪽지함용).
- 대소문자 무시, 공백으로 나눈 **다중 키워드 AND**(전부 포함하는 쪽지만). 조사·형태소 분석은 하지 않는다(과잉 — 부분 문자열 포함이면 충분).
- `hiddenBy` 필터 적용 — 삭제한 쪽지는 검색에도 안 나온다.

### 2-4. 화면 (Antigravity)

- 위치: 쪽지 화면 상단, 탭 줄 옆 검색 입력 1개(데스크톱). 입력 시작 시 전량 조회(캐시 우선) → 로딩 표시("전체 쪽지에서 찾는 중…") → 현재 탭(받은/보낸/즐겨찾기)의 결과로 목록 대체. 탭을 바꿔도 검색어 유지.
- 결과 0건: "'{검색어}'에 해당하는 쪽지가 없습니다."
- 비우면 즉시 원래 목록(최근 구독분)으로 복귀. 개발 용어 금지.
- 모바일 검색은 후순위(데스크톱 실사용 확인 후).

## §3 검증

- selftest(순수): `resolveStarEligibility`(당사자/비당사자/읽음 무관), 검색 매칭 함수(다중 키워드 AND·대소문자·필드 결합) — 매칭 로직은 `src/lib/memo/search_logic.ts`(순수)로 분리해 UI와 selftest가 공유.
- **실측 스크립트(구현 조건)**: `verify_memo_star.ts` — 실계정으로 별표 스탬프 → §1-3 쿼리 2개가 **색인 오류 없이** 별표 문서만 돌려주는지 + 미별표·비당사자 미포함 확인 → 흔적 삭제. 색인 요구 발생 시 §1-3 폴백으로 전환하고 스펙에 기록.

## §4 명시적 범위 제외

- 별표 쪽지의 파기 예외·영구 보관 — §1-4 확정. 장기 보관은 실수요 시 "복사" 계열 별도 기능.
- 외부 검색 엔진·형태소 분석 — 무료 원칙·과잉.
- 모바일 즐겨찾기 탭·모바일 검색 — 데스크톱 실사용 확인 후.
- 별표 시각 표시·별표 많은 순 정렬 — 실수요 후.
