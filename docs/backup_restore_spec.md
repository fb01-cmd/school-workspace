# Firestore 백업·복구 스펙 (2026-08-14, Claude Opus 5)

> 중간점검 ③ 처방 1번. 배경·근거는 [`midterm_ops_risk_2026-08-14.md`](./midterm_ops_risk_2026-08-14.md) §1.
> 이 문서가 정한 것: 무엇을·언제·어떻게 백업하고, **어떻게 되돌리는가**, 그리고 산출물(개인정보)을 어떻게 다루는가.

## 0. 전제 — 실측이 설계를 바꿨다

| 사실 | 출처 |
|---|---|
| Firestore 전량 **1,269 문서** | `scripts/inspect_firestore_volume.ts` 실행(2026-08-14) |
| 전량 백업 1회 ≈ **1,269 읽기 = 무료 일일 한도의 2.5%** | 위 |
| 관리형 백업·PITR·`gcloud firestore export`는 **Blaze(유료) 필요** | 무료 원칙과 충돌 |

→ **admin SDK로 읽어 JSON으로 떨구는 백업은 무료이고, 이 규모에서는 매일 돌려도 한도 안이다.** 백업이 없던 것은 비용 때문이 아니라 아무도 만들지 않아서다.

## 1. 대상 — 하드코딩하지 않는다

**컬렉션 목록을 코드에 적지 않는다.** `listCollections()`로 루트부터 재귀 순회한다.

근거: 오늘 `inspect_firestore_volume.ts` 초판이 정확히 그 실수로 실패했다. `discipline_records`·`memos`·`timetable_terms`를 최상위로 적었는데 실제로는 `컬렉션/{domain}/하위` 구조라 전부 0으로 나왔고, 합계가 1,000으로 **과소 집계**됐다. **목록을 손으로 적으면 새 컬렉션이 생겼을 때 조용히 빠진다.** 백업에서 조용히 빠지는 것은 백업이 없는 것과 같다.

### 1-1. 유령 부모 문서 함정 (필수 구현 사항)

Firestore에서 `memos/{domain}/items/...`는 **`memos/{domain}` 문서가 존재하지 않아도** 성립한다(경로 세그먼트일 뿐). 그리고 `collection.get()`은 **존재하는 문서만** 돌려주므로, 이 경우 `items` 하위 전체가 통째로 누락된다.

→ 순회는 반드시 **`CollectionReference.listDocuments()`** 를 쓴다. 이 API는 존재하지 않지만 하위 컬렉션을 가진 문서의 참조까지 돌려준다. 이 저장소는 `memos`·`discipline_records`·`timetable_*` 등이 모두 이 구조라 **이걸 틀리면 실사용 데이터 대부분을 놓친다.**

> **실증 (2026-08-14 첫 실행)**: 이 판단이 옳았다는 것이 즉시 확인됐다. 하드코딩 목록으로 센 `inspect_firestore_volume.ts`는 **1,269건**이었는데, 재귀 순회한 실제 백업은 **1,314건**이었다. 목록에 없어 통째로 빠졌던 컬렉션 10종:
> `timetable_drafts/(id)/drafts/(id)/classGrids`(30) · `timetable_venue_groups/(id)/groups`(18) · `timetable_simul_groups/(id)/groups`(11) · `promotion_logs/(id)/batches`(4) · `swap_requests/(id)/requests`(4) · `teacher_profiles_archive/(id)/profiles`(3) · `chrome_bookmarks_local`(2) · `homeroom_assignments`(1) · `roster_api_keys`(1) · `timetable_drafts/(id)/drafts`(1)
> 그중 **`roster_api_keys`(외부 공급용 API 키)와 `teacher_profiles_archive`(삭제 전 보관본)** 가 빠져 있었다. 백업에서 조용히 빠지는 것은 백업이 없는 것과 같다.

### 1-2. 값 타입 보존

Firestore 값에는 JSON에 없는 타입이 있다(`Timestamp`, `DocumentReference`, `GeoPoint`, `Bytes`). 태그 방식으로 왕복 가능하게 인코딩한다.

```json
{ "__fs__": "timestamp", "seconds": 1786000000, "nanoseconds": 0 }
```

**모르는 클래스를 만나면 조용히 문자열로 만들지 말고 즉시 중단한다.** 조용한 손상은 복구 시점에야 드러나고, 그때는 원본이 없다.

## 2. 세 갈래 — 정기 백업만으로는 부족하다

정기 백업만 두면 두 가지로 실패한다. ① 사람이 잊는다 ② 잊지 않아도 사고는 백업 사이에 난다.

그런데 이 시스템에서 데이터를 잃는 순간은 무작위가 아니다 — **일괄 삭제·마이그레이션·정리 스크립트를 돌리는 그 순간**에 몰려 있다.

| 갈래 | 시점 | 범위 | 주체 |
|---|---|---|---|
| **A. 위험 직전 스냅샷** | 파괴적 스크립트 실행 직전 | 그 스크립트가 건드릴 경로만 | **코드가 자동** |
| **B. 전량 백업** | 월 1회 + 학기 경계 | 전체 | 사람이 수동 |
| **C. 복구** | 사고 후 | 지정한 경로만 | 사람이 수동, 기본 예행 |

### 2-1. A가 우선순위 1인 이유

크론도, 사람의 기억도 필요 없고, **가장 위험한 순간을 정확히 덮는다.** 이미 관행이 일부 있다 — `scripts/migrate_fix_student_mapped_teachers.ts:88`이 `/tmp`에 JSON을 떨군다. 그걸 공용 헬퍼로 올려 **의무화**하는 것이 이 처방이다.

### 2-2. A가 덮지 못하는 것 (한계 명시)

**화면(UI)의 일괄 삭제는 A가 덮지 못한다.** Vercel 서버리스 함수는 파일시스템이 휘발성이라 durable한 산출물을 남길 수 없고, GCS 업로드는 Blaze가 필요하다. 따라서:

- UI 일괄 삭제·전출·졸업 경로 → **B(월 1회 전량)와 기존 복구 경로**에 의존한다. 계정 자체는 GWS 20일 내 복원(`listDeletedUsers`/`restoreDeletedUser`)이 있고, Firestore 문서는 B가 마지막 방어선이다.
- 이 격차를 줄이려면 크론 백업이 필요한데 산출물 저장소가 없다. **지금은 열어 둔다** — 무료 범위에서 해결책이 없고, 억지로 만들면 PII를 외부에 올리게 된다.

## 3. 복구 — 여기가 위험한 쪽이다

백업은 잘못돼도 백업이 없을 뿐이지만, **복구는 잘못되면 살아 있는 데이터를 덮어쓴다.** 그래서 복구 쪽에 가드를 몰아준다.

1. **기본은 예행(dry-run)이다.** 실제 쓰기는 `--apply`를 명시해야 한다.
2. **기본은 추가 전용(skip)이다.** 이미 있는 문서는 건드리지 않는다. 덮어쓰려면 `--overwrite`를 따로 준다.
3. **복구는 절대 삭제하지 않는다.** 백업에 없는 문서를 지우는 동작은 제공하지 않는다. "백업 시점으로 되돌리기"는 삭제를 동반하므로 훨씬 위험하고, 필요하면 그때 사람이 판단해서 개별 삭제한다.
4. **전체 복구는 `--all`을 명시해야 한다.** 기본은 `--path`로 지정한 경로만.
5. **적용 전에 요약을 출력하고 멈춘다** — 대상 문서 수, 신규/기존 내역, 예상 쓰기 수.
6. **쓰기 예산 표시** — 무료 쓰기 한도 2만/일. 전량 복구도 1,269로 여유지만 숫자를 보여 준다.

> 설계 선례: `scripts/publish_firestore_rules.ts`가 게시 전 대조 → 게시 → 검증 → **롤백용 이전 ruleset id 기록** 4단계를 갖췄다. 복구도 같은 격으로 만든다.

### 3-1. 왕복 검증 — 리허설하지 않은 복구는 복구가 아니다

`--verify`는 **쓰기 없이** "이 백업으로 정말 되돌릴 수 있는가"를 확인한다. 아카이브를 **디코드 → 재인코드 → 살아 있는 값과 대조**하므로, 예행(dry-run)이 건드리지 않는 복구 경로(디코딩)까지 전부 지나간다.

```bash
npm run backup:verify -- --from=~/school-backups/2026-08-14T0028_full
```

이 장치가 필요한 이유: 예행은 "무엇을 쓸지"만 보여줄 뿐 **값이 제대로 복원되는지는 검사하지 않는다.** `Timestamp`가 문자열로 굳어 있어도 예행은 통과한다. 인코딩 결함은 복구하는 날에야 드러나고, 그날은 원본이 없다.

**첫 실행 결과 (2026-08-14): 1,314건 전건 일치, 불일치 0.** 백업 직후와 월 1회 실행을 권한다.

## 4. 산출물 — 개인정보다

백업 파일에는 학생·교직원 개인정보가 **평문으로** 담긴다. 생활지도 기록·졸업 동의 서명·쪽지 본문까지 포함된다.

1. **저장 위치는 저장소 밖** — 기본 `~/school-backups/`. 저장소 안에 두면 언젠가 커밋된다. 이 저장소에는 PII 엑셀이 git 이력에 남은 전례가 있다.
2. **`.gitignore`에도 방어선을 둔다** — 경로를 옮기더라도 걸리도록.
3. **클라우드·메일·메신저로 옮기지 않는다.** 백업을 남에게 전달할 일이 생기면 그 자체를 개인정보 제공으로 보고 판단한다.
4. **보관 기한**: 최근 3개 + 학기 경계본 1개. 나머지는 지운다. 오래된 백업은 유출 위험만 늘리고 복구 가치는 떨어진다.
5. **`personal_data_inventory.md`에 등재**한다 — 개인정보가 있는 곳의 목록에 이 백업이 빠지면 그 문서가 거짓이 된다.

## 5. 산출물 형식

```
~/school-backups/
  2026-08-14T2130_full/
    manifest.json        # 생성 시각·문서 수·컬렉션별 집계·스키마 버전
    data.jsonl           # 한 줄에 한 문서: {"path": "...", "data": {...}}
  2026-08-14T2135_pre_cleanup_departed_teachers/
    manifest.json
    data.jsonl
```

- **JSONL**을 쓴다. 한 줄이 한 문서라 중간에 끊겨도 앞부분이 살아 있고, 큰 파일도 스트리밍으로 읽힌다.
- `manifest.json`에 **문서 수를 적고 복구 시 대조**한다 — 파일이 잘렸는지 알아야 한다.

## 6. 하지 않는 것

- **자동 스케줄 백업** — 산출물을 둘 곳이 없다(§2-2). 크론 슬롯도 2/2다.
- **암호화** — 지금은 하지 않는다. 로컬 디스크 밖으로 나가지 않는다는 규칙이 먼저이고, 키 관리를 잘못하면 복구 불가라는 더 큰 위험이 생긴다. 백업을 반출해야 할 일이 생기면 그때 판단한다.
- **증분 백업** — 1,269 문서에 필요 없다. 복잡도만 늘린다.
- **Firestore 규칙·색인 백업** — 규칙은 `firestore.rules`가 저장소에 있고 게시·롤백 스크립트도 있다. 색인은 콘솔 수동 관리라 별건(③ 잔여).
