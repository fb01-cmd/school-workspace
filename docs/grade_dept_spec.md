# 학년부 판정 스펙 — 이름으로 짐작하지 않는다

> **상태**: 설계 (2026-08-21 Claude Opus). 구현 착수 여부는 `STATUS.md`에서 본다.
> **발안**: 2026-08-21 사용자 — *"차라리 조직도에서 학년부는 워크스페이스 환경설정에서 '몇학년까지 있나요' 질문에 3학년까지라고 대답하면 자동으로 1, 2, 3학년 부서를 만들고 고정하던가 해야."*

## §0. 결론 한 줄

**부서와 학년의 연결을 이름 글자에서 뽑지 말고 설정에 적어 둔다.** 나머지 재료(학년 수·반 수·담임 학년/반)는 **이미 전부 구조적으로 저장돼 있다** — 빠져 있는 것은 이 연결 하나뿐이다.

---

## §1. 지금 무엇이 잘못돼 있나 (2026-08-21 실측)

### 1-1. 학년부 판정이 부서 이름 정규식이고, 그 정규식이 서로 다르다

| 어디 | 정규식 | 「1학년부」 |
|---|---|---|
| 조직도 편집 `OrgChartBuilder.tsx:632` | `/^([1-3])학년$/` — **끝까지 일치** | ❌ 학년부 아님 → **담임 반 선택 사라짐** |
| 조직도 트리 `OrgChartTree.tsx:256` | `/^([1-3])학년$/` | ❌ 같음 |
| 정렬 규칙 `src/lib/org/sort.ts:24` | `/^([1-3])학년/` — **끝 고정 없음** | ✅ 학년부로 취급 → 담임 반 순서 정렬 |

부서 이름은 관리자가 Workspace 환경 설정 §11에서 **자유 문자열로 입력**한다(`OUConfiguration.tsx:855` — `newDeptInput.trim()`을 그대로 배열에 넣는다). 즉 「1학년부」는 **정상 입력**인데, 그 순간 정렬과 화면이 서로 다른 판정을 하게 된다.

**증상의 성질이 나쁘다.** 에러가 안 난다. 담임 반 선택 칸만 조용히 없어지고, 쓰는 사람은 이유를 알 길이 없다.

### 1-2. `1~3` 하드코딩이 **세 곳**이고, 그중 하나는 권한 경로다

학년 수가 설정에 있는데도(`gradesCount`, 편집 UI는 1~12를 받는다) 담임 체계는 3학년까지만 안다.

| 어디 | 무엇 | 성격 |
|---|---|---|
| `OrgChartBuilder.tsx:632`·`OrgChartTree.tsx:256`·`sort.ts:24` | 부서 이름 정규식 `[1-3]` | 화면·정렬 |
| **`src/lib/discipline/server.ts:162`** | **담임 판정 자체가 `grade 1~3`만 통과** | **권한** |
| `HomeroomAssignmentTab.tsx:53` | `grades = [1, 2, 3]` | 화면 |

**⚠️ 가운데 줄이 중요하다.** 이건 표시 문제가 아니라 **생활지도 권한의 입구**다(`authz.ts:98` — 담임은 자기 반 `view`+`record` 자동 허용). `gradesCount`를 4로 올려도 **4학년 담임은 권한을 못 받는다.** 설정값과 코드가 어긋나 있고, 어긋난 쪽이 조용히 이긴다.

> 같은 파일 `HomeroomAssignmentTab.tsx:285`는 표시 반 수를 `classCounts`가 아니라 `Math.max(10, 배정된 반번호)`로 정한다 — 설정을 안 본다. 성격이 같은 결함이라 여기 적어 둔다.

### 1-4. 인접 결함 2건 (같은 뿌리)

- **공동담임 중복 경고가 학년부 안에서만 돈다** (`OrgChartBuilder.tsx:372`) — `${grade}학년` 부서 멤버 중에서만 같은 반 담임을 찾는다. **다른 부서에 소속된 담임과 겹치면 경고가 안 뜬다.** 담임 정보는 부서와 무관하게 저장되는데(§2) 검사만 부서 안에서 도는 탓이다.
- **담임 배지가 학년부 카드에서만 보인다** (`OrgChartBuilder.tsx:753` — `isGradeDept &&` 게이트). 같은 사람이 교과 부서 카드에 있으면 담임인 줄 모른다. `OrgChartTree.tsx:307`에는 이 게이트가 없어 **두 화면이 다르게 보인다.**

### 1-3. 같은 화면이 반 수는 설정에서 읽으면서 학년부 여부는 짐작한다

```ts
// OrgChartBuilder.tsx:632-636
const isGradeDept = /^([1-3])학년$/.test(deptName);          // ← 이름으로 짐작
const gradeNum = isGradeDept ? parseInt(deptName[0], 10) : 0; // ← 이름에서 숫자 파냄
const classCount = isGradeDept
  ? Number(schoolSettings?.classCounts?.[gradeNum] ?? 10)     // ← 반 수는 설정에서 읽음
  : 0;
```

두 줄 아래에서 설정을 읽으면서 두 줄 위에서는 글자를 세고 있다. **문제의 정체가 이 세 줄에 다 들어 있다.**

## §2. 이미 있는 것 — 새로 만들 필요가 없다

사용자가 *"'몇학년까지 있나요' 질문에 (…) 대답하면"* 이라고 제안한 그 질문은 **이미 물어서 저장해 두고 있다.**

| 재료 | 어디에 | 편집 화면 | 소비처 |
|---|---|---|---|
| 학년 수 | `SchoolSettings.gradesCount` | Workspace 환경 설정 (`OUConfiguration.tsx:451`) | 명렬표·클래스룸 배정·프로필·수동 배치 등 **7곳 이상** |
| 학년별 반 수 | `SchoolSettings.classCounts` | 같은 화면 (`OUConfiguration.tsx:494`) | 위와 같음 + 조직도 |
| **담임 학년·반** | `teacher_profiles.{isHomeroom, homeroom:{grade, class}}` | 조직도 편집 · 내 정보 · 수동 배치 | 정렬(`sort.ts:50`)·생활지도 권한·담임 현황 |

**핵심**: 담임 정보는 **이미 숫자 필드**다. 부서 이름에서 파생되지 않는다. 부서 이름은 오직 **「어느 부서 카드에 담임 선택 UI를 띄우고, 어떤 순서로 정렬할까」** 를 정하는 데만 쓰인다.

⇒ **빠져 있는 것은 「부서 ↔ 학년 번호」 연결 하나뿐이다.**

## §3. 설계

### 3-1. 저장 형태 — 프로필을 건드리지 않는다

`settings/{domain}`에 **연결 표 하나를 추가**한다. 기존 필드는 그대로 둔다.

```ts
interface SchoolSettings {
  departments?: string[];                      // 현행 유지 — 표시 순서의 단일 원본
  gradeDepartments?: Record<string, number>;   // 신설 — 부서 이름 → 학년 번호
  // 예: { "1학년": 1, "2학년": 2, "3학년": 3 }
  //     { "1학년부": 1, "2학년부": 2 }  ← 이름을 바꿔도 연결이 유지된다
}
```

**왜 부서에 id를 도입하지 않았나.** id가 이론적으로 더 깨끗하지만 대가가 크다 — `teacher_profiles.departments`가 **이름 문자열 배열**이고, 그것을 **`firestore.rules`가 직접 읽는다**:

```
// firestore.rules:154, 165
get(/databases/$(database)/documents/teacher_profiles/$(request.auth.token.email))
  .data.departments.size() > 0
```

이게 **쪽지·업무의 자격 관문**이다. 프로필의 필드 모양을 바꾸면 **보안 규칙과 데이터 마이그레이션이 동시에 걸리고**, 그 사이 구간에서 전 교직원이 쪽지를 못 쓰게 될 수 있다. 지금 고치려는 문제(담임 칸이 조용히 사라짐)에 비해 감당할 위험이 아니다.

연결 표만 추가하면 **마이그레이션이 0이다** — 기존 도메인은 `gradeDepartments`가 없고, 그때는 §3-2의 폴백이 지금과 똑같이 동작한다.

### 3-2. 판정 함수 하나로 모은다

새 파일 `src/lib/org/gradeDept.ts`:

```ts
/**
 * 부서가 몇 학년부인가. 0이면 학년부가 아니다.
 *
 * ⚠️ 부서 이름에 정규식을 직접 쓰지 마라. 이 함수만 쓴다.
 *    2026-08-21에 화면과 정렬이 서로 다른 정규식을 써서, 부서를 「1학년부」로
 *    개명하면 정렬은 학년부로 보는데 화면은 아니게 되는 상태였다.
 */
export function gradeOfDepartment(
  deptName: string,
  settings: Pick<SchoolSettings, "gradeDepartments" | "gradesCount"> | null | undefined
): number
```

판정 순서:

1. **연결 표가 있으면 그것이 답이다** — `settings.gradeDepartments?.[deptName]`
2. **없으면 이름에서 짐작한다(폴백)** — `/^(\d+)\s*학년/`으로 뽑고 **`1 ≤ n ≤ gradesCount`** 일 때만 인정
   - `[1-3]` 하드코딩이 사라진다
   - 끝 고정이 없으므로 **「1학년부」도 인정된다** — 지금의 불일치가 폴백 단계에서 이미 해소된다
3. 둘 다 아니면 0

**호출부 3곳을 이 함수로 교체한다**: `OrgChartBuilder.tsx:632` · `OrgChartTree.tsx:256` · `sort.ts:24`.

> `sort.ts`는 `settings`를 안 받는 순수 함수다. 인자를 하나 늘리거나, 호출부에서 미리 계산한 `gradeNum`을 넘기도록 시그니처를 바꾼다 — **구현 시 판단**(호출부가 5곳 안쪽이면 인자 추가가 단순하다).

### 3-3. 재발을 기계가 막는다

`scripts/check_screen_headers.ts`와 같은 방식으로, **부서 이름에 학년 정규식을 직접 쓰는 코드를 금지**하는 검사를 `npm run check:ui`에 얹는다.

- 금지 패턴: `학년` + `match(`/`test(` 이 같은 줄에 있으면서 파일이 `src/lib/org/gradeDept.ts`가 아닌 경우
- 시간표·엑셀 파서 계열(`src/lib/timetable/**`)은 **대상이 아니다** — 거기서 「N학년」을 뽑는 것은 부서 판정이 아니라 외부 문서 파싱이다. 경로로 제외한다.

### 3-4. 설정 화면 (Workspace 환경 설정 §11)

부서 목록의 각 행에 **학년 연결을 드러낸다.**

- 학년부로 연결된 행에는 딱지: `1학년부`
- 행마다 작은 선택기: `학년 없음 / 1학년 / … / {gradesCount}학년`
- **학년 수를 바꾸면**: 비어 있는 학년이 있을 때 *"3학년부가 없습니다. 만들까요?"* 로 **제안**한다. 자동으로 만들되 **잠그지는 않는다**.

> **왜 「고정」까지 가지 않는가.** 사용자의 발안에는 요구가 둘 들어 있다 — ⓐ 앞뒤가 맞을 것 ⓑ *"1학년 대신 1학년부라고 이름을 줄 수도 있는 거고"* = **이름은 자유일 것**. 부서를 잠그면 ⓐ는 되지만 ⓑ가 죽는다. **연결을 명시**하면 둘 다 산다 — 이름을 무엇으로 바꾸든 연결이 따라가므로 앞뒤가 맞는다.

### 3-5. 이 설계는 마이그레이션이 0이다 (그리고 그게 핵심이다)

전수 조사 결과 **부서 이름은 6가지 사본에 퍼져 있다**:

| # | 어디 | 형태 |
|---|---|---|
| 1 | `settings/{domain}.departments` | 문자열 배열 |
| 2 | `teacher_profiles/{email}.departments` | 문자열 배열 |
| 3 | `teacher_profiles/{email}.deptHeadMap` | **부서명이 객체 키** |
| 4 | `teacher_profiles_pending/{email}` | 위 둘 그대로 |
| 5 | `org_index/{domain}.profiles[]` | 프로필 통째 복제 |
| 6 | `teacher_profiles_archive/…` · 전출 작업 문서의 `archivedProfile` | 프로필 스냅샷 |

**이 스펙은 위 여섯 곳을 하나도 건드리지 않는다.** `settings`에 `gradeDepartments` 필드를 **더할 뿐**이다. 기존 도메인은 그 필드가 없고, 없으면 §3-2의 폴백이 지금과 동일하게 동작한다. ⇒ **배포 즉시 안전하고, 되돌리기도 필드 삭제 한 번이다.**

부서 id를 도입했다면 위 여섯 곳 + `firestore.rules` 두 줄 + Drive에 이미 만들어진 제출 파일 이름(§6-3)까지 걸린다. 그 대가를 치를 문제가 아니다.

## §6. 이 조사에서 같이 드러난 별건 (이 스펙의 범위 밖)

세 건 다 **학년부와 무관한 기존 결함**이다. 여기서 고치지 않되, 발견했으므로 적어 둔다.

### 6-1. 개명 마이그레이션이 절반만 옮긴다

`scripts/migrate_dept_rename_2026_08_13.ts`는 `settings.departments`와 `teacher_profiles.departments`만 치환한다. **빠진 것**:

- `teacher_profiles.deptHeadMap` — **부서명이 키**다. 개명하면 옛 키가 남아 **부장 표시가 사라진다**
- `teacher_profiles_pending` — 개명 시점에 승인 대기 중인 신청
- `org_index/{domain}` — 프로필을 통째로 복제하므로 `buildRosterIndex(..., {force:true})` 재조립이 필요하다(그냥 두면 최대 48시간 낡은 이름)
- `teacher_profiles_archive` · 전출 작업 문서의 `archivedProfile` — 전출 취소로 **복원되면 옛 이름이 되살아난다**

### 6-2. 부서명이 지워지지 않는 곳 두 군데 — **고치면 안 된다**

- `memos`·`tasks` 문서의 `recipientMeta.depts` — 발송 시점 부서명이 문서에 **영구 저장**된다. 개명해도 옛 쪽지는 옛 이름을 보여준다. **이건 결함이 아니라 올바른 동작이다** — 「그때 그 부서로 보냈다」는 사실 기록이므로 소급해 고치면 기록이 거짓이 된다.
- `audit_logs.details` — 같은 이유로 손대지 않는다.

### 6-3. 되돌릴 수 없는 것

`src/lib/tasks/logic.ts:286` — 담임이 아닌 사람의 제출 파일은 **`{부서명}_{이름}_{제목}` 형태로 Drive에 실물 저장**된다. 이미 만들어진 파일 이름은 마이그레이션으로 못 고친다. 부서 개명을 결정할 때 알고 있어야 할 사실이다.

---

## §4. 하지 않는 것

- **부서 id 도입** — §3-1의 이유. 필요해지면 별건으로 다시 판단한다.
- **`teacher_profiles.departments` 형태 변경** — 보안 규칙이 직접 읽는다.
- **학년부 자동 잠금** — §3-4의 이유.
- **시간표·엑셀 파서의 「N학년」 파싱 통일** — 같은 글자를 쓸 뿐 다른 문제다(외부 문서 파싱). 건드리면 범위가 터진다.

## §5. 구현 단위와 검증

| # | 무엇 | 검증 |
|---|---|---|
| 1 | `gradeOfDepartment` 신설 + 호출부 3곳 교체 | 자가 테스트: 「1학년」·「1학년부」·「1학년 담당」·「11학년」·`gradesCount=6`일 때 「4학년」 — 화면·정렬이 **같은 답**을 내는지 |
| 2 | `check:ui`에 정규식 직접 사용 금지 검사 | 일부러 어긴 코드를 넣어 실패하는지 확인(반대 방향 확인) |
| 3 | 설정 화면 §11에 학년 연결 선택기 + 학년 수 변경 시 제안 | 이름을 「1학년부」로 바꿔도 담임 반 선택이 **그대로 뜨는지** — 이 스펙의 목적 그 자체 |
| 4 | 개명 마이그레이션 스크립트 보강(`gradeDepartments` 키 + `pending`) | `APPLY=0` 미리보기로 계획 출력 → 실행 후 옛 이름 잔존 0 |

**1·2는 마이그레이션이 없고 그것만으로 지금 증상이 사라진다.** 3·4는 그 뒤에 해도 된다.
