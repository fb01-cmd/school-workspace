## §1 왜 셋인가 — 병목은 판단이 아니라 읽기다

2026-08-20 실측: 픽커 전수 대조 **76k 토큰** · 스펙 §8 검증 **119k 토큰**. 반면 *"어느 처방을 고를까"* 류 판단은 토큰을 거의 안 먹는다.

**Claude 비용의 대부분은 판단이 아니라 읽기에서 나온다.** 8/22 이후 용량이 4분의 1로 줄면 병목이 되는 것도 판단이 아니라 **검증**이다. 그런데 검증 규칙(AGENTS §1-1 — 주장이 산출물인 일의 2단계 검증)을 느슨하게 하면 이 저장소의 고질병(완료 주장 vs 실제)이 돌아온다.

**그래서 규칙을 깎는 대신 검증할 사람을 늘린다.** 이것이 세 번째 에이전트의 존재 이유다.

## §2 역할 — 셋의 경계

| | 맡는 것 | 절대 안 맡는 것 |
|---|---|---|
| **Claude** | 판단 · 스펙 작성 · **결정** · 되돌릴 수 없는 작업 설계 · 보안·개인정보 · 최종 검수 | 기계적 대량 편집 |
| **Antigravity** | 생산 — 구현 · UI · 대량 편집 · 저장소 탐색 | 결정 · 실기기 검증(불가) |
| **Codex** | **검증 · 조사 · 전수 대조 · 표적 감사** | **결정 · 스펙 확정 · 구현** |

### §2-1 Codex를 「검증 전담」으로 두는 이유

**생산자를 하나 더 만들지 않는다.** Antigravity가 생산을 하고 있고(2026-08-19~20 실측: 지시서 12항목·결함 8건·화면 4종을 정확히 수행), 여기에 두 번째 생산자를 얹으면 **"누가 뭘 했는지" 추적 대상만 셋이 된다.** 2026-08-19에 지시 없는 커밋의 출처를 반나절 추적한 전례가 있다.

**예외 하나**: **Antigravity가 두 번 이상 막힌 일**은 Codex에게 second opinion을 물을 수 있다. 이때도 **구현은 Antigravity가 한다** — Codex는 진단만 준다.

### §2-2 ⭐ 결정하는 입은 하나다

**Codex는 결정하지 않는다.** 스펙을 확정하지 않고, 우선순위를 정하지 않고, "이렇게 가자"를 쓰지 않는다. 조사 결과와 선택지까지만 낸다.

**근거는 2026-08-19 「조직도 메뉴」 사고다.** 사용자 결정과 Claude 제안이 문서 안에서 섞였고, 나중에 Claude가 **자기 제안을 사용자 결정인 줄 알고 사용자에게 반박**했다. 같은 날 `messaging_hub_ia_spec` §2-4에서도 같은 일이 벌어져 **사용자가 없앤 기능 2개가 화면에 되살아났다.**

**결정하는 입이 늘면 이 사고는 구조적으로 증가한다.** 조사는 셋이 해도 되지만 결정은 한 곳이어야 한다.

## §3 ⭐ 검증 결과를 어떻게 다루나 — 차등 재확인

**이 절이 이 규칙의 핵심이다.** Codex가 검증하고 Claude가 전건을 다시 확인하면 비용이 두 배가 되어 도입 이유가 사라진다. 그렇다고 그대로 믿으면 검증이 아니다.

**주장의 성격에 따라 다르게 다룬다.**

| Codex의 주장 | Claude의 처리 | 이유 |
|---|---|---|
| **「실패」·「결함 발견」** | **전건 재확인 (필수)** | **행동을 바꾸는 주장**이다. 틀리면 멀쩡한 코드를 고치게 된다 |
| 「통과」 | **표본 재확인** (전건 아님) | 틀려도 현상 유지다. 다만 "다 통과"가 무검증의 얼굴일 수 있으므로 표본은 반드시 본다 |
| **「판정 불가」** | **그대로 수용** | 보수적 방향의 주장이라 위험이 낮다. 대신 **무엇을 실행해야 아는지** 적혔는지만 본다 |

**비용이 실제로 줄어드는 이유**: 읽기 비용의 대부분은 **찾는 데** 들지 **확인하는 데** 들지 않는다. 2026-08-20 §8 검증에서 Codex는 119k를 썼고, Claude가 두 「실패」 주장을 재확인하는 데는 grep 두 번이면 됐다.

> **⚠️ 「전건 재확인」의 뜻**: 그 주장이 가리키는 `file:line`을 **직접 열어 본다**는 뜻이다. 요약을 읽고 그럴듯하면 넘기는 것은 재확인이 아니다.

## §4 프롬프트에 매번 넣을 것

2026-08-20 시험에서 Codex가 5개 중 2개를 「판정 불가」로 둔 것은 좋은 행동이었다. **그런데 그렇게 하라고 프롬프트에 명시했다.** 지시 없이도 그러는지는 확인되지 않았으므로, **매번 넣는다.**

1. **「판정 불가」를 허용한다** — *"실행해야 알 수 있는 것은 무리해서 통과/실패로 몰지 말고 판정 불가로 두고, 무엇을 실행해야 아는지 적어라"*
2. **스펙을 정답으로 전제하지 마라** — *"스펙에 적힌 기대치가 지금 코드와 다를 수 있다. 다르면 다르다고 보고해라"*
   - 이 문장 하나가 2026-08-20에 **스펙 §8-3의 낡음**을 찾아냈다
3. **근거는 `file:line`으로** — 근거 없는 단정은 그 자체가 실패다
4. **고치지 마라 / 커밋하지 마라 / git 명령을 쓰지 마라** (검증 과제일 때)
5. **읽기 명령은 허용한다** — Codex는 파일 읽기를 터미널로 한다. *"터미널 명령 금지"* 라고 쓰면 눈을 가리는 셈이다(2026-08-20 1차 시험 무효 사유)

## §5 권한·안전

**설정 위치**: `~/.codex/` (Codex) · `~/.gemini/antigravity-cli/settings.json` (`agy`)

| | 값 |
|---|---|
| 검증 과제 | **읽기 전용 샌드박스** (`--sandbox read-only`) |
| 구현 과제 | **건드릴 파일만 열거.** 디렉터리 통째로 열지 않는다 |
| 항상 금지 | `git push` · `gh` · `.env.local` · `~/.ssh/` · `rm -rf` |
| 절대 금지 | 승인 우회 옵션(`--dangerously-*`, `--full-auto`) — 이 저장소에서는 쓰지 않는다 |

**푸시는 Claude 또는 사용자만 한다.** 2026-08-19에 지시 없는 커밋이 올라온 전례가 있고, 배포는 되돌리기 비싼 작업이다.

## §6 기록·귀속

1. **커밋 메시지에 출처를 적는다** — *"Codex 2차 시험에서 찾음"*, *"agy 구현 + Claude 검수"*. git 작성자만으로는 구분이 안 된다(2026-08-19 전 커밋이 `antigravity`로 찍혀 있던 문제)
2. **검증 결과는 문서로 남긴다** — 누가 무엇을 찾았는지가 다음 판단의 재료다
3. **Claude가 놓친 것을 Codex가 찾으면 그 사실을 적는다.** 부끄러워서 지우면 규칙을 고칠 근거가 사라진다
   - 실사례: 2026-08-20 Claude는 「이메일 비노출」을 `HubOrgTree`만 grep 하고 통과 처리했다. Codex는 *"허브가 무엇을 렌더링하는가"* 를 따라가 `TaskStatusBoard`의 이메일 노출을 찾았다. **범위를 좁게 잡은 Claude의 실수**였고, 같은 날 같은 종류의 실수가 세 번 있었다

## §7 재검토 — 언제 이 규칙을 고치나

**이 초안은 관측 3회 위에 서 있다.** 다음 중 하나가 오면 다시 판단한다.

| 시점 | 무엇을 |
|---|---|
| **누적 10회** | §3의 「통과 표본 재확인」 비율을 줄일지. 그때까지는 유지 |
| **Codex가 틀린 「실패」 주장을 한 첫 사례** | 즉시 기록하고 §3을 강화한다. **한 번이라도 나오면 차등을 후퇴시킨다** |
| **2026-09-01** | 토큰 소모 누적치로 실익 재계산. 검증 1회당 100k 안팎이면 Max5 예산에서 몇 회가 가능한지 |
| 사용자 플랜 소진 | 아내분 계정으로 전환 — **사전 양해 필요**(사용량 공유) |

**측정해서 적을 것**: 과제 유형별 토큰(검증/구현/조사) · Claude 재확인에 든 추가 비용 · 「실패」 주장의 정확도.
