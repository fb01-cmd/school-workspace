# 쪽지 답장 스펙 — 스레드 왕복 (2단계 잔여분)

> 2026-08-18 작성 (Claude Fable 5). 1단계 [`memo_spec.md`](./memo_spec.md) §0 "2단계: 답장·스레드"의 확정판.
> 배경: 이미지 첨부 종결 직후 사용자가 답장 부재를 **핵심 누락 기능으로 격상** (roadmap §2 2026-08-18 기록 — "메신저 대체인데 왕복이 안 되면 반쪽").

## §0 설계 원칙 — 답장은 새 기능이 아니라 "수신자가 정해진 발송"이다

기존 쪽지 1통 = 독립 문서이고, 발송·푸시·알림 원장·읽음 확인·첨부·회수·보존이 전부 문서 단위로 이미 동작한다. 답장을 **별도 데이터 구조 없이 `send`의 변형**으로 설계하면 이 인프라가 전부 공짜로 승계된다. 이 스펙의 모든 결정이 이 원칙에서 나온다.

## §1 결정 ① — 답장 수신 범위: **원 쪽지의 발신자 1인, 서버 강제**

- **답장 = 받은 쪽지에 대해서만, 수신자 = 그 쪽지를 보낸 사람 1인.** 클라이언트가 보낸 수신자 목록은 무시하고 **서버가 원 쪽지의 `senderEmail`로 확정**한다(이중 방어 규칙 — UI를 신뢰하지 않는다).
- **전체 답장(reply-all)은 만들지 않는다.**
  - 사용자 확정 원칙과 충돌: "쪽지는 업무용, 소통은 구글 챗"(1단계 §11-2 그룹 제거 결정, 2026-08-13). 전체 답장은 쪽지를 단체 대화방으로 끌고 가는 문이다.
  - 전 교직원 공지(300명)에 전체 답장이 하나 나가면 300명이 푸시·알림을 받는다 — 알림 피로의 최대 리스크 지점을 구조적으로 봉쇄한다.
  - 여러 명에게 새로 알릴 일이면 기존 [쪽지 쓰기]가 그 동선이다 — 기능이 없는 게 아니라 자리가 다르다.
- 왕복 성립: A→B 발송, B가 답장(→A), A가 그 답장에 다시 답장(→B) … 체인은 자연히 1:1로 이어진다.
- 내가 **보낸** 쪽지에는 답장 버튼이 없다(자기 쪽지에 답장 = 재발송 혼란). 추가 전달은 새 쪽지로.

## §2 결정 ② — 데이터 모델: `memos` 문서 재사용 + 필드 2개

```
memos/{domain}/items/{memoId} 에 추가 (모두 선택 필드 — 기존 문서 소급 불요):
  threadId?: string   // 스레드 뿌리 쪽지의 memoId. 뿌리 자신에게는 없음
  replyTo?: string    // 직접 부모 쪽지의 memoId (v1은 선형 체인이라 사실상 직전 쪽지)
```

- 답장 발송 시 서버가 스탬프: `threadId = 부모.threadId ?? 부모.id`, `replyTo = 부모.id`. 답장의 답장도 같은 `threadId`를 물려받아 한 스레드로 묶인다.
- **firestore.rules 무변경.** 답장도 보통 쪽지 문서라 기존 읽기 규칙(발신자·수신자 본인만)이 그대로 적용된다. 원 쪽지가 30명에게 갔어도 **B의 답장은 A만 읽을 수 있다** — 전체 공개 답장이 규칙 차원에서 불가능하다(§1과 정합).
- **색인 무변경 — 스레드 전용 쿼리를 만들지 않는다 (구조적 제약).** 1단계 §3의 규칙상 통과 가능한 목록 쿼리는 받은쪽지함(array-contains 본인)·보낸쪽지함(senderEmail 본인) 두 형태뿐이다. `where("threadId","==",…)` 쿼리는 규칙을 증명할 수 없어 **거부된다.** 대신: 답장의 당사자는 항상 스레드 전 문서의 발신자거나 수신자이므로, **스레드 뷰 = 이미 구독 중인 받은/보낸 두 목록을 `threadId`로 로컬 그룹핑**하면 끝난다. 신규 쿼리 0·읽기 비용 0.
  - 수용 한계(명기): 두 목록의 `limit(50)` 밖으로 밀린 옛 쪽지는 스레드 이력에 안 보인다. 실사용 규모에서 왕복이 50건을 밀어내는 경우는 드물고, 밀려도 각 쪽지는 문서로 남아 있다(표시의 문제일 뿐).

## §3 결정 ③ — 화면: 목록은 건별 그대로, 상세에 이력 + [답장]

- **목록(받은/보낸)은 지금처럼 건별 1행.** 스레드 접기(그룹핑 행)는 만들지 않는다 — 읽음 확인이 문서 단위라는 1단계 의미론(수신확인이 데모 핵심)을 흐리지 않는 것이 우선. 답장 항목은 제목이 `RE: 원제목`이라 자연 구분된다.
- **상세 패널**: 본문 위(또는 아래)에 **「주고받은 이력」** — 같은 `threadId`의 내 관련 쪽지들을 시간순 요약 행(보낸이·제목·시각, 클릭 시 그 쪽지 상세로 이동)으로 표시. 현재 보는 쪽지는 강조.
- **[답장] 버튼**: 받은쪽지함 상세에만. 클릭 → 기존 ComposeModal을 열되:
  - 수신자 = 원 발신자 1인 **고정 표시**(칩 삭제·추가 불가 — 서버가 어차피 강제하므로 화면도 정직하게 잠근다). 조직도 단계(§11-2의 ①)는 건너뛰고 바로 작성 단계.
  - 제목 프리필 `RE: 원제목`(수정 가능, `RE:` 중첩 방지 — 이미 `RE:`로 시작하면 그대로).
  - 본문·링크·이미지 첨부는 일반 발송과 동일.
- **모바일(/m)**: 열람 전용 원칙 유지 — 스레드 이력 표시는 하되 [답장] 버튼은 넣지 않는다(1단계 §4-2 "쓰기 버튼 없음"과 동일 결정. 모바일 발신은 별도 단계에서 통째로 판단).
- 문구 규칙: "답장"으로 통일(회신·리플 금지). 개발 용어 금지.

## §4 결정 ④ — 알림·읽음: 전부 기존 경로 재사용, 신규 0

- 답장도 `send`이므로 **웹 푸시(`notifyMemo`)·알림 원장(`emitNotificationsBatch`, type "memo")·읽음(`read` 멱등 기록)·보낸쪽지함 실시간 읽음 표가 코드 추가 없이 그대로 작동**한다.
- 푸시·알림 문구도 기존 형식 그대로(`{이름} 선생님의 쪽지: RE: …`) — 제목의 `RE:`가 답장임을 이미 말해 준다. 별도 유형 신설 안 함.

## §5 결정 ⑤ — 첨부·회수·삭제·보존 승계: 전부 문서 단위 그대로

| 규칙 | 답장에서 | 근거 |
|---|---|---|
| 이미지 첨부 | **그대로 가능** (코드 변경 0) | 답장도 send — attachment spec의 staging 대조·권한 부여가 자동 적용 |
| 회수(§12-2) | **그대로 가능** — 그 답장 문서만 회수됨 | 스레드의 다른 쪽지는 각자 독립. 이력 표시에서 회수된 쪽지가 빠지는 것은 정상(원래 안 읽은 상대에겐 없던 쪽지가 되는 것이 회수의 의미) |
| 삭제(§12-1, 미구현) | 후행 그대로 — 구현되면 `hiddenBy` 필터가 스레드 이력에도 적용 | 선행 아님 |
| 보존·파기 | 각 문서의 `expireAt` 독립 — 스레드 앞부분이 먼저 파기될 수 있음 | 수용. 이력에 갭이 생겨도 각 쪽지의 보존 약속이 우선. 파기 크론이 스레드를 특별 취급할 필요 없음 |

## §6 서버 사양 — `send` 확장 (신규 액션 없음)

입력에 `replyToMemoId?: string` 추가. 있으면:

1. 대상 문서 조회 — 없으면 404 문구("답장할 쪽지를 찾을 수 없습니다").
2. **자격: 본인이 대상 문서의 `recipientEmails`에 포함**되어야 함(발신자 본인의 자기 쪽지 답장 거부 포함) — 아니면 403.
3. 수신자 확정: `recipients` 입력 무시, `[대상.senderEmail]`로 강제. 이후 기존 실존 대조(§2-2)·학생 제외는 그대로 통과시킨다(원 발신자가 퇴직 등으로 디렉터리에서 빠졌으면 "받을 수 있는 수신자가 없습니다" — 정직한 기존 오류 재사용).
4. 스탬프: `threadId = 대상.threadId ?? 대상.id`, `replyTo = 대상.id`.
5. 나머지(검증·저장·푸시·알림·첨부)는 기존 send 흐름 그대로.

- `MemoDoc` 타입에 두 선택 필드 추가. 순수 로직(`logic.ts`)에 `resolveReplyContext(parent, senderEmail)` — 자격·threadId 계산을 분리해 selftest 대상化.
- recall·read·attachment_quota 무변경.

## §7 검증

- `memo_selftest.ts` 확장(순수): 답장 자격(수신자만/발신자 거부/비당사자 거부)·threadId 계승(뿌리/중간)·RE 제목은 서버 무관심(일반 title 검증) 확인.
- 실계정 검증은 기존 실기기 시나리오 확장 1줄: A→B 발송 → B [답장] → **A 휴대전화 푸시 + 알림 원장 + A 받은쪽지함에 RE 도착 + B 보낸쪽지함에서 A의 읽음 실시간 표시** → A가 상세에서 왕복 이력 확인.

## §9 명시적 범위 제외

- 전체 답장 — §1 판정. 실수요가 확인되면 "관리자 지정 상황 한정" 같은 통제된 형태로 별도 판단.
- 목록의 스레드 접기(그룹 행)·대화방형 UI — 쪽지는 채팅이 아니다(구글 챗과 역할 분담).
- 모바일 답장 발신 — 모바일 쓰기 전반과 함께 별도 단계.
- 전달(forward) — 실수요 후. 지금은 새 쪽지 + 첨부 재업로드로 갈음.
