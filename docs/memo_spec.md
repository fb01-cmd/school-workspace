# 쪽지(사내 메신저) 1단계 스펙 — 도달 + 수신확인 MVP

> 2026-08-11 Claude 설계. 로드맵 Phase 8 "단계별 구현 계획"의 1단계.
> 서버부(§1~§3, §5~§7)·보안 규칙 = Claude 구현, 화면(§4) = Antigravity 구현, 표적 리뷰 = Claude.
> 목표 시점: 가을 착수 → 연말 쿨메신저 계약 갱신 창 이전 "시연 가능한 쪽지" (기관 채택 모델 — 데모 완결성이 목적).

## §0 목적·확정 전제·범위

- **목적**: 교직원 간 쪽지 발송·도달·**수신확인**. 쿨메신저 대비 데모 포인트 = "누가 언제 읽었는지가 발신자 화면에 실시간으로 보인다".
- **확정 전제 (2026-08-09 재검토 최종 결론, 재론 금지)**:
  - **순수 플랫폼 네이티브** — Firestore 원본 + 웹 푸시 + 읽음 확인. 메일 사본 층은 전면 철회됨(기관 채택 모델). DWD 추가 스코프 0.
  - **교직원 전용** — 학생은 발신·수신 모두 제외.
  - 상태 단일 원본 = 플랫폼. 인간 생성 데이터라 용량 판정 '하' 유지.
- **1단계 범위**: 발송(조직도·그룹·개인 다중 선택 → 제목·내용·링크) / 받은쪽지함 / 보낸쪽지함(수신자별 읽음) / 웹 푸시 / 보안 규칙 / 보존 정책(정책 확정만, 파기 크론 구현은 후행) / 개인정보 인벤토리 등재.
- **범위 밖 (단계 지도 — 로드맵 확정 분할)**:
  - 2단계: 첨부 파일 실체(사본 수수 의미론, Vercel 4.5MB 우회 결정), 답장·스레드, 대시보드 "안 읽은 쪽지 N건" 카드·메뉴 뱃지, 발송 회수(취소).
  - 3단계: 업무 타입(기한·수락·완료 상태 머신, 제출함). 4단계: 캘린더 출력.
  - 미열람 N시간 후 지연 메일 알림: 필요성 입증 시에만(잔존 후보로만 기록).

## §1 데이터 모델 — `memos/{domain}/items/{memoId}`

| 필드 | 타입 | 설명 |
|---|---|---|
| senderEmail | string | 소문자. 발신자 |
| senderName | string | 표시 이름 — teacher_profiles 이름 → GWS 프로필 이름 → 이메일 로컬부 순 폴백 |
| title | string | ≤200자, 트림 후 빈 값 금지 |
| body | string | ≤10,000자, 일반 텍스트(줄바꿈만, 서식 없음) |
| links | {url, label?}[] | ≤5개, `https://` 시작·2048자 이하만. 1단계 첨부는 링크뿐(파일 실체는 2단계) |
| recipientEmails | string[] | **서버가 확장·검증한 최종 개인 이메일 목록**(§2), 소문자·중복 제거, 1~300명 |
| recipientCount | number | recipientEmails.length (표시용 캐시) |
| recipientSummary | string | 목록 표시용 요약 (예: "2학년부 외 3명") — 클라이언트가 만든 문자열을 서버가 길이(≤100자)만 검증해 저장 |
| reads | map<email, number> | 수신자 이메일 → 최초 열람 시각(ms). **키에 점(.)이 포함되므로 갱신은 반드시 `FieldPath('reads', email)` 사용** — 문자열 dot-notation 금지 |
| createdAt | number | ms |
| expireAt | number | createdAt + 보존기간(§6). 파기 크론의 기준 필드(크론 구현은 후행) |

- **수용 트레이드오프(명기)**: 수신자는 문서를 직독하므로 수신자 목록과 서로의 읽음 상태를 볼 수 있다. 내부 업무 도구에서 통상 노출 범위이며, 읽음 상태를 발신자에게만 숨기려면 수신자별 문서 fan-out이 필요해 모델·읽기 비용이 커진다 — 1단계는 단순 모델 채택.
- 재열람은 reads를 갱신하지 않는다(최초 열람 시각 보존).

## §2 API — `POST /api/memo` (action 기반, 기존 관례)

전 액션 `verifyAuthAccess` + **users 문서 `role ∈ {teacher, super_admin}` && `teacher_profiles/{email}` 문서 존재**(= 교직원 조직도 등록). 학생·조직도 미등록 403. domain = 이메일 도메인.

> **[2026-08-13 정정 — 원래 `isApproved === true`였다]** 그 필드는 로그인할 때마다 `sync-user`가 `isApproved: isWorkspaceAdmin`으로 **덮어쓴다.** 실측 결과 일반 교사 16명 전원 `false`, `true`인 교사는 0명이었고 앞으로도 될 수 없다 — 쪽지가 **수퍼어드민 4명 전용**이 돼 있었다. §10-2에서 사용자가 확정한 "승인된 전 교직원"의 의도와 정반대다. 자격 기준을 **교직원 조직도에 소속이 등록된 계정**(`teacher_profiles/{email}.departments`가 비어 있지 않음)으로 바꾼다(2026-08-13 사용자 확정 — "무조건 조직이 있어야 통과"): 학교 구성원 판정의 실제 단일 원본이고, 인프라·미등록 계정(`fb01@` 등)은 자연히 빠진다. **교훈: 게이트에 쓸 필드는 이름만 보고 고르지 말고 실제 값 분포를 재고 고를 것.**

### `send`

입력: `{ title, body, links?, recipientSummary?, recipients: { users: string[], groups: string[] } }`

서버 처리 순서 (UI를 신뢰하지 않는다 — 이중 방어 규칙):

1. **그룹 확장은 서버가 직접** — `listGroupMembers`(workspace.ts 기구현)로 확장. member `type === "GROUP"`이면 재귀 확장(방문 집합으로 순환 방지, 깊이 ≤3 초과분은 경고 로그+제외). 클라이언트가 펼쳐 보낸 목록을 그대로 믿지 않는다.
2. **개별 수신자 실존 대조** — 이메일 형식 정규식(400) 후, GWS `users.list` 전수 1회(기존 사용자 목록 헬퍼)로 대조. 호출 수가 수신자 수와 무관하게 고정된다(getUser N회 금지).
3. **학생 제외** — 대조 결과의 `orgUnitPath`가 `/학생` 하위인 계정은 제외(학번 휴리스틱이 아니라 실데이터 기준 — 그룹에 학생이 섞여 있어도 안전). 도메인 외 이메일 제외.
4. 소문자 정규화·중복 제거 → 최종 1~300명 범위 밖이면 400. 발신자 본인 포함은 허용(자기에게 보내기).
5. 문서 생성(§1 필드) — `reads: {}`.
6. **웹 푸시**: 응답 후 `after()`로 발송 — `listSubsByEmails(recipientEmails)` → `sendPushToSubs`. 페이로드:
   - `{ title: "새 쪽지", body: "{senderName} 선생님: {title}", url: "/", tag: "memo:" + memoId }`
   - **본문 내용은 싣지 않는다** — 잠금화면 노출 텍스트이므로 발신자·제목까지만(웹 푸시 스펙 §7 원칙과 동일).
   - tag를 쪽지별로 다르게 해 여러 쪽지 알림이 서로 덮어쓰지 않게 한다(시간표의 단일 tag 집계와 반대 — 쪽지는 건별 확인이 목적).
   - url은 `/` — 로그인 리다이렉트가 뷰포트 분기(모바일 `/m`, 데스크톱 `/admin`)를 자연 통과(mobile_m_spec §2). 딥링크 플럼빙은 1단계에 넣지 않는다.

### `read`

입력: `{ memoId }`. 문서의 recipientEmails에 **본인이 포함된 경우만**, `reads`에 본인 키가 없으면 `FieldPath('reads', email) = Date.now()` 기록. 이미 있으면 no-op(멱등). 비수신자는 403.

## §3 읽기 경로 — 클라이언트 직독 + 보안 규칙 (쓰기는 API 전용)

읽기는 Firestore 직독(onSnapshot 실시간 — 보낸쪽지함 읽음 반영이 데모 핵심), 쓰기는 전면 API 경유.

- **받은쪽지함**: `where("recipientEmails", "array-contains", myEmail)` + `orderBy("createdAt", "desc")` + `limit(50)` — **복합 색인 1건 필요**.
- **보낸쪽지함**: `where("senderEmail", "==", myEmail)` + `orderBy("createdAt", "desc")` + `limit(50)` — **복합 색인 1건 필요**.
- **[2026-08-12 실측 정정] 복합 색인은 필요하지 않았다.** 두 쿼리 모두 색인을 따로 만들지 않은 상태에서 정상 실행됨을 admin SDK 실행과 실기기 화면(보낸쪽지함 목록 표시)으로 확인했다. 위 "복합 색인 1건 필요" 표기는 착수 전 추정이었고, 운영 액션에서 삭제한다. 남은 규칙은 §8 참조.

**firestore.rules 추가** (deny-by-default 예외 개방, 재검토 ①의 수신자·발신자 검사 요구 충족):

> **[2026-08-13 정정] 아래 블록은 실배포 규칙과 동일하게 갱신했다.** 초안은 `isApproved == true`를 썼으나 §2의 정정과 같은 이유로 폐기됐고(그 필드는 "워크스페이스 관리자인가"였다), 자격 검사는 `teacher_profiles/{email}.departments.size() > 0`으로 바뀌어 2026-08-13 게시됐다(ruleset `871128f7…`). 이 문서를 복사해 규칙을 만들지 말 것 — 규칙의 단일 원본은 저장소 `firestore.rules`다.

```
// ── memos/{domain}/items — 쪽지 (1단계) ─────────────────────
// 읽기: 교직원 조직도에 소속이 등록된 교직원 중 발신자·수신자 본인만. 쓰기: 서버 API 전용.
match /memos/{domain}/items/{memoId} {
  allow read: if isSchool()
    && myUserDoc().role in ['teacher', 'super_admin']
    && exists(/databases/$(database)/documents/teacher_profiles/$(request.auth.token.email))
    && get(/databases/$(database)/documents/teacher_profiles/$(request.auth.token.email)).data.departments.size() > 0
    && (request.auth.token.email == resource.data.senderEmail
        || request.auth.token.email in resource.data.recipientEmails);
  allow write: if false;
}
```

- 학생·조직도 미등록 계정·비수신 교직원의 직독 불가. 목록 쿼리는 위 두 쿼리 형태만 규칙을 통과한다(array-contains 본인 / senderEmail 본인).

## §4 화면 (Antigravity 인계 스펙 — IA 명시, 임의 배치 금지)

### §4-1 데스크톱 — 관리자 포털

- `src/app/admin/page.tsx` `MenuType`에 `"memo"` 추가. **사이드바 최상위 메뉴 "쪽지", 위치는 "홈" 바로 아래.** 전 교직원 노출(super_admin 전용 아님).
- 화면 구성: 상단 [받은쪽지함 | 보낸쪽지함] 탭 + "쪽지 쓰기" 버튼.
- **받은쪽지함**: 발신자 이름·제목·보낸 시각 목록, 내 이메일이 reads에 없으면 **안 읽음 강조**(굵게 등). 항목 클릭 → 상세(본문·링크) 열림과 동시에 `POST /api/memo {action:"read"}` 호출.
- **보낸쪽지함**: 제목·보낸 시각·**읽음 N/M** 목록. 상세에서 수신자별 읽음 여부·최초 열람 시각 표(onSnapshot이므로 열람 즉시 갱신 — 데모 핵심 화면).
- **쪽지 쓰기** — 수신자 선택 3경로, 선택 결과는 칩 목록으로 표시·개별 제거 가능:
  1. **조직도에서 선택**: 부서 체크 = 소속 전원(기존 조직도 트리 컴포넌트 계열 재사용). 선택 결과는 `recipients.users`(개인 이메일 배열)로 전송.
  2. **그룹 선택**: `groups:all` 프리페치 캐시에서 로컬 필터링(프리페치 우선 규칙). 그룹 이메일은 `recipients.groups`로 전송 — **확장은 서버가 한다**, 클라이언트가 멤버를 펼치지 않는다.
  3. **개인 검색**: `AutocompleteInput` 재사용 — **`onSelect`로만 추가**, 원시 검색 문자열을 제출값으로 쓰지 않는다(자동완성 규칙 4 준수).
  - `recipientSummary`는 클라이언트가 생성해 전송(예: "2학년부 외 3명").
- 발송 전 확인 1회: "N명에게 쪽지를 보냅니다." (서버 응답의 최종 인원과 다를 수 있음 — 학생·중복 제외는 서버 몫이므로 발송 후 보낸쪽지함 기준이 확정치).
- 문구 규칙: 개발 용어·메타문구 금지. 명칭은 화면 전체에서 **"쪽지"**로 통일(메신저·DM·푸시 등 금지).
- 대시보드 카드·사이드바 안읽음 뱃지는 만들지 않는다(2단계 확정 범위).

### §4-2 모바일 — `/m`

- `/m` 홈에 **"쪽지" 섹션(받은쪽지함 열람 전용)** 추가: 안 읽은 쪽지 우선 정렬 목록 → 탭하면 상세 + read 호출. **쓰기 버튼 없음** — 발송은 PC(관리자 포털)에서. (푸시 탭 → `/` → 모바일 분기 → `/m` 도착 즉시 새 쪽지가 보이는 흐름이 성립하는 지점.)
- 기존 mobile_m_spec의 수정 금지 목록(sw.js·push 발송부·RouteGuard)은 그대로 유효.

## §5 웹 푸시 재사용

- `src/lib/push/webpush.ts`에 `notifyMemo(domain, memo)` 헬퍼 추가 — 기존 `listSubsByEmails`·`sendPushToSubs` 재사용, 신규 인프라 0. 실패는 절대 throw하지 않는다(발송 실패가 쪽지 저장을 깨면 안 됨).
- iOS 제약·설치 안내는 웹 푸시 스펙 §11 그대로(신규 사항 없음). 구독이 없는 수신자는 푸시만 못 받을 뿐 쪽지함에는 정상 도달 — 로그인 인구 확대와 함께 자연 개선.

## §6 보존 정책·개인정보 (1단계는 정책 확정까지, 크론 구현은 후행)

- **보존 기간: 기본 365일** — `settings/{domain}.memoRetentionDays`로 오버라이드 가능(환경설정 UI 노출은 하지 않음, 필요 시 콘솔). 근거: 쪽지는 일상 업무 연락이라 증빙성 기록(서명 3년·감사 5년)보다 짧게, 학사연도 1주기는 보장.
- `expireAt`은 발송 시 즉시 스탬프 — 크론이 나중에 생겨도 과거분 소급 계산 불요.
- **파기 크론 구현은 후행**. 단 Vercel Hobby 크론 2개 한도가 이미 소진 상태(기존 1 + 생활지도 브리지 1)이므로, 구현 시점에 **기존 크론 엔드포인트 통합 또는 GitHub Actions 스케줄** 중 택일(신규 Vercel 크론 불가).
- **`personal_data_inventory.md` 등재(1단계 산출물)**: 항목 = 쪽지 제목·본문·링크·발신/수신자·열람 시각 / 보존 365일 / 파기 = 크론(구현 전까지 수동 정리 가능성 명기).
- 푸시 페이로드는 발신자 이름·제목까지만(§2) — 본문·수신자 목록 금지.

## §11 쪽지 쓰기 개편 v1.1 (2026-08-13 사용자 실사용 피드백 — 확정)

> 시연 통과 직후 사용자가 실제로 써 보고 지적한 2건. **현재 화면이 "교내 실무 동선"이 아니라 범용 메신저 동선을 따르고 있다는 지적**이며, 둘 다 스펙 §4-1을 개정한다.

### §11-1 발송 확인창 제거 — 보내기 = 즉시 발송

- **현행 폐기**: §4-1의 "발송 전 확인 1회"(`"N명에게 쪽지를 보냅니다."`)를 **없앤다.** 사용자 표현 그대로 "의미 없는 경고가 떠서 한 번 더 뭘 누르게" 만든다. 교내 쪽지는 하루에도 여러 건 오가는 일상 연락이라 매번 2클릭은 마찰이다.
- **대신 정보는 버튼에 싣는다**: 버튼 라벨을 `보내기` → **`N명에게 보내기`**. 클릭 수를 늘리지 않고 인원을 알린다. 수신자 0명이면 비활성.
- **오발송 안전망은 회수로 옮긴다**: 확인창이 사라지면 되돌릴 수단이 없다(1단계에는 회수가 없다). **§0 2단계 목록의 "발송 회수(취소)" 우선순위를 올린다** — v1.1과 함께 갈지는 별건 판단이나, 확인창 제거의 대가로 반드시 큐에 남긴다.
- 곁가지: 현재 확인 오버레이는 `relative` 조상이 없어 **화면 전체를 덮는다**(표적 리뷰 지적). 제거하면 이 결함도 함께 사라진다.

### §11-2 수신자 선택 = 조직도 우선 (기본 동선 교체)

**사용자 판단**: "교내에서 처음 쪽지를 보낼 때 사람을 검색해서 보내는 일은 없다. 그건 경기도교육청 메신저에서나 하는 일이고, 대부분은 조직도에서 바로 클릭한다."

- **[쪽지 쓰기] → 조직도가 먼저 뜬다.** 2단계 흐름으로 바꾼다.
  - **① 받는 사람 고르기** — 조직도 트리 + 상단 이름 검색
  - **② 작성** — 제목·내용·링크. 이 단계에서도 **수신자를 더하거나 뺄 수 있다**(칩 목록 + 같은 이름 검색). ①로 돌아가는 것도 가능.
- **⚠️ 트리의 출처를 바꾼다 — 지금 것은 개념이 다르다.** 현행 "부서별 선택" 탭은 `OUCheckboxTree`(구글 **OU** 트리) + `users:all`을 쓴다. OU는 계정 관리 단위이지 학교 부서가 아니다. **교직원 조직도(`teacher_profiles.departments`)**로 교체한다. 부서 순서는 `settings/{domain}.departments`(27개, 없으면 [`src/lib/org/departments.ts`](../src/lib/org/departments.ts) 폴백).
- **초기 펼침 = 내 소속 부서만.** 로그인한 사람의 `teacher_profiles.departments`에 해당하는 부서만 펼치고 나머지는 접는다(사람은 여러 부서 소속이 가능하므로 전부 펼침).
- **선택 단위 2가지**: 개인 체크 / **부서 헤더 체크 = 그 부서 전원**. 한 사람이 여러 부서에 속하므로 이메일 기준 중복 제거(서버도 §2-4에서 재차 제거).
- **명단에 올릴 대상 = 소속이 있는 사람만.** 소속이 빈 계정은 §2 자격 조건상 **받아도 열지 못하므로** 애초에 고를 수 없어야 한다(현재 조직도 89명 중 81명). 보낼 수 있는 사람과 목록이 어긋나지 않는 것이 이 규칙의 목적이다.

**규칙 1 — 조건부 부제.** 전체 명단에 **같은 이름이 2명 이상일 때만** 그 이름들에 부제를 붙인다. 유일한 이름에는 아무것도 붙이지 않아 목록이 깔끔하게 유지된다.

**규칙 2 — 부제 우선순위** (학교에서 사람을 실제로 지칭하는 순서. 실측: 담임 30명 / 소속 81명 / 직책 78명):

| 순위 | 부제 | 예 |
|---|---|---|
| 1 | **담임 학반** | `김한별 · 2학년 3반 담임` |
| 2 | 소속 부서·교과 첫 번째 | `김한별 · 수학` |
| 3 | 직책 | `김한별 · 부장` |
| 4 | **사람이 지정한 구분 표기**(규칙 4) | `김한별 · 큰 김선생` |

담임을 1순위로 두는 이유: 교직원 사이에서 사람을 특정하는 가장 자연스러운 단위다. **둘 다 담임인 경우는 오히려 안전하다** — 같은 반 담임은 존재할 수 없으므로 학반으로 갈린다.

**규칙 2-1 — "존재하는" 첫 항목이 아니라 "서로 다른" 첫 항목을 쓴다.** 부제는 두 사람의 값이 **실제로 갈릴 때만** 구분에 성공한다. 소속이 둘 다 `수학`이면 소속은 건너뛰고 다음 순위로 내려간다. 값이 있는지가 아니라 값이 다른지를 본다.

**규칙 3 — 어디서든 같은 표기.** 부제를 붙이기로 한 사람은 조직도 트리·검색 결과·수신자 칩·보낸쪽지함 수신자 목록에서 **전부 같은 형태**로 보인다. 한 화면에서만 구분되면 다른 화면에서 오인이 난다.

**규칙 4 — 자동 구분이 불가능한 경우: 사람이 이름을 붙인다.**

진짜 막히는 조합은 **둘 다 담임이 아니고 소속·직책까지 같을 때**다(예: 수학 교사 김한별 2명, 둘 다 비담임·직책 "교사"). 이때 조직도에는 구분할 재료가 **실제로 없다** — "관리자가 조직도를 정리하라"는 지시는 고칠 대상이 없으므로 성립하지 않는다.

→ `teacher_profiles`에 **선택 필드 `displaySuffix`(구분 표기)**를 둔다. 조직도 편집 화면(관리자)과 「정보 수정 신청」(본인)에서 채울 수 있는 짧은 문자열이며, **교직원들이 실제로 그 사람을 부르는 방식을 그대로 적는다**(`큰 김선생`, `2반 옆자리`, `작년 3학년` 등 무엇이든). 시스템이 규칙을 만들어 비트는 것보다, 이미 존재하는 호칭을 받아 적는 편이 정확하다.

**규칙 5 — 채워지기 전까지는 아이디 로컬부를 임시로 쓰고, 그 상태를 경고로 드러낸다.**

`displaySuffix`가 비어 있고 1~3순위도 전부 같으면, 목록에 **똑같은 이름 두 개**가 나란히 뜬다 — 오발송이 확실히 나는 상태다. 이때만 예외적으로 아이디 로컬부를 부제로 쓴다(`김한별 · kim1234`).

**이것은 정상 표기가 아니라 "데이터가 덜 채워졌다"는 신호로 취급한다** — 화면에 아이디가 보이는 순간이 곧 구분 표기를 등록하라는 알림이다(§11-2의 "이메일을 화면에서 지운다" 원칙의 유일한 예외이며, 조건은 *자동 구분 완전 실패*뿐이다). 조직도 편집 화면에는 해당 인원과 함께 구분 표기 입력을 요구하는 경고를 띄운다.

**규칙 6 — 발생 시점을 알린다.** 조직도 편집 화면에서 동명이인이 새로 생기면 그 자리에서 표시한다. 사후에 발견하지 않고 등록 시점에 알게 하는 것이 이 항목의 핵심이다.

#### 2계층 저장 — 승인 필요 vs 즉시 저장 (2026-08-13 사용자 확정)

「내 정보 관리」를 두 구획으로 나눈다. **구분 기준은 "이 값이 권한이나 조직 구조에 닿는가"**다.

| 구획 | 필드 | 경로 |
|---|---|---|
| **조직 정보 (승인 필요)** | 소속 부서 · 직책 · 부서장 · 담임 학반 | 기존 그대로: `teacher_profiles_pending` 제출 → 수퍼어드민 승인. 담임 판정이 생활지도 열람 권한의 근거라 2026-07-25 잠금 유지 |
| **연락처 정보 (즉시 저장)** | 내선번호 (D 갈래에서 별칭 합류) | 본인이 저장 즉시 반영. 어드민이 내선번호를 일일이 검사할 일이 아니다 |

**즉시 저장의 구현 = `firestore.rules`의 필드 한정 자기 업데이트.** 서버 라우트를 새로 만들지 않는다(이 컬렉션의 기존 쓰기 패턴이 클라이언트 직접 쓰기이고, 규칙의 `diff().affectedKeys()`가 정확히 이 용도다):

```
match /teacher_profiles/{email} {
  allow read: if isTeacher();
  allow write: if isSuperAdmin();
  // 2026-08-13: 비권한 필드(내선번호)만 본인 즉시 수정 허용.
  // affectedKeys().hasOnly()가 소속·직책·담임·부서장을 구조적으로 봉쇄하므로
  // 2026-07-25 잠금(권한 근거 필드는 승인 경로만)은 그대로다.
  allow update: if isSelf(email)
    && request.resource.data.diff(resource.data).affectedKeys()
        .hasOnly(['extension', 'updatedAt', 'updatedBy'])
    && request.resource.data.extension is string
    && request.resource.data.extension.size() <= 20
    && request.resource.data.updatedBy == request.auth.token.email;
}
```

- `update`만 허용(create 불가) — **조직도에 등록된 사람만** 내선을 넣을 수 있다. 미등록자에겐 "조직 정보 승인 후 입력할 수 있습니다" 안내.
- D 갈래에서 별칭이 오면 `hasOnly` 목록에 `displaySuffix` 한 단어 추가로 끝난다.
- **운영 액션**: 규칙 게시 필요(수동 게시 구조). 8/12 확립한 Rules API 게시 절차 재사용 — 게시 전 실배포 대조, 게시 후 재조회 검증, 롤백 ruleset 기록.

## §12 삭제·회수 (2026-08-13 사용자 제기 — 수신확인과의 충돌 검토·해소)

> 사용자 제기: "쪽지 삭제(내 쪽에서만 안 보이는 것)와 회수. 회수는 **이미 읽은 사람 것은 놔두고 안 읽은 사람 것만** 회수했다. 이 둘은 발신자가 수신 여부를 확인하는 지금 기능과 충돌할 수 있으니 절충하거나 버려야 할 것 같다."
>
> **판단: 둘 다 살린다.** 충돌 지점은 각각 하나뿐이고, 규칙 한 줄로 해소된다. 오히려 회수는 §11-1(확인창 제거)의 안전망이라 **없으면 안 되는 쪽**이 됐다.

### §12-1 삭제 — "내 화면에서만 감추기"  *(서버부·UI ✅ 2026-08-18 완결 — action "hide"·클라이언트 필터·확인 1회·안읽음 삭제 방어)*

- 받은쪽지함·보낸쪽지함 각각에서 **본인 화면에서만** 감춘다. 상대 쪽은 그대로다. 문서는 지우지 않는다(§6 보존 365일).
- **충돌은 딱 하나 — 안 읽고 삭제하는 경우.** 수신자가 열지 않고 지우면 발신자 화면에는 영원히 "안 읽음"으로 남는다. 발신자는 아직 못 본 줄 알고 기다리거나 재촉하는데 실제로는 이미 버려진 것이다. 수신확인이라는 이 기능의 존재 이유가 거짓 정보를 주게 된다.
- **해소: 안 읽은 쪽지는 삭제할 수 없다.** 열어서 읽은 뒤에 정리할 수 있게 한다("읽은 뒤에 정리할 수 있습니다").
  - 대안으로 검토했다가 버린 것: ⓐ 삭제 시 읽음으로 간주 → **발신자에게 거짓말**을 한다. ⓑ "확인하지 않고 정리함" 상태 신설 → 정직하지만 상태가 늘고, *내가 안 읽고 버렸다*는 사실이 발신자에게 노출돼 수신자 쪽 프라이버시를 침해한다.
  - 실무 부담은 없다. 어차피 지우려면 무슨 쪽지인지는 봐야 한다.
- 발신자 삭제는 제약 없음(보낸쪽지함에서 감춤 + 읽음 현황도 함께 감춰짐). 수신자 쪽은 영향 없다.
- **구현**: 문서에 `hiddenBy: { [email]: ms }`. 쓰기는 API 경유(§3 규약). Firestore에 array-not-contains가 없으므로 **목록 필터는 클라이언트**에서 한다 — `limit(50)` 안에서 감춘 건이 많으면 표시 건수가 줄어드는 점을 감안(실사용 규모에서 문제되지 않음).
- **개인정보 고지 정합**: "삭제"라고 쓰지만 실제로는 본인 화면에서 감추는 것이고 원본은 보존 기간까지 남는다. **`personal_data_inventory.md`와 /privacy 문안에 이 사실을 명시**해야 한다("받는 분이 삭제해도 보존 기간 동안 원본은 남습니다"). 이용자가 "지웠으니 없어졌다"고 오해하게 두면 안 된다.

### §12-2 회수 — "안 읽은 사람 것만"  *(서버부 ✅ 2026-08-13 구현 · UI ✅ 구현 완료 — af5da4a에서 개정 2건까지 반영, 실기기 동작 2026-08-18 사용자 확인)*

- 쿨메신저 동작 그대로: 회수하면 **이미 읽은 사람 것은 그대로 두고 아직 안 읽은 사람 것만** 사라진다.
- **이 모델과 잘 맞는다.** `recipientEmails`에서 미열람자만 빼면 그들은 §3 규칙상 그 문서를 읽을 수 없게 되어 목록에서 사라지고, 열람자는 그대로 남는다. `reads` 기록은 손대지 않으므로 **수신확인 이력이 보존된다** — 충돌이 없다.
- **충돌처럼 보이지만 아닌 것**: "회수하면 누가 안 읽었는지 발신자가 알게 된다" → 발신자는 이미 읽음 현황을 보고 있다. 새로 노출되는 정보가 없다.
- **진짜 주의점 — 회수는 완전한 취소가 아니다.**
  - 푸시는 이미 발송됐다. 잠금화면 알림에 **발신자와 제목이 남아 있고** 그건 되돌릴 수 없다(§2-6 페이로드).
  - 따라서 화면에 반드시 알린다: **"이미 읽은 분의 쪽지는 회수되지 않습니다. 휴대전화 알림은 취소할 수 없습니다."**
- **이력을 남긴다**: 회수하면 `recipientCount`가 줄어 "5명 중 2명 읽음"이 "2명 중 2명 읽음"으로 바뀐다. 그대로 두면 보낸 이력이 왜곡되므로 `recalledAt`·`recalledCount`를 남기고 보낸쪽지함에 **"3명에게서 회수함"**을 표시한다.
- **우선순위 상향 근거**: §11-1에서 발송 확인창을 없앴다. 되돌릴 수단이 회수뿐이므로, 회수는 이제 "있으면 좋은 것"이 아니라 **확인창 제거의 짝**이다. §0의 2단계 목록에서 끌어올린다.

**서버부 구현 메모 (2026-08-13)**

- `POST /api/memo {action:"recall", memoId}` — **보낸 사람만** 가능(403). 순수 로직은 `computeRecall`(logic.ts)로 분리해 자가 테스트 8항목 통과.
- **트랜잭션으로 처리한다.** 대상 계산과 쓰기 사이에 누군가 열면 "읽었는데 목록에서 사라진 사람"이 생겨 수신확인 이력이 왜곡된다 — 트랜잭션이면 그 경합에서 재시도되어 항상 최신 `reads` 기준으로 자른다.
- **전원이 이미 읽었으면 아무것도 쓰지 않고 `recalledCount: 0`으로 성공 응답한다.** 여기서 `recalledAt`을 찍으면 회수한 적 없는 쪽지에 회수 이력이 생겨 거짓이 된다. 화면은 이 값으로 "이미 모두 읽어 회수할 쪽지가 없습니다"를 안내하면 된다.
- `recalledCount`는 **누계**로 쌓는다(덮어쓰면 앞선 회수 이력이 사라진다). 재회수는 자연히 0건이 되어 멱등이다.
- `reads`는 건드리지 않는다 → 남는 수신자와 읽음 기록이 저절로 정합된다.
- 규칙 변경 없음 — 쓰기는 이미 서버 전용이고, `recipientEmails`에서 빠진 사람은 §3 읽기 조건에서 자동으로 탈락한다.

- 사용자 확정: 회수 버튼을 누르면 **"안 읽은 N명에게서 회수합니다. 이미 읽은 분 것은 회수되지 않고, 휴대전화 알림도 취소되지 않습니다."** → [회수] / [취소].
- **§11-1이 발송 확인창을 없앤 논거는 회수에 적용되지 않는다.** 두 동작은 성질이 반대다: 발송은 하루에도 여러 번 하고 **회수로 되돌릴 수 있는** 반면, 회수는 드물게 하고 **되돌릴 수 없다**(수신자 목록에서 빠지면 복구 수단이 없다). 확인창의 마찰 비용은 빈도에 비례하고 편익은 비가역성에 비례하므로, 같은 규칙을 두 곳에 똑같이 적용하면 안 된다.
- 부수 근거: 첫 구현에서 회수 버튼이 **닫기(×) 바로 옆**에 놓여 오조작 거리가 0에 가까웠다.

**[2026-08-13 개정] 주의 안내는 회수 *후*에도 남긴다.** 첫 구현은 안내를 `!recallResult` 조건으로 걸어, **회수 직후 결과 카드가 뜨면 그 문구가 사라졌다.** "그럼 알림은 어떻게 되나"라는 물음은 회수를 누른 **다음에** 생기므로, 정작 필요한 순간에 화면에서 없어지는 셈이다. 결과 카드 본문에 "휴대전화 알림은 취소할 수 없습니다"를 포함한다.

### §12-3 착수 순서 제안

1. **회수** — §11-1과 짝이므로 쪽지 쓰기 개편과 가까운 시점에.
2. **삭제** — 급하지 않다(사용자 표현: "잘 안 쓰긴 하지만"). 고지 문안 갱신이 딸려 오므로 개인정보 관련 작업과 묶는 편이 낫다.
