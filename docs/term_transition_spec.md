# 학기 전환 스펙 — 신학기 준비를 운영과 분리한다 (2026-08-14, Claude Fable 5)

> 발단: 사용자 질문 *"이동수업·특별실 등록부는 현재 운영 시간표용인데, 새 시간표 짤 때는 어디서 정하나? 지금 화면에서 고치면 현재 것이 망가질 텐데?"* — **정확한 지적이고, 실제 구멍이다.**
>
> 모델 판단: **나이스형** — 학기 단위 데이터 분리 + 미리 작성·검증 + 전환(포인터 교체). 컴시간(파일 통째 사본)도 같은 결론의 다른 구현이다. 레퍼런스 실측: 컴시간 매뉴얼 §3·§4(현재시간표로 새 시간표 만들기·전량 불러오기 시 전체 초기화), 나이스 실무(사용자 증언: 연말 사전 작성 → 학기전환 메뉴 → 필요시 공지 후 임시 회귀).
>
> **우리 뼈대는 이미 나이스형이다.** 학기(`TimetableTerm`)에 draft/active/archived 상태가 있고, 활성화(=학기전환)가 있고, 등록부 6종은 전부 `termId`를 갖고 있으며, 등록부 API도 `body.termId || activeTermId`로 명시 학기를 이미 받는다(`manage/route.ts` simul_list 등). **빠진 것은 화면의 학기 선택과, 학기 생애주기 액션 3개뿐이다.**

## 0. 원칙

1. **초안 학기 편집은 운영에 절대 영향 없다.** 활성 학기 데이터는 초안 작업 중 한 글자도 바뀌지 않는다.
2. **활성 학기 등록부 편집은 현행 그대로 둔다** (운영 중 조정은 지금도 정당한 작업이다 — 잠그지 않는다).
3. **임시 회귀는 만들지 않는다.** 나이스의 회귀는 생활기록부류 법정 기록 정정 때문에 존재한다(사용자 확정 2026-08-14: *"우리 플랫폼에서 임시 회귀가 과연 필요할 일이 있을까 싶어"*). 우리에겐 그 무게의 기록이 없고, 전환 실수는 보관 학기를 다시 활성화하면 복구된다(전환 자체가 상호 역연산). 별도 기능 없음으로 종결.

## 1. 신학기 초안 학기 생성 — action `term_create_draft`

- 본문: `{ newTermId: "2027-1", newTermName: "2027학년도 1학기" }`
- 서버: `TimetableTerm` 생성 — `status: "draft"`, `subjects: []`, 그리드 없음. `importedBy`/`importedAt`은 생성자·생성 시각으로.
- 검증: termId 형식 `^\d{4}-[12]$` · 기존 학기와 중복 금지 · super_admin 또는 일과계 관리자.
- UI: 「학기 & 권한 관리」(TimetableImportTab 4단계)에 "신학기 초안 만들기" 폼. 기존 학기 목록 표에 초안이 함께 보인다(이미 보임).
- 감사 로그 등재.

## 2. 편집 대상 학기 선택 — 시간표 작성 전체에 학기 축 노출

- `TimetableCreationSection`에 `workingTermId` 상태 신설. 선택지 = 활성 학기 + draft 학기들(archived 제외). 기본값 = 활성 학기.
- 등록부 탭 6종(이동수업·특별실·특별교사 금지·연속수업·복수교사·(일괄 배정이 화면화되면 그것도))과 시수 계획·교육과정 탭·자동 작성 탭에 `activeTermId` 대신 `workingTermId`를 내려보낸다. **서버 API는 이미 termId를 받으므로 각 탭의 요청 본문에 termId를 명시하는 것이 구현의 전부다** — 단, 탭별로 termId를 안 보내고 서버 기본값(activeTermId)에 기대는 호출이 있는지 전수 확인할 것.
- **비활성 학기 편집 중임을 항상 보이게**: 선택이 활성 학기가 아니면 상단에 고정 배너 — *"2027-1 초안을 편집하고 있습니다. 운영 중인 시간표에는 영향이 없습니다."* 문구에 "termId"·"draft" 같은 용어 금지.
- 교육과정 고정 시간(코호트) 탭은 **학기 축이 없다**(입학년도 축, 9c-H §2) — 선택과 무관하게 동작. 배너 대상에서 제외.

## 3. 승계 복사 — action `registry_inherit`

- 본문: `{ fromTermId, toTermId }`
- 대상 6종: `simulGroups` · `venueGroups` · `teacherSlotBans` · `consecutiveRules` · `coTeaching` · `fixedBlocks`.
- 서버 규칙:
  1. `toTermId`는 **draft 학기만** 허용 (활성·보관 학기로 복사 금지).
  2. **대상 학기에 등록부가 1건이라도 있으면 거부** — 병합·중복 방지. 다시 하려면 대상 학기 등록부를 비우고 재실행(전량 복사만 지원, 부분 병합은 만들지 않는다).
  3. 문서 ID는 전부 새로 발급, `termId` 교체, `createdBy`=실행자, 원본 참조(`inheritedFrom: fromTermId`) 스탬프.
  4. 배치 쓰기, 건수 요약 반환(종별 n건), 감사 로그.
- UI: 학기 선택(§2)에서 초안 학기를 고르면, 등록부가 전부 빈 경우 안내 카드 — *"현 학기(2026-2) 등록 내용을 가져와서 시작할 수 있습니다"* + [가져오기] 버튼 1개.
- 참고: 선택과목 개편으로 바뀌는 것은 주로 이동수업 구성이다 — 장래 「이동수업 현황 파일 → 그룹 자동 갱신」([`hours_source_files_analysis_2026-08-14.md`](./hours_source_files_analysis_2026-08-14.md) §6)이 이 사본 위에 얹힌다.

## 4. 시수 계획의 학기 소속 — `HoursPlan.targetTermId`

- `HoursPlan`에 선택 필드 `targetTermId` 추가. 업로드·파생·신규 생성 시 현재 `workingTermId`를 스탬프.
- 시수 계획 탭 목록에 소속 학기 표시. 계획이 많아질 때 학기별 필터.
- 기존 저장 계획(필드 없음)은 "소속 없음"으로 표시만 — 마이그레이션 불요.

## 5. 자동 작성 결과 채택 — action `draft_adopt`

신학기 파이프라인의 마지막 연결. 현재 자동 작성 초안(`timetable_drafts`)은 학기 기초 그리드로 넘어가는 경로가 없다(학기를 만드는 유일한 통로였던 컴시간 가져오기는 2026-08-14 화면에서 숨김).

- 본문: `{ draftId, termId }`
- 서버 규칙:
  1. `termId`는 **draft 학기만** 허용. **활성 학기 채택 금지** — 활성 학기 변경은 기초시간표 개정(`revision_apply`) 경로 유지(이원화를 명시적으로 지킨다).
  2. 초안의 현재 그리드(ops 재생 결과)를 학기의 기초 그리드로 **전량 저장**(기존 그리드 있으면 교체 — draft 학기라 안전).
  3. 채택 전 서버가 검사기를 돌려 **하드 위반 있으면 거부**(요약 반환). 소프트는 경고만.
  4. `term.subjects`를 그리드에서 파생해 채움(과목명·약칭 집계 — import_commit이 하던 역할의 대체).
  5. 감사 로그.
- UI: 자동 작성 탭 결과 화면에 [이 결과를 ○○ 학기 기초시간표로 채택] — workingTermId가 draft일 때만 노출.

## 6. 학기전환 — 기존 활성화 재사용 + 관문만 보강

- 기능은 현행 「학기 활성화」 그대로(활성 → archived 자동).
- 활성화 확인창에 **전환 관문 요약**을 추가: ⓐ 기초 그리드 존재 ⓑ 검사기 하드 0 ⓒ 학년별 학급 구성. 미충족 항목은 경고로 표시하되 super_admin은 강행 가능(관문은 안내지 자물쇠가 아니다 — 개학 전날의 현실 대비).
- 전환·재전환 모두 감사 로그(이미 있음) 확인.

## 7. 하지 않는 것

- **임시 회귀 기능** — §0-3. 필요 시 보관 학기 재활성화로 갈음(그 경로가 이미 회귀다).
- **등록부 부분 병합 승계** — 전량 복사만. 병합 규칙은 실수요가 생기면.
- **활성 학기 등록부 잠금** — 현행 유지.
- **archived 학기 편집** — 선택지에서 제외.

## 7-1. 학사일정은 학기 밖으로 — 날짜 축 고정 원장 (2026-08-14 사용자 발제)

> 사용자: *"학사일정은 캘린더로도 연동되는 특성도 있고 해서 테이블과는 별도로 그냥 고정되어 있어야 하는 거 아닌가? 연도별 학사일정끼리 겹치는 부분이 있진 않아."* — **맞다.**

**현행 실측**: 학사일정 문서에 `termId`가 붙어 있고 조회도 학기 축이다(`loadCalendarEvents` = `where termId ==`). 그런데 이 결합이 **이미 세 군데서 어긋나 있다**:

1. **ICS 구독 피드는 학기 축을 우회 중** — `loadAllCalendarEventsForICS`가 전량을 읽은 뒤 "보관 아닌 학기들"로 걸러 잇는다. 피드가 학기 경계를 넘어 연속이어야 해서 생긴 우회 = 데이터가 날짜 축이고 싶다는 증거.
2. **전환하면 과거 일정이 구독 캘린더에서 소멸** — 위 필터가 archived 학기 일정을 버리므로, 2026-2를 보관 처리하는 순간 그 일정들이 교직원 구독 캘린더에서 사라진다.
3. **연말 사전 수집이 잘못 귀속될 예정** — 나이스 수집이 `termId: term.id`(활성 학기)로 스탬프하므로, 12월에 수집된 내년 3월 일정이 2026-2 소속이 되고, 2027-1로 전환한 뒤 주간 파생(`loadCalendarEvents(현 학기)`)에서 **안 보인다.** 학기 전환 설계와 정면 충돌.

**사실관계**: 날짜는 학기와 달리 겹치지 않는 전역 유일 축이고, 나이스 dedupe 키(`neisKey = YYYYMMDD|행사명`)도 이미 날짜 기반이다. 학사일정의 자연 정체성은 날짜다.

**규칙 확정**:

1. **학사일정 조회는 전부 날짜 축으로 전환한다.** 주간 파생은 해당 주의 날짜 범위로, ICS는 전량(현행 유지하되 학기 필터 제거). 컬렉션이 소형(연 100건 규모)이므로 전량 로드 후 메모리 필터로 충분 — Firestore 이중 범위 쿼리 불요.
2. **`termId` 필드는 동결** — 기존 문서 마이그레이션 없이 그대로 두되, **판정·필터에 쓰지 않는다.** 신규 저장 시에도 채우지 않는다(하위 호환 읽기만).
3. 나이스 수집·수동 등록 모두 학기 무관 동작 — 수집이 내년 일정을 미리 담아도 그대로 옳다(연말 사전 준비와 자연 정합).
4. 화면(학사일정 관리 탭)도 학기 선택(§2)의 **대상에서 제외** — 코호트 탭처럼 학기 축이 없는 화면으로 분류.
