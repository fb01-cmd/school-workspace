## 과제 C — 휴대폰에서 스크린샷을 제출하면 `Failed to fetch`

**기준 커밋**: `0db229f` · **사용자 실기기 신고 2026-08-20**

### 증상

휴대폰에서 업무에 **스크린샷 이미지를 첨부해 제출**하면 `portal.hmh.or.kr 내용: Failed to fetch` 경고가 뜨고 제출되지 않는다. **같은 JPG여도 어떤 것은 되고 어떤 것은 안 된다.** 엑셀 파일은 문제없다.

`Failed to fetch`는 **서버가 응답을 준 것이 아니라 요청이 서버에 닿지 못한 것**이다. 그래서 서버 로그에도 안 남고 화면에는 원인이 안 나온다.

### 확정된 사실

- **PC와 모바일의 요청 생성 코드는 완전히 같다.** 코드 분기 차이가 아니다.
- **서비스워커는 요청을 가로채지 않는다**(`public/sw.js`의 `fetch` 핸들러가 `return;`만 한다). 아니다.
- 파일 크기(388KB)는 한도(4MB)의 10분의 1이다. 아니다.
- 확장자 `jpg`는 화이트리스트에 있다(`src/lib/tasks/logic.ts:310`). 아니다.
- **서버는 원본 파일명에서 확장자만 쓴다.** `normalizeSubmissionFileName`(`src/lib/tasks/logic.ts:283`)이 `{소속}_{이름}_{업무명}.{확장자}`로 **새로 만든다.** 원본 이름의 나머지는 **어차피 버려진다.**

### 원인 후보 둘 — 한 번에 막는다

정확히 어느 쪽인지 실기기 없이는 못 가른다. **다행히 둘 다 같은 한 곳을 고치면 막힌다.**

| | 후보 | 왜 스크린샷만 |
|---|---|---|
| ① | 안드로이드 사진 선택기가 준 파일 통로가 **고른 뒤 확정까지의 몇 초 사이에 닫힌다** | 엑셀은 「파일」 앱에서 골라 통로가 안정적이다 |
| ② | 스크린샷 파일명에 붙는 **앱 이름(한글·띄어쓰기·괄호)** 이 전송 중 문제를 일으킨다 | 다른 JPG는 이름이 단순하다 |

**둘 다 「파일을 고른 시점」에 처리하면 사라진다.**

### 할 일

**파일을 고르는 순간, 내용을 즉시 읽어 안전한 이름의 새 파일로 바꿔 담는다.**

대상은 **파일을 담는 모든 자리**다:

- `src/components/mobile/MobileTasksSection.tsx` — `setStagedSubmitMap`으로 담는 곳 **전부**(`:770`, `:813` 부근)
- `src/components/admin/tasks/TasksSection.tsx` — 같은 방식으로 담는 곳 **전부** (PC도 같은 위험이 있다)

**(1) 공용 헬퍼를 만든다** — `src/lib/tasks/logic.ts`에 추가한다(서버·클라이언트 공용 파일이다).

```ts
/**
 * 고른 파일을 즉시 메모리로 읽어 **전송 안전한 이름**의 새 File 로 바꾼다 (2026-08-20).
 *
 * 두 가지를 동시에 막는다.
 * ① 안드로이드 사진 선택기가 준 파일 통로가 담기~확정 사이에 닫히는 것
 *    — 여기서 미리 읽어 두면 통로가 닫혀도 바이트는 손에 있다.
 * ② 스크린샷 파일명의 한글·띄어쓰기·괄호가 전송에서 문제를 일으키는 것
 *    — 서버는 어차피 확장자만 쓰고 이름은 새로 만든다(normalizeSubmissionFileName).
 *      그러므로 원본 이름을 그대로 보낼 이유가 없다.
 *
 * **원본 이름은 버리지 말고 호출부가 따로 보관해 화면에 표시한다.**
 */
export async function toTransportSafeFile(file: File): Promise<File> {
  const m = /\.([A-Za-z0-9]{1,10})$/.exec(file.name || "");
  const ext = m ? m[1].toLowerCase() : "bin";
  const buf = await file.arrayBuffer();
  return new File([buf], `upload.${ext}`, {
    type: file.type || "application/octet-stream",
  });
}
```

**(2) 담을 때 이 함수를 쓴다.** 담는 자리마다 `await`가 필요하므로 핸들러를 `async`로 바꾼다.

**(3) [중요] 화면에는 원본 이름을 계속 보여준다.**

지금 카드는 `staged.file.name`을 그린다. 그대로 두면 **선생님이 고른 이름 대신 `upload.jpg`가 보인다 — 회귀다.**

- 담는 자료구조에 **원본 이름 칸을 하나 더** 둔다: `{ file, displayName, note }`
- 카드의 파일명 표시를 **`displayName`으로 바꾼다.**
- 파일 크기 표시는 `file.size` 그대로면 된다(내용이 같으므로 값도 같다).

**(4) 읽기 실패도 처리한다.** `arrayBuffer()`가 실패하면(통로가 이미 닫힌 경우) **담지 말고** 이렇게 알린다:

```
파일을 읽지 못했습니다. 다시 선택해 주세요.
```

### 하지 말 것

- **서버를 고치지 마라.** 서버는 이미 확장자만 쓰고 이름을 새로 만든다. 정상이다.
- 제출 API·업로드 흐름·4MB 분기를 건드리지 마라.
- 화면에 `upload.jpg`가 보이게 두지 마라 — **(3)이 이 과제의 절반이다.**
- 파일 크기 한도(30MB)를 바꾸지 마라.

### 완료 확인

1. `npx tsc --noEmit` 0건.
2. **화면에 원본 파일명이 그대로 보인다** — 고르기 전후로 표시가 안 바뀐다.
3. `bash scripts/check_ui_removals.sh 0db229f` — 삭제 항목이 뜨면 어디로 옮겨졌는지 `파일:줄번호`로 대라.
4. **PC와 모바일 양쪽 모두** 적용됐는지 `파일:줄번호`로 각각 대라.
5. **실기기 확인은 Antigravity가 못 한다.** 보고에 *"실기기 미확인 — 스크린샷 제출은 사용자 확인 필요"* 를 명시해라.
