## 과제 0 (최우선) — 직권 배정 「담아둔 배정안」이 안 보이고, 아무 교사나 고르면 삭제된다

**기준 커밋**: `48f2aee` · **사용자 실기기 신고 2026-08-20**

### 증상 (사용자가 실제로 겪은 것)

「시간표 운영 → 직권 배정」을 열면 **담긴 항목이 화면에 하나도 안 보인다.** 그런데 교사를 고르면 *"담아둔 배정안 1건이 있습니다. 다른 교사를 선택하면 담아둔 내용이 비워집니다"* 라는 창이 뜬다. **데이터는 있는데 화면에 없다.**

### 원인 (Claude가 코드로 확인 완료 — 조사하지 말고 이대로 고쳐라)

세 개가 겹쳤다.

1. **담을 때 「누구의 시간표인지」를 저장하지 않는다.**
   - 클라이언트가 `draft_save`로 보내는 본문에 `sourceTeacherEmail`이 **없다** (`DirectSubstituteTab.tsx:675-683`, `:836-844`).
   - **서버도 그 필드를 저장하지 않는다.** `saveSwapDraft`의 `docPayload`(`src/lib/timetable/server.ts:6558` 함수 안)는 필드를 **골라서** 넣는데 그 목록에 없다. 즉 클라이언트만 고쳐도 안 된다.
   - `requesterEmail`은 **로그인한 일과계 담당자**이지 대상 교사가 아니다. 직권 배정은 남의 시간표를 다루므로 **둘이 다른 사람**이다. 그래서 별도 필드가 필요하다.
2. **그 결과 복원 코드가 죽어 있다.** `DirectSubstituteTab.tsx:271`의 `if (loaded.length > 0 && loaded[0].sourceTeacherEmail)`은 **항상 거짓**이라 교사 복원 분기가 한 번도 실행된 적이 없다. 지금까지 안 드러난 이유는 `sessionStorage` 폴백(`:286-296`)이 **같은 창을 계속 켜 둔 동안만** 가려 줬기 때문이다. 앱을 완전히 닫았다 열거나 다른 기기에서 열면 드러난다.
3. **담기 목록 UI 전체가 교사 선택 뒤에 갇혀 있다.** `DirectSubstituteTab.tsx:1406`이 `{selectedTeacherEmail ? ( ... ) : ( ...먼저 선택해 주세요... )}`라서, 담긴 항목이 있어도 교사가 비어 있으면 **아무 표시가 없다**(담기 목록 블록은 `:1777` 이하, 그 안에 있다).

**게다가 되살릴 방법이 없다.** `handleSelectTeacher`(`:430-453`)에서 `currentEffectiveTeacher`가 빈 문자열이므로 **어떤 교사를 골라도** 조건이 참이 되어 확인창이 뜨고, 확인을 누르면 **서버 초안까지 지운다**(`draft_delete`). 즉 보는 것도 살리는 것도 불가능하고 아무거나 누르면 삭제된다.

### 할 일

**(1) 서버 — 필드를 저장한다**

`src/lib/timetable/server.ts`의 `saveSwapDraft` 안 `docPayload`에 아래를 추가한다. **직권 초안일 때만** 넣는다(교사 본인 초안에는 불필요).

```ts
...(draftData.direct && draftData.sourceTeacherEmail
  ? {
      sourceTeacherEmail: String(draftData.sourceTeacherEmail).trim().toLowerCase(),
      sourceTeacherName: String(draftData.sourceTeacherName || "").trim().slice(0, 40),
    }
  : {}),
```

- **이메일 형식 검증을 추가한다.** 같은 함수가 `counterpartEmail`에 이미 하는 것과 **같은 정규식·같은 방식**으로, 형식이 틀리면 `throw`한다. 새 패턴을 만들지 마라.
- `listSwapDrafts`가 문서를 그대로 돌려주는지 확인하고, 필드를 골라 담는 구조면 거기에도 추가한다.

**(2) 클라이언트 — 담을 때 함께 보낸다**

`DirectSubstituteTab.tsx`의 `draft_save` 본문 **두 곳 모두**(`:675`, `:836`)에 추가한다.

```ts
sourceTeacherEmail: selectedTeacherEmail,
sourceTeacherName: selectedTeacherName,
```

- 체인 저장 쪽(`:675`)은 변수명이 다를 수 있다. **그 화면에서 실제로 선택된 대상 교사**를 넣어라.

**(3) 화면 — 담긴 게 있으면 무조건 보이게 한다**

`:1406`의 조건을 고쳐, **담기 목록 블록(`:1777` 이하)은 `selectedTeacherEmail`과 무관하게 렌더**되도록 한다. 시간표 그리드·후보 목록 등 나머지는 지금처럼 교사 선택 뒤에 둬도 된다.

- 교사가 안 골라졌는데 담긴 항목이 있으면, 목록 위에 **누구 것인지와 다음에 할 일**을 한 줄로 보여라. 예: `이 배정안은 000 선생님 시간표에서 담은 것입니다. 이어서 작업하려면 위에서 그 선생님을 선택하세요.`
- **이름을 모르는 경우**(아래 4번) 문구: `담긴 항목이 있으나 어느 선생님 시간표에서 담은 것인지 확인할 수 없습니다. 내용을 확인하고 직접 비워 주세요.`

**(4) [중요] 파괴적 동작 가드 — 여기가 이 과제의 핵심이다**

`handleSelectTeacher`(`:430-453`)를 이렇게 바꾼다.

- **`cartItems[0]?.sourceTeacherEmail`이 비어 있으면(= 주인을 모르는 옛 초안) 자동 삭제를 하지 마라.** 확인창도 띄우지 말고, **담긴 항목을 지우지 않은 채** 교사 선택만 진행한다. 화면에는 3번의 「이름을 모르는 경우」 문구와 함께 목록이 그대로 보인다. 사용자가 **[전체 비우기]를 직접 누를 때만** 지운다.
- 주인을 아는 경우(1·2번 수정 이후 새로 담은 것)는 **지금 동작 그대로** 둔다 — 확인창을 띄우고, 확인하면 비운다.

> **왜 이렇게 하는가**: **주인을 잃어버렸다는 이유로 데이터를 지우는 것이 최악의 선택이다.** 지금 코드가 정확히 그렇게 하고 있고, 사용자가 오늘 그 창을 만났다. 복구 불가한 삭제는 **사용자가 내용을 보고 스스로 누른 경우에만** 일어나야 한다(`AGENTS.md` §1-2 「복구 불가한 파괴적 작업」).

### 하지 말 것

- `requesterEmail`을 대상 교사로 바꾸지 마라. 그건 **누가 요청했는가**이고 감사·권한 검사가 그 값을 쓴다.
- 기존 초안을 일괄 정리하는 마이그레이션 스크립트를 만들지 마라. **주인을 모르는 초안은 사용자가 화면에서 보고 판단한다.**
- 담기·반영 로직 자체를 건드리지 마라. 이 과제는 **저장 필드 + 표시 + 삭제 가드** 셋뿐이다.

### 완료 확인

1. `npx tsc --noEmit` 0건.
2. **재현 시나리오**: 교사 A를 골라 1건 담는다 → 앱을 **완전히 닫는다** → 다시 열어 직권 배정에 들어간다.
   - **담긴 1건이 화면에 보인다.**
   - 안내 줄에 **교사 A의 이름**이 나온다.
   - 교사 B를 고르면 확인창이 뜨고, 취소하면 담긴 것이 **그대로 남는다.**
3. **옛 초안 시나리오**(주인 정보가 없는 것): 담긴 항목이 보이고, 교사를 골라도 **자동으로 지워지지 않는다.**
4. `bash scripts/check_ui_removals.sh 48f2aee` — 사라진 상호작용이 뜨면 항목마다 이 지시서에 있었는지 확인해라.
5. **실기기 확인은 Antigravity가 못 한다.** 보고에 *"실기기 미확인"* 을 명시해라.

## 과제 2 — 명단 요약본 갱신 지연 (승인한 변경이 5분간 안 보이는 문제)

**기준 커밋**: `47f422f` · **대상**: `src/lib/org/roster.ts`

**증상**: 교직원 프로필을 승인하거나 고친 직후, 그 변경이 **최대 5분간 화면에 안 보인다.** 절약 모드에서는 더 길다.

**원인 (Claude 확인 완료)**

`loadTeacherProfiles()`가 이 순서로 돈다.

| 줄 | 하는 일 | 문제 |
|---|---|---|
| `roster.ts:60` | 요약본 재조립을 서버에 **요청만 하고 기다리지 않는다** | — |
| `roster.ts:67` | 곧바로 요약본을 읽는다 | **아직 옛날 것이다** |
| `roster.ts:69` | 그 값을 캐시에 넣는다 | **옛 값이 기본 TTL(5분)간 고정된다** |

같은 파일 16~18행에 이 함정 경고가 이미 있지만 *"요청을 언제 던질까"* 만 다루고 **"읽기가 기다려야 한다"** 가 빠져 있었다.

**설계 (이대로 구현해라. 순서가 곧 정확성이라 임의로 바꾸지 마라)**

1. `requestRosterIndexRebuild()`가 **진행 중인 요청의 Promise를 모듈 변수에 보관**하게 한다. 반환형은 그대로 `void`로 두고 외부 호출부는 바꾸지 않는다 — 기다릴 사람만 그 변수를 본다.
   - 요청이 끝나면(성공·실패 무관) 변수를 비운다.
2. `fetchProfilesViaIndexOrOrigin()`이 **요약본을 읽기 전에**, 진행 중인 재조립이 있으면 **최대 3초까지 기다린다**(`Promise.race`로 타임아웃).
   - **3초는 상한이지 대기 시간이 아니다.** 재조립이 200ms에 끝나면 200ms만 기다린다.
3. **3초 안에 안 끝나거나 요청이 실패했으면, 요약본을 읽지 말고 원본(`teacher_profiles` 전수)을 직접 읽는다.**
   - 이 경우 **캐시에는 넣되**, 원본이므로 값은 정확하다.
   - 비용은 1회 89 reads로 늘지만, **틀린 값을 5분간 보여주는 것보다 낫다.**
4. 위 대기는 **재조립이 진행 중일 때만** 한다. 평상시(요청이 없던 경우) 경로는 **지금과 완전히 동일해야 한다** — 매번 3초씩 기다리게 만들면 안 된다.

**함정 (반드시 확인)**

- **서버는 10초 중복 방지가 있다.** 상수는 `src/lib/org/roster_index_shared.ts:18`(`ROSTER_INDEX_DEBOUNCE_MS = 10 * 1000`)에 **정의**돼 있고, 판정은 `src/lib/org/roster_index.ts:53-55`에서 한다. 10초 안에 두 번째 요청이 오면 **재조립 없이** `{ built: false, reason: "debounced" }`로 즉시 돌아온다(`roster_index.ts:54`).
  - **그 경우 기다려도 값이 안 바뀐다.** 다른 사람이 방금 재조립했으면 내 변경은 아직 안 들어간 색인이다. **이때는 3번(원본 직접 읽기)으로 가야 맞다.**
  - **지금 `requestRosterIndexRebuild`는 응답 본문을 읽지 않는다**(`roster.ts:28-32`에서 `await fetch(...)` 하고 버린다). **`res.json()`으로 `built`·`reason`을 꺼내 쓰도록 고쳐야 한다.** 이게 이 과제에서 유일하게 기존 함수의 동작을 바꾸는 지점이다.
- **`REBUILD_MARKER_KEY` 5분 억제 마커를 없애지 마라.** 그건 여러 클라이언트가 동시에 재조립을 때리는 것을 막는 장치다.
- 서버 경로(`buildRosterIndex`를 직접 부르는 곳)는 **이 과제 범위가 아니다.** 건드리지 마라.

**완료 확인**

- `npx tsc --noEmit` 0건.
- **셀프테스트를 추가해라** — 최소 3케이스: ⓐ 재조립이 제때 끝나면 새 값을 읽는다 ⓑ 3초를 넘기면 원본으로 간다 ⓒ 재조립 요청이 없던 평상시 경로는 종전과 동일하다.
- **실기기 확인은 Antigravity가 못 한다.** 프로필 승인 후 즉시 반영되는지는 **사용자 또는 Claude가 확인**하므로, 보고에 *"실기기 미확인"* 을 명시해라.

**주의**: 이 과제는 순서·경합 로직이라 원래 Claude 몫이다(`AGENTS.md` §1-2). 설계를 Claude가 위에 고정해 두었으므로 **구현만** 해라. **설계를 바꿔야 한다고 판단되면 고치지 말고 보고해라.**
