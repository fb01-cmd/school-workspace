# 수읽기 엔진 스펙 — 루미큐브 수순(기보)을 제안하는 탐색 보조

작성 2026-08-22 (Claude, Max20 선행 확보분). 발안 = 사용자 (로드맵 §2 「루미큐브 수읽기 엔진」): *"체스 게임에 AI가 붙어서 몇 수 앞을 다 계산해보는 느낌. 솔버 로직과는 전혀 다른 방식으로 일과계에게 도움."*

선행 스펙 = [`timetable_manual_move_spec.md`](./timetable_manual_move_spec.md) (직접 조정 — 수 공간의 원본). 이 문서는 그 수 공간을 **기계가 두는 쪽**을 정의한다.

## §0 정체 규정 — LLM이 아니라 탐색 엔진이다

체스의 "AI"(스톡피시)는 LLM이 아니라 결정론 탐색 엔진이다. 이 기능도 같다 — **대원칙 유지: AI(LLM)는 질문 해석만, 수는 엔진이 만들고 검사기가 전수 채점** (ask_fix_spec의 원칙 그대로). LLM은 수 생성·평가 경로에 일절 없다. 따라서 결정론·재현 가능·AI 호출 0건(무료 한도 무관)이다.

**기존 도구와의 관계**: 「해결안 찾기」(체인 탐색 v3)의 **후계(v4)다.** 별도 메뉴가 아니라 같은 진입점(해결안 찾기 버튼·물어보고 고치기의 수 생성기)을 업그레이드한다. 달라지는 것 셋 —

| | 현행 체인 탐색 v3 | 수읽기 엔진 (v4) |
|---|---|---|
| 수 공간 | 교환 체인(전용 로직) | **직접 조정 UI와 동일한 수** (이동·맞바꿈·잠깐 빼두기) — 사람이 할 수 있는 수만 둔다 |
| 산출물 | 최종 교환안 1개 | **수순(기보) 상위 3개** — 일과계가 한 수씩 밟고, 중간에 멈추고, 다른 라인으로 갈아탈 수 있다 |
| 수읽기 | 고정 패턴(2자·전파) | **빔 탐색 N수 앞** + 「빼두기」를 중간 수로 허용 (사람 손의 비장의 수 — 어떤 자동 도구도 아직 안 쓴다) |

## §1 수 공간 (직접 조정과 완전 동일 — 이것이 설계의 심장)

엔진이 두는 수 = 사람이 직접 조정에서 둘 수 있는 수, 그 이상도 이하도 아니다:

1. **이동/맞바꿈** — `moveCandidates.evaluateMoveCandidates`가 주는 후보 그대로 (하드 차단·집기 규약 포함 — 동시수업·자리표시·연속묶음은 엔진도 못 만진다).
2. **잠깐 빼두기(park) / 되돌리기(unpark)** — 중간 수로만 허용. **완결 수순 조건: 라인이 끝날 때 트레이가 비어 있어야 한다** (빼놓고 안 돌아오는 라인은 제안 자격 없음 — 게시 관문과 동형).

수 공간이 같으므로: 엔진의 제안 = 사람이 그대로 재연 가능 / 사람이 두다 만 판 = 엔진이 이어서 읽기 가능. 채점은 `moveCandidates`(본검사기 단일 소재지) 재사용 — **엔진과 화면과 서버가 같은 눈으로 본다.**

## §2 탐색 (결정론 빔 탐색)

- **목표 입력**: ⓐ 감점 상세의 특정 항목(해결안 찾기 진입) ⓑ 물어보기의 해석 결과(기존 목표 어휘 재사용) ⓒ 목표 없음 = "이 판을 더 좋게" (총점 최소화).
- **빔 탐색**: 깊이 D(기본 4수) × 빔 폭 W(기본 8). 각 노드에서 후보 생성 → 평가 → 상위 W만 다음 수로. 평가 = 사전식 [목표 항 해소 여부, 하드(항상 0 강제), 공식 총점, 트레이 잔량]. 동률은 (day, period, kind) 정렬로 결정론.
- **가지치기**: 후보 생성 시 목표와 무관한 수를 거른다 — 목표 위반의 관련 자원(그 교사·그 학급·그 요일)을 건드리는 수 + 각 노드 상위 K(기본 12)만 전개. **예산 상한: 평가 노드 총 2,000개 또는 워커 8초** — 초과 시 그때까지의 최선 라인만 제안(부분 결과 정직 표시).
- **park의 전개 규칙**: 깊이 여유가 2수 이상 남았을 때만 park 수를 열고(되돌릴 기회가 있어야 하므로), 같은 수업의 park→즉시 unpark 제자리 수는 금지(무한 루프 방지).
- **성능 전제**: 실데이터 채점은 후보당 수~수십 ms(M1 채점기 실측으로 갱신). 예산 2,000노드 × 10ms ≈ 20초가 최악 — 기본 예산을 낮게 잡고(500노드) 「더 깊이 읽기」 버튼으로 예산 증액. 후속 최적화(증분 채점기) 전까지는 예산이 품질을 결정함을 화면에 정직 표시("500가지 수를 읽었습니다").

## §3 산출물 계약 — 기보(Line)

```ts
interface LookaheadLine {
  ops: BaseRevisionOp[];          // 한 수 = op 1건 (직접 조정과 동일 어휘)
  stepScores: number[];           // 수마다 공식 총점 (중간 악화 라인도 정직 표시)
  finalDelta: number;             // 최종 총점 변화 (음수 = 개선)
  resolves: string[];             // 해소되는 감점 항목 키
  touched: Array<{grade; classNum; day; period}>; // 미니 그리드 미리보기용
}
```

- 상위 3개 라인 반환. **텍스트 수순 표기 금지 원칙 그대로** — 화면은 라인을 미니 그리드 연쇄로 그린다(직접 조정 §0-1).
- **적용 방식 두 가지**: ⓐ 한 수씩 밟기 — 각 수를 기존 `draft_op`(+`expectedOpCursor`)로 적용, 언제든 멈춤/실행취소 ⓑ 통째 적용 — M2의 연쇄 op 1건으로(원자성). ⓐ가 기본 — 사람이 과정을 소유한다는 것이 이 기능의 존재 이유다.

## §4 화면 (Antigravity 몫 — 배치 원본)

- 진입 1: 감점 상세의 「해결안 찾기」 버튼 — 지금 자리 그대로, 내부 엔진만 교체. 결과 카드가 교환안 텍스트 대신 **기보 카드**(미니 그리드 연쇄 + 최종 delta + [한 수씩] [전체 적용]).
- 진입 2: 직접 조정 모드에서 수업을 집은 상태의 「이 수업 수읽기」 버튼 — 그 수업을 첫 수로 하는 라인만 탐색.
- 라인 hover = 그리드 위 고스트 미리보기(수순 전체 결과), 카드의 수 hover = 그 수까지의 중간 판.
- 못 찾으면: 물어보기의 잠금 안내와 같은 눈높이 문구 + 읽은 수 예산 표시("500가지 수를 읽었지만 개선 수순이 없습니다 — 더 깊이 읽기").

## §5 관문·검증

- 신규 selftest(`lookahead_selftest.ts`, Firestore 무의존): ① 합성 세계에서 정답이 알려진 2수·3수 문제를 찾는가(park 필수 케이스 포함 — 빼놨다 되돌려야만 풀리는 판) ② 결정론(같은 입력 = 같은 기보) ③ 완결 수순 조건(트레이 미청산 라인 배제) ④ 예산 상한 준수.
- 기존 관문 무관: 솔버 벤치마크·백지 편성과 독립(이 엔진은 편집기 보조 — 솔버 산출물을 바꾸지 않는다).
- **실전 통과 기준**: 실전 잔존 위반(장예빈 수 1-2-3)에 대해 ⓐ 몇 수 기보를 내는가 ⓑ 못 내면 예산·깊이 어디가 병목인지 계측이 말해주는가.

## §6 분담·순서

- **Claude**: 엔진 코어(빔 탐색·park 시뮬레이션·결정론·예산) + selftest — §1-2 직접 구현 영역(정확성·원복이 코드 구조).
- **Antigravity**: §4 화면(기보 카드·고스트 미리보기·버튼 배선).
- **순서**: **L1** = M1 완료 후 — park 없는 수읽기(이동·맞바꿈만, 한 수씩 적용)로 해결안 찾기 교체. **L2** = M2 완료 후 — park 수 + 통째 적용(연쇄 op). 수읽기 자체는 M2 저장 형식과 독립(park 시뮬은 메모리에서 가능)이므로 L1을 먼저 내도 된다.
- 읽기량: 전 계산이 브라우저(워커) 안 — Firestore·AI 호출 0건.
