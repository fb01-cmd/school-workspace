## §1 메뉴 이름과 배치

### §1-1 이름 — **「쪽지·업무」** (2026-08-19 사용자 확정)

동사를 넣지 않는다. 사용자 지적: *"쪽지/업무 보내기라고만 하면 보내는 장소처럼만 느껴져. **수신도 하고 검토도 하는 자리야.**"* — 이 화면은 보내는 곳이자 받는 곳이자 확인하는 곳이므로, 동사가 들어가면 **이름이 기능의 3분의 1만 가리킨다.**

- 「메신저」는 쓰지 않는다 — memo_spec §4-1 확정(화면 명칭은 「쪽지」로 통일).
- 조직도는 이름에 넣지 않는다 — *"이름이 조직도라면 거기서 업무나 쪽지를 보낼 수 있다는 생각 자체를 못 한다"*(사용자).

### §1-2 배치 — 메뉴 2개를 흡수하고 1개로 줄인다

`src/app/admin/page.tsx` — **「교직원 공통 도구」 섹션, 「홈」 바로 아래.**

```
교직원 공통 도구
  홈 (대시보드)
  쪽지·업무            ← 신설 (기존 「쪽지」·「업무 관리」를 흡수)
  ~~쪽지~~             ← 제거
  ~~업무 관리~~        ← 제거
  내 시간표
  …
  교직원 조직도         (현행 그대로 — 승인 대기·수동 배치·트리 편집은 관리 기능)
```

**구현 접점 4곳** (page.tsx는 배열이 아니라 JSX 하드코딩이다):
1. `MenuType`에 `"hub"` 추가
2. `renderContent()`에 `case "hub"` 추가. **`case "memo"`·`case "tasks"`는 지우지 말고 `"hub"`로 넘긴다**(아래 3번 이유).
3. **⚠️ 크로스 네비 호환이 이 개정의 최대 함정이다.** 알림 센터·대시보드 쪽지 패널·업무 카드가 `window.dispatchEvent(new CustomEvent("admin_navigate", { detail: { menu: "memo", memoId } }))` 형태로 **특정 쪽지/업무를 지목해 이동**한다(page.tsx L100~). 메뉴만 지우고 끝내면 **알림을 눌러도 아무 데도 안 가는 죽은 링크가 된다.** `menu: "memo"` → 허브의 [쪽지] 구분, `menu: "tasks"` → [업무] 구분으로 **별칭 라우팅**하고, `memoId`·`taskId`가 있으면 해당 항목을 연 상태로 도착시킨다.
   - 이 배선에는 **이미 알려진 결함이 하나 있다**: `case "memo"` 분기가 도달 불가라 `initialMemoId`가 전달되지 않는다(2026-08-19 실증, 로드맵 읽기 다이어트 「기타 ⓐ」). **허브로 옮기면서 같이 고친다** — 옮겨 심으면 안 되는 버그다.
4. 사이드바 JSX에서 「쪽지」·「업무 관리」 버튼 제거 + 「쪽지·업무」 추가
5. **[2026-08-19 사용자 메모] 「홈」의 부제 「(대시보드)」를 없앤다.** 홈은 더 이상 대시보드 역할이 아니다(관리자 화면 제외). 두 곳이다 — `page.tsx:625` 사이드바 라벨 `홈 (대시보드)` → **`홈`**, `page.tsx:1066` 상단 제목 `어드민 홈 대시보드` → **`홈`**. 후자는 일반 교사에게도 "어드민"이 그대로 보이던 자리라 화면 문구 규칙(개발 용어 금지) 위반이기도 하다. 사이드바 JSX를 어차피 건드리는 작업이므로 같이 처리한다.

컴포넌트는 기존 관례대로 `next/dynamic` 지연 로드. 전 교직원 노출(super_admin 전용 아님).
**모바일 `/m`은 무관하다** — `MobileMemoSection`·`MobileTasksSection`은 별도 IA이므로 이 개정으로 건드리지 않는다.

## §2 화면 골격 — 2단 고정

```
┌──────────────┬────────────────────────────────────────────────┐
│ 좌 320px [◀] │ 우 (나머지)                                    │
│ 조직도 상주  │  [ 업무 ] [ 쪽지 ]          ← 큰 구분 2개      │
│              │   내 할 일 | 보낸 업무      ← 하위 탭          │
│ [이름 검색]  │ ──────────────────────────────────────────────│
│              │                                                │
│ ▾ 교무기획부 │   목록·상세 (기존 화면 그대로)                 │
│   □ 홍길동   │                                                │
│   □ 김철수   │                                                │
│ ▸ 학생부     │                                                │
│ …            │                                                │
│              │                                                │
│ N명 담김     │                                                │
└──────────────┴────────────────────────────────────────────────┘

  사람을 담으면 ↓ 우측 위에 띠가 내려온다 (목록은 뒤에 그대로)

┌──────────────┬────────────────────────────────────────────────┐
│ 좌 320px     │ 홍길동 × 김철수 × … 3명   [업무 등록] [쪽지]  │
│ 조직도       │ ──────────────────────────────────────────────│
│ ☑ 홍길동     │   목록·상세 (그대로)  →  누르면 작성 폼으로   │
└──────────────┴────────────────────────────────────────────────┘
```

- 좌·우 각각 독립 스크롤. 좌측 폭 고정(320px), 우측 가변.
- **좌측은 접을 수 있다. 기본은 펼침, 접힌 상태는 기억한다**(`localStorage`, 사이드바 접힘 전례). 읽기만 할 때 자리를 비켜 주기 위한 것이므로 접기 버튼은 눈에 띄되 작게.
- ~~**최소 폭 1024px.** 미만에서는 화면을 렌더하지 않고 "이 화면은 컴퓨터에서 사용해 주세요" 한 줄만 — 반응형 축소판을 만들지 않는다(전제 2).~~ **[2026-08-20 대체]** 1024px 미만: 본 화면을 1단으로 렌더 + 조직도는 「수신자 선택」 버튼 → 전면 오버레이(같은 컴포넌트·같은 선택 상태). 전제 2의 개정 경위 참조.

### §2-0 모드는 「담긴 사람 수」가 정한다 — 이 화면의 중심 규약

우측에 별도의 모드 전환 버튼을 두지 않는다.

| 담긴 사람 | 우측 | 뜻 |
|---|---|---|
| 0명 | 목록·상세 (읽는 자리) | **받고 확인하는 시간** |
| 1명 이상 | 목록 위에 대상 띠 + 행동 버튼 | **보내는 시간** |

**좌측 조직도가 곧 모드 스위치다.** 사람을 담으면 보내는 화면이 되고, 비우면 읽는 화면으로 돌아온다. 배워야 할 조작이 없다.

### §2-1 좌측 — 조직도 (상주)

| 요소 | 동작 |
|---|---|
| 검색창 | **이름만** 로컬 필터. 서버 호출 0. **입력이 있으면 트리 대신 평면 결과 목록을 띄운다** — §2-1-1 |
| 부서 헤더 | 이름 클릭 = 접기/펼치기 · **체크박스 = 그 부서 전원 담기/빼기** (`indeterminate` 지원) · 우측에 인원수 |
| 사람 행 | **체크박스 = 담기/빼기** · **이름 클릭 = 정보 카드**(§2-2) |
| 하단 고정줄 | `N명 담김` + [비우기] |
| 초기 펼침 | **내 소속 부서만** 펼치고 나머지는 접는다 (memo_spec §11-2 승계) |

**제스처 분리가 이 화면의 핵심 규약이다** — 체크는 담기, 이름 클릭은 보기. 더블클릭 같은 숨은 조작은 만들지 않는다(배워야 알 수 있는 조작은 채택 논리에 반한다).

### §2-1-1 검색은 트리를 필터링하지 않는다 — 평면 결과 목록이다 (2026-08-19 사용자 확정)

> **[개정 2026-08-19]** 초판은 *"입력 중에는 트리가 일치 항목만 남고 부서는 자동 펼침"* 이었다. 실기기에서 뒤집혔다: *"조직도는 내가 그 사람의 위치를 알고 있을 때 쓰는거고, **검색은 내가 그 사람의 위치를 잘 모를 때 쓴다**."* 트리를 필터링하는 방식은 일치자가 부서 아래 흩어져 있어 **여전히 부서를 훑게 만든다** — 검색을 쓰는 이유 자체를 못 푼다.

**규약**: 검색어가 1자 이상이면 좌측 패널의 트리 자리를 **평면 결과 목록**이 대체한다. 부서 계층은 결과에 나타나지 않는다.

| 항목 | 규약 |
|---|---|
| 후보 집합 | **소속이 등록된 교직원 전원**(§3의 명단과 동일 — `noDept` 미포함). 부서를 가로질러 하나의 목록으로 평평하게 편다 |
| 매칭 | **이름만**. 이메일·아이디·부서명으로 매칭하지 않는다 (memo_spec §11-2) |
| 한 줄의 표시 | **`이름` + 부제 `부서`** — 부서가 여럿이면 전부(`홍길동 · 교무기획부 · 수학`). 이 부제는 **검색 결과에서 항상** 붙는다(동명이인일 때만 붙이는 §11-5 규칙의 예외 — 여기서는 부서가 곧 "그 사람이 어디 있는지"라는 검색의 답이다) |
| 중복 | **사람 1명 = 줄 1개.** 3개 부서 소속이어도 3줄이 되지 않는다 (이메일 기준 유일) |
| 선택 | 줄 왼쪽 체크박스 = 담기/빼기. **트리와 같은 제스처**(체크는 담기, 이름 클릭은 정보 카드) — 검색 결과라고 다른 조작을 만들지 않는다 |
| 담긴 표시 | 이미 담긴 사람은 결과에서도 체크된 채로 보인다. 검색어를 지우면 트리로 돌아오고 **담긴 사람은 그대로 유지**된다 |
| 0건 | 목록 자리에 한 줄: `"이름과 일치하는 선생님이 없습니다."` — 부서 헤더를 남기지 않는다 |
| 정렬 | 이름 가나다순. 부서장·담임 우선 정렬(`sortMembersForDept`)은 **쓰지 않는다** — 그 정렬은 부서 안에서만 뜻이 있다 |
| 비용 | 서버 호출 0. 이미 불러온 명단(§5-1 캐시)만 필터링한다 |

- 부서 단위 전체 선택(부서 헤더 체크)은 **트리에서만** 한다. 검색 결과에는 부서 헤더가 없으므로 그 조작도 없다.
- 「효명고 전체 선택」(§2-1-2)은 검색 중에는 숨긴다 — 보이는 것은 일부인데 버튼은 전원을 담으면 오해가 확실하다.

### §2-1-2 「효명고 전체 선택」 — 기존 두 픽커에 있던 기능이다 (회귀 방지)

전 교직원 발송의 **유일한 수단**이다. memo_spec §11-2가 그룹 선택을 화면에서 제거하면서 *"전 교직원 발송은 조직도 전체 선택으로 대체된다"* 고 못 박았으므로, 이것이 없으면 전 교직원에게 보낼 방법이 사라진다.

- 위치: 검색창 아래 · 부서 트리 위 (기존 `MemoSection`·`TaskRecipientPickerModal`과 같은 자리)
- 라벨: **`효명고 전체 선택 (N명)`** / 전원이 담긴 상태에서는 `전체 해제 (N명)` — N은 명단 인원수(소속 있는 교직원, 현재 81)
- 하단의 [비우기]는 **전체 해제와 별개로 유지**한다(비우기는 부분 선택 상태에서도 쓰는 버튼)

### §2-2 정보 카드 — 좌측 위로 뜨는 팝오버

이름을 클릭하면 좌측 패널 위에 팝오버(폭 ~280px)가 뜬다. **우측 작업 영역을 뺏지 않는다** — 작성 중에도 내선번호를 확인할 수 있어야 하기 때문이다.

- 내용: 이름 · 부서(복수면 전부) · 직위 · 담임이면 `N학년 M반` · **내선번호** · 부서장 표시
- 버튼: [담기] (이미 담겼으면 [빼기])
- 바깥 클릭 또는 Esc로 닫힘

> 이 카드가 로드맵 피드백 16번(「교직원 조직도」를 관리자 전용으로 → 철회)이 짚은 **내선 등 정보 열람 수요**를 흡수한다.

### §2-3 우측 — 읽는 자리 (담긴 사람 0명)

**큰 구분 2개 + 하위 탭** (2026-08-19 사용자 확정). **업무를 왼쪽에 둔다** — §2-5 참조.

```
[ 업무 ]  [ 쪽지 ]
  ├ 내 할 일 · 보낸 업무          (업무를 고르면)
  └ 받은 쪽지 · 보낸 쪽지 · 즐겨찾기 (쪽지를 고르면)
```

- **처음 들어오면 [업무] → [내 할 일]** (사용자 확정). 마지막 위치를 기억하지 않는다 — 매번 같은 자리에서 시작하는 편이 예측 가능하고, 그 자리가 「내 할 일」인 것이 §2-5의 유도 장치다.
- 목록·상세의 내용과 동작은 **기존 화면 그대로** 옮긴다. 검색·즐겨찾기·회수·삭제·읽음 현황·재촉·제출함 등 지금 되는 것이 하나도 빠지면 안 된다(§8-11).
- 각 목록은 기존 컴포넌트를 재사용한다. **모달로 열리던 상세는 우측 안 분할로 바꿔도 되지만, 기능을 다시 구현하지 않는다**(AGENTS.md ①-1 재작성 금지).

### §2-4 우측 — 보내는 자리 (담긴 사람 1명 이상)

목록 위에 띠가 내려온다: **담긴 사람 칩(이름만, × 제거) + `총 N명` + [비우기] + 행동 버튼 2개.**

**이 화면의 실제 이득이 여기서 나온다.** 기존 [쪽지 쓰기]는 ①수신자 → ②작성 2단계 모달이라, 작성 중에 사람을 바꾸려면 ①로 돌아가야 한다. 여기서는 **좌측이 ①을 상시 수행하므로 작성 폼은 처음부터 ② 상태로 뜨고, 작성 중에도 좌측 체크로 대상이 즉시 바뀐다.**

| | 업무 (주) | 쪽지 (보조) |
|---|---|---|
| 버튼 | **[업무 등록] — 강조(primary)** | [쪽지 보내기] — 보조(secondary) |
| 입력 | 업무명 · 기한(날짜+시각) · 확인형/제출형 · 양식 첨부 · **내용** | 제목(선택) · 내용(서식) · 첨부 |
| 발송 | `{action:"prepare"}` → `{action:"send", taskId}` **2회** | `POST /api/memo {action:"send"}` **1회** |
| 버튼 라벨 | `N명에게 보내기` | `N명에게 보내기` (memo_spec §11-1 — 확인창 없음) |
| 발송 후 | 폼·담긴 사람 초기화 → 읽는 자리로 복귀 + [보낸 업무] 탭으로 이동 | 동일 + [보낸 쪽지] 탭으로 이동 |

> **🔴 이 표의 정정 (2026-08-19) — 위 두 칸이 틀렸었다. §0 전제 4와 같은 사고다.**
> 초판은 업무 입력에 **「지시 내용」**, 쪽지 입력에 **「링크」** 라고 적었다. **둘 다 사용자가 이미 없애기로 하고 실제로 제거까지 끝낸 것**이다 — 「지시」는 로드맵 8번(*"어감이 매우 안 좋아"* → 전면 금지, 커밋 `92fadca`), 링크 첨부는 로드맵 28번(*"본문에 링크가 먹으니 없어도 될 것 같아"* → 입력 UI 제거, 커밋 `306e07a`).
> **Claude가 이 스펙을 쓰면서 그 두 결정을 확인하지 않았고, 구현자는 스펙대로 충실히 만들었다.** 그래서 허브에 「지시 내용 및 안내 사항」 라벨과 「웹 링크 / + 링크 추가」 입력이 되살아났다 — **구현 잘못이 아니라 스펙 잘못이다.**
> **교훈(§0 전제 4의 반복)**: 스펙에 입력 항목을 적을 때는 **그 항목이 살아 있는지 로드맵의 제거 결정과 대조**한다. 문서가 스스로 낡으면, 그 문서를 근거로 만든 화면이 사용자가 지운 것을 되살린다.

- **[업무] ↔ [쪽지] 전환 시 담긴 사람은 유지된다.** 작성하던 본문이 있으면 전환 시 확인 1회(경고 없이 버리지 않는다). **첨부·양식 파일도 같다 — 이미 올라간 파일을 조용히 버리지 않는다.**
- 발송 후 이동은 **같은 화면 안 탭 전환**이다 — 메뉴를 떠나지 않으므로 크로스 네비가 필요 없다.

### §2-5 업무로 유도한다 — 이 화면의 취지 (2026-08-19 사용자)

> *"이 메뉴의 취지가 **불편한 메신저 기반의 업무를 개선하자**는 거라, 기존에 사용하는 기능은 그대로 구현하되 **업무 쪽으로 유도**를 하고 싶어."*

현장의 기본값은 "메신저로 말로 시키기"다. 그러면 누가 했는지 세는 일이 사람 몫으로 남는다. 업무로 보내면 기한·수락·완료·제출이 자동으로 집계된다. **이 화면은 그 전환을 돕되, 쪽지를 불편하게 만들어서 밀지는 않는다**(쪽지는 그대로 다 된다 — 사용자 지시).

유도는 **배치와 기본값**으로만 한다. 다음 4개가 전부다.

1. **처음 뜨는 곳이 [내 할 일]** — 이 화면의 첫인상이 "내가 처리할 업무"다.
2. **탭 순서에서 [업무]가 [쪽지]보다 앞**.
3. **사람을 담았을 때 [업무 등록]이 주 버튼, [쪽지 보내기]가 보조 버튼** — 아무 생각 없이 누르면 업무로 간다.
4. **쪽지 작성 중 [업무로 바꾸기] 전환** — 제목·본문·수신자를 그대로 들고 업무 폼으로 넘어간다(반대 방향도 동일). 옆에 도움말 한 줄: *"기한이 있는 일은 업무로 보내면 누가 끝냈는지 자동으로 모입니다."* **이 문구는 전환 버튼 옆에 상시 1개만 둔다.**

**금지 — 이것들은 유도가 아니라 잔소리다.**
- 쪽지 내용을 읽고 "이건 업무 같습니다" 류로 **판정·제안하는 자동 장치**(자동 교정 금지 계열, 9c-D 철칙과 같은 선).
- 쪽지를 보낼 때 뜨는 확인창·경고 (memo_spec §11-1이 없앤 마찰을 되살리는 것).
- "N건 중 M건은 업무로 보내는 게 좋습니다" 류의 **대조 화법** (AGENTS.md 화면 문구 규칙 4).
- 쪽지 기능의 축소·숨김. **기존에 되던 것은 전부 그대로 된다.**

## §3 담긴 사람(선택 상태) 규약

- **자료구조 = `Set<string>` (소문자 이메일).** 기존 두 픽커와 동일. uid 아님.
- **중복 제거는 이메일 기준.** 한 사람이 여러 부서에 속하므로 부서 전체 선택이 겹치면 1명으로 센다(서버도 재차 제거).
- **명단 = 소속이 등록된 교직원만** (현재 89건 중 81건). `noDept` 계정·소속 빈 계정은 **목록에 뜨지 않는다** — 받아도 열지 못하는 사람을 고를 수 있으면 안 된다(memo_spec §11-2).
- **이름만 보여준다. 이메일은 화면 어디에도 쓰지 않는다.** 동명이인은 memo_spec §11-5 규칙(모호할 때만 부서 부제).
- **수명**: 메뉴를 벗어나면 비운다. `sessionStorage`에 영속시키지 않는다 — 다음 접속에 남은 대상이 오발송으로 이어진다. 단 **작성 중 내용이 있는 상태로 이탈하면 확인 1회**(피드백 35번 「담기 이탈 경고」 계열).
- 우측 칩 줄과 좌측 체크는 **양방향 동기화**. 칩의 ×로 빼면 좌측 체크가 풀린다.

## §5 비용 계약 (★ 선행 조건의 이행부) — **이 절이 이 스펙에서 가장 안 지켜지기 쉬운 곳이다**

"좌측 조직도 상주"는 89건 명단이 **탭 전환형에서 상주형으로 바뀐다**는 뜻이다. 잘못 만들면 교사 전원에게 상시 비용원이 생긴다.

1. **`onSnapshot` 금지.** 좌측 조직도는 `getClientCache("teacher_profiles:all")` → 미스일 때만 `getDocs` 1회 경로만 쓴다. **이 화면 파일에서 `onSnapshot`이 0건인 것이 검증 항목이다.**
2. **GWS 실명·재직 필터는 `users:all` 프리페치 캐시를 재사용한다.** `/api/workspace/*` 추가 호출 금지.
3. **첫 화면이 아니다**(전제 3) — 안 쓰는 교사에게는 읽기 0.
4. **캐시 TTL을 숫자로 넘기지 않는다.** 현재 5곳 전부 `setClientCache(key, data, 5*60*1000)`처럼 TTL을 명시 전달하는데, 그 때문에 **절약 모드의 TTL 연장 손잡이가 명단 읽기에는 걸리지 않는다**(`setClientCacheDefaultTtl`은 기본값만 바꾼다). 추출할 공용 로더는 `setClientCache(key, data)`로 **기본 TTL을 쓴다** — 평시 5분으로 동일하고, 절약 모드에서만 자동으로 늘어난다.
5. **예상 읽기**: 화면 진입 1회 = 최대 89 reads, 5분 내 재진입 0. 조직도·쪽지 쓰기·업무 픽커와 **같은 캐시 키를 공유**하므로 실효 비용은 그보다 낮다.
6. **[개정 2026-08-19] 활성 탭만 구독한다.** 흡수로 목록이 5개가 됐다(받은 쪽지·보낸 쪽지·즐겨찾기·내 할 일·보낸 업무). **다섯을 한꺼번에 구독하면 화면 하나가 기존 두 메뉴를 합친 것보다 비싸진다.** 보이지 않는 탭의 `onSnapshot`은 붙이지 않고, 탭을 떠나면 해제한다. 기존 `limit`(쪽지 50 · 업무 현황판 50 · 내 할 일 90일 창)은 그대로 승계한다.
7. **[개정 2026-08-19] 이 개정으로 명단 요약 문서(STATUS 작업 대기 2번)의 필요성이 올라갔다.** 초판에서 이 화면은 "보낼 때만 여는 곳"이었지만, 이제 **받은 쪽지·내 할 일을 보러 하루에도 여러 번 여는 곳**이 된다. 즉 89건 명단 읽기의 빈도가 초판 가정보다 훨씬 높다. **요약 문서를 화면보다 먼저 넣는 순서(STATUS 1 → 2 → 3)를 반드시 지킨다** — 뒤집으면 만들자마자 다시 뜯어야 한다.
