## §1 메뉴 이름과 배치

### §1-1 이름 — **「쪽지·업무 보내기」** (Claude 권고, 사용자 확인 1건)

사용자 제안은 `[메신저/업무]`였다. **의도(= 여기 들어가면 보낼 수 있다는 걸 이름만 보고 알아야 한다)는 전적으로 옳고 그대로 살린다.** 다만 「메신저」라는 단어만 바꾸기를 권한다.

- **이유**: 2026-08-11 사용자 확정으로 *"명칭은 화면 전체에서 **쪽지**로 통일(메신저·DM·푸시 등 금지)"* 규칙이 서 있다(memo_spec §4-1). 사이드바에 「쪽지」와 「메신저」가 나란히 있으면 **서로 다른 두 기능으로 읽힌다** — 이름 통일 규칙이 막으려던 바로 그 혼선이다.
- **대안이 의도를 더 잘 싣는다**: 「보내기」라는 동사가 들어가 목적이 더 분명하다. 「메신저/업무」는 명사 둘이라 여전히 "무엇을 하는 곳"인지는 안 말한다.
- 사용자가 그래도 「메신저」를 원하면 그렇게 간다 — **단어 하나라 언제 바꿔도 비용이 0이다.** 다만 그때는 memo_spec §4-1의 명칭 통일 규칙에 예외를 명시해 둔다(규칙과 화면이 어긋난 채 남지 않도록).

### §1-2 배치

`src/app/admin/page.tsx` — **「교직원 공통 도구」 섹션, 「홈」 바로 아래 / 「쪽지」 바로 위.**

```
교직원 공통 도구
  홈 (대시보드)
  쪽지·업무 보내기      ← 신설
  쪽지                  (받은/보낸함 — 현행 그대로)
  업무 관리             (내 할 일·현황판 — 현행 그대로)
  …
  교직원 조직도         (현행 그대로 — 승인 대기·수동 배치·트리 뷰)
```

**순서 근거**: 이 화면은 *보내는* 곳이고 「쪽지」·「업무 관리」는 *결과를 보는* 곳이다. 실무 순서(보낸다 → 확인한다)와 메뉴 순서를 맞춘다.

**구현 접점 3곳** (page.tsx는 배열이 아니라 JSX 하드코딩이라 셋을 함께 고쳐야 한다):
1. `MenuType`에 `"send_hub"` 추가 (L60 부근)
2. `renderContent()` switch에 `case "send_hub"` 추가 (L256~)
3. 사이드바 JSX에 버튼 추가 (L617 「홈」과 L630 「쪽지」 사이)

컴포넌트는 기존 관례대로 `next/dynamic` 지연 로드. 전 교직원 노출(super_admin 전용 아님).

## §2 화면 골격 — 2단 고정

```
┌──────────────┬────────────────────────────────────────────┐
│ 좌 320px     │ 우 (나머지)                                │
│ 조직도 상주  │ 작업 영역                                  │
│              │                                            │
│ [이름 검색]  │  ┌ 담긴 사람 칩 줄 (항상 표시) ─────────┐  │
│              │  │ 홍길동 ×  김철수 ×  … 총 N명  [비우기]│  │
│ ▾ 교무기획부 │  └──────────────────────────────────────┘  │
│   □ 홍길동   │                                            │
│   □ 김철수   │   ⓐ 대기 상태  또는  ⓑ 작성 상태          │
│ ▸ 학생부     │                                            │
│ …            │                                            │
│              │                                            │
│ N명 담김     │                                            │
└──────────────┴────────────────────────────────────────────┘
```

- 좌·우 각각 독립 스크롤. 좌측 폭 고정(320px), 우측 가변.
- **최소 폭 1024px.** 미만에서는 화면을 렌더하지 않고 "이 화면은 컴퓨터에서 사용해 주세요" 한 줄만 — 반응형 축소판을 만들지 않는다(전제 2).

### §2-1 좌측 — 조직도 (상주)

| 요소 | 동작 |
|---|---|
| 검색창 | **이름만** 로컬 필터. 서버 호출 0. 입력 중에는 트리가 일치 항목만 남고 부서는 자동 펼침 |
| 부서 헤더 | 이름 클릭 = 접기/펼치기 · **체크박스 = 그 부서 전원 담기/빼기** (`indeterminate` 지원) · 우측에 인원수 |
| 사람 행 | **체크박스 = 담기/빼기** · **이름 클릭 = 정보 카드**(§2-2) |
| 하단 고정줄 | `N명 담김` + [비우기] |
| 초기 펼침 | **내 소속 부서만** 펼치고 나머지는 접는다 (memo_spec §11-2 승계) |

**제스처 분리가 이 화면의 핵심 규약이다** — 체크는 담기, 이름 클릭은 보기. 더블클릭 같은 숨은 조작은 만들지 않는다(배워야 알 수 있는 조작은 채택 논리에 반한다).

### §2-2 정보 카드 — 좌측 위로 뜨는 팝오버

이름을 클릭하면 좌측 패널 위에 팝오버(폭 ~280px)가 뜬다. **우측 작업 영역을 뺏지 않는다** — 작성 중에도 내선번호를 확인할 수 있어야 하기 때문이다.

- 내용: 이름 · 부서(복수면 전부) · 직위 · 담임이면 `N학년 M반` · **내선번호** · 부서장 표시
- 버튼: [담기] (이미 담겼으면 [빼기])
- 바깥 클릭 또는 Esc로 닫힘

> 이 카드가 로드맵 피드백 16번(「교직원 조직도」를 관리자 전용으로 → 철회)이 짚은 **내선 등 정보 열람 수요**를 흡수한다.

### §2-3 우측 ⓐ 대기 상태 (담긴 사람 0명 또는 행동 미선택)

- 안내 한 줄: "왼쪽에서 받을 사람을 고르세요."
- 큰 버튼 2개: **[쪽지 보내기]** / **[업무 등록]** — 담긴 사람이 0명이면 비활성.

### §2-4 우측 ⓑ 작성 상태

**이 화면의 실제 이득이 여기서 나온다.** 기존 [쪽지 쓰기]는 ①수신자 → ②작성 2단계 모달이라, 작성 중에 사람을 바꾸려면 ①로 돌아가야 한다. 여기서는 **좌측이 ①을 상시 수행하므로 작성 폼은 처음부터 ② 상태로 뜨고, 작성 중에도 좌측 체크로 대상이 즉시 바뀐다.**

| | 쪽지 | 업무 |
|---|---|---|
| 입력 | 제목 · 내용(서식 재사용) · 링크 · 첨부 | 업무명 · 기한(날짜+시각) · 확인형/제출형 · 양식 첨부 · 지시 내용 |
| 보내기 | `POST /api/memo {action:"send"}` **1회** | `{action:"prepare"}` → `{action:"send", taskId}` **2회** |
| 버튼 라벨 | `N명에게 보내기` (memo_spec §11-1 — 확인창 없음) | `N명에게 보내기` |
| 발송 후 | 폼·담긴 사람 초기화 → ⓐ 대기 상태 + "보냈습니다" 안내 + [보낸쪽지함 열기] | 동일 + [보낸 업무 현황판 열기] |

- **[쪽지 보내기] ↔ [업무 등록] 전환 시 담긴 사람은 유지된다.** (이게 "사람 먼저 → 행동 선택"의 요점이다.) 작성하던 본문은 전환 시 경고 없이 버리지 않는다 — 내용이 있으면 확인 1회.
- 발송 후 이동은 기존 크로스 네비를 쓴다: `window.dispatchEvent(new CustomEvent("admin_navigate", { detail: { menu: "memo" } }))` (page.tsx L100~).

## §3 담긴 사람(선택 상태) 규약

- **자료구조 = `Set<string>` (소문자 이메일).** 기존 두 픽커와 동일. uid 아님.
- **중복 제거는 이메일 기준.** 한 사람이 여러 부서에 속하므로 부서 전체 선택이 겹치면 1명으로 센다(서버도 재차 제거).
- **명단 = 소속이 등록된 교직원만** (현재 89건 중 81건). `noDept` 계정·소속 빈 계정은 **목록에 뜨지 않는다** — 받아도 열지 못하는 사람을 고를 수 있으면 안 된다(memo_spec §11-2).
- **이름만 보여준다. 이메일은 화면 어디에도 쓰지 않는다.** 동명이인은 memo_spec §11-5 규칙(모호할 때만 부서 부제).
- **수명**: 메뉴를 벗어나면 비운다. `sessionStorage`에 영속시키지 않는다 — 다음 접속에 남은 대상이 오발송으로 이어진다. 단 **작성 중 내용이 있는 상태로 이탈하면 확인 1회**(피드백 35번 「담기 이탈 경고」 계열).
- 우측 칩 줄과 좌측 체크는 **양방향 동기화**. 칩의 ×로 빼면 좌측 체크가 풀린다.

## §4 발신 자격

- 조건 = **내 `teacher_profiles.departments`가 비어 있지 않을 것.** 쪽지·업무 모두 같은 기준(memo_spec 게이트 / phase8_tasks_spec §4).
- 자격이 없으면 화면은 열리되 **조직도 열람만 되고 [쪽지 보내기]·[업무 등록]이 비활성**, 안내 한 줄("조직 정보가 등록되면 보낼 수 있습니다" 수준 — 「내 조직 정보 신청」으로 가는 링크를 단다. 나열만 하고 출구가 없는 화면 금지 — AGENTS.md 화면 문구 규칙 5).

> **곁가지 지적(이 스펙의 범위 밖, 별건)**: `TasksSection`에는 이 자격 게이트가 없다(쪽지에만 있음). 허브는 자체적으로 게이트를 걸지만, 기존 업무 화면의 게이트 부재는 따로 판단이 필요하다.

## §5 비용 계약 (★ 선행 조건의 이행부) — **이 절이 이 스펙에서 가장 안 지켜지기 쉬운 곳이다**

"좌측 조직도 상주"는 89건 명단이 **탭 전환형에서 상주형으로 바뀐다**는 뜻이다. 잘못 만들면 교사 전원에게 상시 비용원이 생긴다.

1. **`onSnapshot` 금지.** 좌측 조직도는 `getClientCache("teacher_profiles:all")` → 미스일 때만 `getDocs` 1회 경로만 쓴다. **이 화면 파일에서 `onSnapshot`이 0건인 것이 검증 항목이다.**
2. **GWS 실명·재직 필터는 `users:all` 프리페치 캐시를 재사용한다.** `/api/workspace/*` 추가 호출 금지.
3. **첫 화면이 아니다**(전제 3) — 안 쓰는 교사에게는 읽기 0.
4. **캐시 TTL을 숫자로 넘기지 않는다.** 현재 5곳 전부 `setClientCache(key, data, 5*60*1000)`처럼 TTL을 명시 전달하는데, 그 때문에 **절약 모드의 TTL 연장 손잡이가 명단 읽기에는 걸리지 않는다**(`setClientCacheDefaultTtl`은 기본값만 바꾼다). 추출할 공용 로더는 `setClientCache(key, data)`로 **기본 TTL을 쓴다** — 평시 5분으로 동일하고, 절약 모드에서만 자동으로 늘어난다.
5. **예상 읽기**: 화면 진입 1회 = 최대 89 reads, 5분 내 재진입 0. 조직도·쪽지 쓰기·업무 픽커와 **같은 캐시 키를 공유**하므로 실효 비용은 그보다 낮다.

## §6 선행 리팩터 — 허브를 만들기 **전에** 한다 (Antigravity)
