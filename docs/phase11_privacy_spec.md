# Phase 11 스펙 — 개인정보 처리 고지·최초 로그인 확인 체계

> 2026-08-05 Claude 작성. 단일 원본: [`personal_data_inventory.md`](../personal_data_inventory.md) (새 컬렉션 추가 시 그 표부터 갱신하고 이 문안을 파생 갱신한다).

## 0. 원칙 (로드맵 §Phase 11 결정 재확인)

- **고지 중심, 동의 최소화.** 학교가 법령상 사무(학적 관리, 생활지도, 계정 관리 등)로 처리하는 개인정보는 별도 '동의'의 대상이 아니라 처리 내용을 알리는 '고지'의 대상이다. 불필요한 동의를 받으면 "동의를 거부하면 처리하지 않는가"라는 잘못된 기대와 철회 문제를 만든다 — 과잉 동의는 오히려 리스크.
- 현재 기능 범위에서 법적으로 '동의'가 필요한 항목은 **없음** → 최초 로그인 화면은 **"고지 확인(읽었음)"** 화면이다. 버튼 문구도 "동의합니다"가 아니라 **"확인했습니다"**.
- ⚠️ 문안과 법적 판단의 최종본은 학교 개인정보 담당(행정실·교육청 지침) 검토를 권장한다. 이 스펙의 문안은 검토용 초안이다.
- **플랫폼 확장 상시 전제 (2026-08-05 사용자 지시)**: 이 시스템은 계속 기능이 추가되는 중이다. 새 기능이 개인정보 처리를 추가하면 ① `personal_data_inventory.md` 갱신 → ② 문안 파생 갱신 → ③ `POLICY_VERSION` 상향 → 전 사용자 자동 재고지의 순서를 따른다. 법적으로 동의가 필요한 항목이 새로 생기면 그 시점에 별도 동의 절차를 추가한다(고지 확인과 동의는 화면·기록 모두 구분). 이 가능성 자체를 문안에도 명시한다(§5).

## 1. 산출물 A — 개인정보 처리 안내 페이지 `/privacy`

- 공개 페이지(로그인 불필요, 개인정보 미포함). 상단에 버전 표기(예: **v2026-08**)와 시행일.
- 교사용/학생용 두 섹션. 문안은 §5 초안을 그대로 사용 (개발 용어·컬렉션명 노출 금지 — 사용자 눈높이 표현 규칙).
- 표 형식: 무엇을 저장하나 / 왜 / 누가 볼 수 있나 / 언제까지.

## 2. 산출물 B — 최초 로그인 고지 확인 화면

- **버전 상수**: `src/lib/policy/version.ts`에 `export const POLICY_VERSION = "2026-08"`. 정책 개정 시 이 문자열을 올리면 전 사용자에게 자동 재고지된다.
- **트리거**: 로그인 후 `users/{uid}` 로드 시 `policyAck?.version !== POLICY_VERSION`이면 전면 고지 화면(닫기 불가, 스크롤 후 확인 버튼). 교사 화면(`/teacher`)과 학생 포털(`/student`) 공통. 역할(role)에 따라 교사용/학생용 문안 표시.
- **확인 기록**: `POST /api/policy/ack` (본문 없음, 인증 토큰의 본인만 처리) —
  1. `users/{uid}.policyAck = { version, ackedAt }` 갱신 (최신 상태 판별용)
  2. `policy_acks/{uid}_{version}` 이력 문서 생성: `{ uid, email, role, version, ackedAt }` (개정 이력 증빙용, 서버만 쓰기)
- **firestore.rules**: `policy_acks` 클라이언트 전면 차단(읽기·쓰기 모두 서버 경유) — `graduation_consents`·생활지도 컬렉션과 동일 패턴.

## 3. 산출물 C — 관리자 고지 확인 이력 조회

- 관리자 화면 서브 탭 "개인정보 고지 현황": 현재 버전 기준 확인자 수 / **미확인자 목록**(이름·이메일·역할), 버전별 이력.
- 조회는 서버 API(`/api/policy/ack`의 `action: "list"` 등) 경유. 학생 이메일이 포함되므로 **수퍼어드민 한정**.

## 4. 산출물 D — records API studentEmail 합성 버그 수정 (서버, Claude 직접)

- 현행: 기록 생성 시 `${학번}@${도메인}`으로 이메일을 합성 — 학생 실이메일은 입학년도 기반(예: 26027@)이라 **실존하지 않는 주소가 민감 기록·감사 로그에 저장**된다 (8/5 이관 때 발견, 이관분 173건은 실이메일로 정정 저장 완료 — 소급 불필요).

## 5. 문안 초안 (v2026-08)

> **어조 확정 (2026-08-05 사용자 지시)**: 진지한 문서다 — **이모지·장식 금지**, 구어체("누가 볼 수 있나", "알려드립니다", "여쭙습니다" 류) 금지, **간결한 격식 문어체**("저장 항목/처리 목적/열람 범위/보유 기간", "~고지합니다")로 통일. **학생용도 아기자기한 카드·색상 없이 동일 격식**. **법률 용어("법령", "법정", 개별 법률명 인용 등)는 사용자 노출 문안에서 쓰지 않는다** — 위압감을 주지 않도록 "학교 업무 수행에 필요한 최소한의 범위에서만 처리" 같은 눈높이 표현으로 대체(같은 날 사용자 지시. 고지 중심 설계의 법적 근거 자체는 본 스펙 §0에만 남긴다). 확정 문안의 단일 원본은 구현체(`/privacy`·고지 모달·로그인 박스)이며 아래 초안은 역사 기록.

### 5-1. 교사용

> **효명고등학교 관리 시스템 개인정보 처리 안내 (교직원용)**
>
> 이 시스템은 효명고등학교가 학교 업무(학생 계정 관리, 생활지도, 시간표 운영 등)를 처리하기 위해 운영합니다. 학교의 법령상 사무 수행을 위한 것으로, 처리하는 정보와 방법을 아래와 같이 알려드립니다.
>
> | 무엇을 저장하나 | 왜 | 누가 볼 수 있나 | 언제까지 |
> |---|---|---|---|
> | 선생님의 학교 이메일·이름·담당 업무 | 로그인과 권한 구분, 교직원 조직도 | 교직원 | 전출·퇴직 처리 시 삭제 |
> | 학생의 학교 이메일·이름·학번 | 계정 관리, 명렬표, 수업 도구 정리 | 교직원 | 졸업·전출 계정 정리 시 함께 삭제 |
> | 학생 생활지도 기록 (지도 항목·날짜·메모) | 학생 생활지도 (민감 정보로 취급) | 담임은 자기 반, 그 외에는 별도 권한을 받은 선생님만 | 졸업·제적 시 파기 |
> | 시간표·수업 교환 신청 내역 | 시간표 운영 | 교직원 | 학년도 경과 후 정리 |
> | 시스템 사용 기록 (누가 언제 무슨 작업을 했는지) | 안전한 운영 확인(감사) | 교직원 열람, 수정·삭제 불가 | 별도 방침으로 보존 |
>
> - 주민등록번호, 전화번호, 주소, 학부모 정보는 **저장하지 않습니다**.
> - 구글 계정 안의 메일·드라이브 원본은 이 시스템이 아니라 학교–Google 간 교육용 계약에 따라 관리됩니다.
> - **이 시스템은 계속 개발 중입니다.** 새로운 기능으로 처리하는 정보가 늘어나면 이 안내를 개정하고 로그인 시 다시 알려드립니다. 법적으로 동의가 필요한 항목이 생기는 경우에는 그때 별도로 동의를 여쭙습니다.
> - 문의: 정보부 (관리자 계정 운영 부서)

### 5-2. 학생용

> **효명고 관리 시스템이 여러분의 정보를 다루는 방법**
>
> 이 시스템은 학교가 여러분의 구글 계정과 학교 생활을 관리하기 위해 운영합니다.
>
> - **저장하는 것**: 학교 이메일, 이름, 학번. 생활지도가 있었던 경우 그 기록(담당 선생님만 볼 수 있습니다). 졸업할 때 계정 정리를 위한 안내 확인 기록.
> - **저장하지 않는 것**: 주민등록번호, 전화번호, 집 주소, 부모님 정보.
> - **언제까지**: 졸업하거나 전학 가면 계정과 함께 정리됩니다.
> - 이 시스템은 계속 새로운 기능이 더해지고 있습니다. 다루는 정보가 달라지면 이 안내를 고쳐서 로그인할 때 다시 알려주고, 여러분의 동의가 필요한 일이 생기면 그때 따로 물어봅니다.
> - 궁금한 점은 담임 선생님이나 정보부에 물어보세요.
