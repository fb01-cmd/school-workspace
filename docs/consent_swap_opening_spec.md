## 0. 설계 원칙 (사용자 확정 반영)

1. **차단 → 양해 게이트**: 물리적으로 불가능한 교체(겹강·가상 교사)만 하드 차단으로 남기고, **당사자 양해로 풀리는 충돌(특별실·구장)은 "조율 필요 후보"로 노출**한다. 시스템이 실무보다 엄격해서 실무가 시스템 밖으로 나가는 상황(체육 교체 전멸 실측, project_notes 2026-08-08)을 없애는 것이 목적.
2. **양해 기록이 책임 보호의 핵심**: 조율 필요 후보의 신청에는 "양해 받음" 확인이 필수이고, 누구에게·언제 양해를 받았는지가 **불변 원장(swap_requests)에 남는다**. 일과계는 이 기록을 보고 승인한다 — 조율 책임은 교사, 확정 책임은 일과계로 분리 유지.
3. **탐색은 모두에게, 확정 권한은 역할대로**: 공강 탐색·체인 탐색을 일반 교사에 개방하되, 교사는 신청→승인 경로만, 일과계는 직권 즉시 반영. 기존 상태 기계(§5)·승인 트랜잭션은 불변.
4. **기존 동작 보존**: 모든 신설 기능은 opt-in 파라미터/신규 액션 — 옵션 미지정 시 현행 엔진·체인·직권 경로의 출력이 바이트 단위로 동일해야 한다.

## 2. 축 ⓐ — 후보 이원화 (깨끗한 후보 + 조율 필요 후보)

### 2-1. 대상 (1차)

**특별실(§F) 충돌만.** 내 수업의 room이 목표 슬롯에서 점유돼 있거나, 상대 수업의 room이 내 슬롯에서 점유돼 있는 후보 — 현재 무언 제외되는 두 `isRoomFree` 검사가 정확한 전환 지점. 다른 하드 제외는 §1 표대로 유지(확장은 실수요 신호 후).

### 2-2. 엔진 (swap.ts — Claude 구현)

- `findSwapCandidates`·`findCrossSwapCandidates`에 옵션 `opts?: { includeCoordination?: boolean }` 추가. **기본 false = 현행 출력 불변** (체인 탐색·기존 호출 전부 자동 보존).
- true일 때: room 충돌 후보를 버리지 않고 후보에 포함하되 다음 필드를 채운다:

```typescript
coordination?: {
  kind: "venue";                       // 1차는 특별실만 — 확장 여지용 판별자
  conflicts: Array<{
    roomName: string;                  // 겹치는 특별실 (예: "탁구장")
    slot: { weekId: string; day: number; period: number };  // 충돌이 나는 슬롯
    occupants: Array<{                 // 그 슬롯에서 room을 점유 중인 수업 = 양해 필요 당사자
      grade: number; classNum: number;
      subjectName: string;
      teacherEmail: string; teacherName: string;
    }>;
  }>;
}
```

- 산출 방법: `isRoomFree` 실패 시 `SlotIndex.roomUse`에서 점유 학급을 얻고, 해당 학급 그리드의 그 슬롯 lesson에서 과목·교사를 역참조(추가 Firestore 읽기 0 — 이미 로드된 합성본만 사용). 점유 수업의 교사가 가상(이메일 없음)이면 그 후보는 **조율 불가로 계속 하드 제외**(양해 당사자가 없음).
- 감점 계산·scope 분류는 깨끗한 후보와 동일 적용. 정렬: **깨끗한 후보 전체 → 조율 필요 후보 전체** 2단 정렬(각 단 안에서는 기존 정렬 유지). `coordination` 유무가 곧 구분자 — 별도 배열로 쪼개지 않는다(스냅샷·대조 로직 단순 유지).

### 2-3. API·재검증 (server.ts — Claude 구현)

- `computeCandidates`/`computeCandidatesAllWeeks`에 옵션 전달. requests `candidates`·`candidates_all`, manage `direct_candidates`·`direct_candidates_all`은 **항상 켠다**(교사·일과계 화면 모두 조율 필요 후보를 봄 — §14-4 동등성 원칙). **체인 탐색은 켜지 않는다** — 체인 단계에 조율 필요 후보가 섞이면 양해 당사자가 눈덩이처럼 늘어 실무 성립 불가(1차 결정, 완화는 실수요 후).
- `createSwapRequest` 재검증: 매칭된 서버 계산 후보에 `coordination`이 있으면 → `params.consent.confirmed !== true`일 때 400 ("이 후보는 당사자 양해가 필요합니다. 양해를 받은 뒤 확인란을 체크해 주세요."). 스냅샷(`SwapCandidateSnapshot`)에 coordination 포함 저장.
- `approveSwapRequest` 재검증: includeCoordination 켜고 재계산 — 매칭 후보에 coordination이 있으면 request에 consent 기록이 있는지 확인(없으면 승인 실패 사유 반환). **승인 결과 특별실이 이중 점유된 합성본이 되는 것은 의도된 상태** — 장소 재조정(합반·교실 수업)은 오프라인 실행이고 시스템은 수업 배치만 기록한다. 이후 후보 계산에서 그 슬롯 room은 점유로 보이므로 3중 겹침은 자연 차단된다.
- `directCommit`(일과계 직권): 같은 규칙 — 조율 필요 후보 반영 시 `consent` 파라미터 필수(§14-4 동등성 — 일과계도 양해는 받아야 함).

## 3. 축 ⓓ — 양해 기록 (consent) 모델·워크플로

### 3-1. 원장 기록 (swap_requests — 불변)

```typescript
consent?: {
  confirmed: true;
  parties: Array<{ email: string; name: string }>;  // 서버가 coordination.occupants에서 도출 — 클라이언트 값 불신
  note?: string;                                     // 예: "체육관 합반으로 양해" (선택, 200자)
  confirmedAt: number;                               // 서버 시각
}
```

- **parties는 서버 도출** — 신청 body의 값은 무시하고 재계산된 coordination에서 뽑는다(AGENTS.md §5 이중 방어). note만 신청자 입력.
- 체인 신청(§4-3)에서는 parties = 체인 관련 교사 전원(아래 정의).

### 3-2. UI 흐름 (Antigravity 구현)

- **후보 표시**: 조율 필요 후보는 별도 섹션("🤝 양해가 필요한 후보")에 — 충돌 내용을 수신자 눈높이 문장으로("이 시간에 탁구장을 정동희 선생님(2-3 체Ⅱ)이 사용 중 — 장소 양보 양해가 필요합니다"). 개발 용어 금지 원칙 준수(“coordination”, “§F” 노출 금지).
- **신청 다이얼로그**: 조율 필요 후보 선택 시 양해 확인 단계 삽입 — 당사자 명단 표시 + "위 선생님들께 양해를 받았습니다" 체크(필수) + 메모(선택). 체크 없이는 제출 버튼 비활성 + 서버도 400(이중 방어).

  - ~~조율 당사자용 변형 카드~~ → **2026-08-11 폐기(사용자 확정, 수집 19)**. 카드는 "무슨 수업이 어떻게 교체되는지"를 한눈에 전달하는 **정보 수단**이지 양해를 구하는 행위 자체가 아니다 — 특별실 점유 교사와는 **직접 소통으로 조율**해야 하며 카드를 보내지 않는다. coordination이 있어도 카드는 항상 일반 교환 카드 + 겹침 경고로 렌더한다(§3-2d 피드백 1 "조율 방식 지시 금지"와 동일 원칙).
- **요청대장(일과계)**: 조율 필요 신청 카드에 "🤝 양해 확인됨" 배지 + 당사자·메모·확인 시각 표시. 승인 판단 근거가 원장에 있음을 보이는 것이 목적.
- **알림**: 승인 시 기존 수신자(신청자+맞교환 상대)에 **양해 당사자(parties)를 추가** — 자기 특별실 슬롯에 다른 수업이 들어오는 걸 당사자가 통지받아야 기록이 보호 장치로 완성된다. 발신자 규칙(hmnotice@) 불변.

### 3-2b. 마찰·시각 위계 보강 — v1.1 (2026-08-10 관리자 실기기 1차 피드백, 사용자 확정)

> 배경: ① 조율 후보(감점 2~3)가 부드러운 표시라, 깨끗한 후보의 높은 감점(예: 감점 7)이 오히려 더 위험해 보이는 **시각 위계 역전** ② 조율 후보가 경고 없이 그냥 눌러짐 — "원래 1차로 막혀 있던 것"이라는 성격이 전달되지 않음 ③ 직권 탭에서 양해 필수 체크가 담기 전(선택 시점)에 뜨는데, 양해 요청 카드는 담은 뒤에 생성됨 — 순서 모순.

1. **시각 위계**: 감점(품질)과 조율(장소 충돌)은 다른 축 — 색으로 위계를 분리한다. 조율 후보는 **감점 색보다 명확히 강한 경고 스타일**(빨간 계열·굵은 테두리, 라벨 "⚠️ 양해 필수")로 통일 — 인라인 그리드 셀(교사 포털)·후보 카드(직권 탭) 모두. 감점 후보의 기존 초록/주황/빨강(연한 톤)은 유지하되 조율 경고보다 약하게 보여야 한다.
2. **클릭 마찰(2단 진입)**: 조율 후보 클릭 시 즉시 선택/초안 저장하지 않는다 — 먼저 **경고 다이얼로그**(충돌 요지+양해 당사자 실명, "이 교환은 당사자 양해 없이는 반영할 수 없습니다. 그래도 검토하시겠습니까?" [취소]/[양해 전제로 검토]) → 진행 선택 시에만 기존 동작(직권: 후보 선택·사이드바 / 교사 포털: 초안 저장). 원래 하드 차단이던 것을 여는 만큼, 함부로 눌리지 않는 마찰을 명시적으로 둔다.
3. **양해 체크 위치 원칙 — "확정 직전"에만**: 양해 필수 체크박스는 시간표가 실제로 바뀌기 직전 단계에만 존재한다. 선택·담기·초안 저장 단계에서는 **정보 블록(충돌 내용·당사자)만** 표시.
   - 직권 탭: 사이드바에서 필수 체크 제거(정보만) → [담기]는 체크 없이 허용 → **[즉시 1건 반영] 클릭 시 양해 확인 다이얼로그**(체크+메모, 기존 confirm 대체) / 일괄 반영 모달은 현행 유지(이미 올바른 위치).
   - 교사 포털: 단건 즉시 신청 버튼 옆 체크(=확정 직전)·일괄 제출 모달·초안 단건 제출 다이얼로그는 현행 유지. 인라인 클릭(초안 저장)에는 2항의 경고만 추가.

### 3-2c. 교사 포털 후보 상호작용 개정 — 클릭=선택 (2026-08-10 일반 교사 실기기 1차 피드백, 사용자 확정)

> 배경: §14-2 v2.1의 "인라인 후보 클릭 = 즉시 초안 저장"은 호버 툴팁으로만 감점 사유를 보여줘 ① 모바일에서 사유 조회가 원천 불가 ② 클릭이 조회가 아니라 실행이라 확인 단계 부재 ③ 사이드바가 호버 후보에 종속돼 양해 체크박스로 마우스를 옮기는 동안 내용이 바뀌거나 사라짐(단건 신청의 양해 체크 도달 불가 — 상태 설계 버그). v2.1의 "클릭 상태가 그리드에 남는" 장점은 초안(점선 칸)이 이미 담당하므로 클릭=저장의 즉시성만 포기한다.

### 4-3. 체인 신청 — 신규 요청 타입 `chain`

체인 단계는 **다른 교사 명의의 수업 이동을 포함**하므로 기존 create(본인 수업 검증)로는 신청이 불가능 — 실측으로 확인된 구조 공백. 신규 타입으로 해소한다:

- **모델**: `SwapRequest.type = "chain"` 확장 + `chainSteps: ChainStepItem[]`(서버 재계산 스냅샷, 2~3단계). source = 신청자 본인의 원 수업(1단계 소스), candidate = 최종 목적지 요약(사람용). 상태 기계·중복 차단(같은 소스 셀 PENDING)·취소 규칙 전부 기존과 동일.
- **생성 검증**: 신청자 본인이 1단계(또는 이동 대상 수업)의 담당자인지 확인 → `computeChainSearch` 재실행 → 제출된 체인과 단계열이 일치하는 결과가 존재해야 성립(후보 위조 차단 — create 재검증과 같은 정신). **consent 필수**: parties = 체인의 전 관련 교사(각 단계의 counterpart + 단계 소스 담당자 중 신청자 본인 제외) — 서버가 재계산 결과에서 도출. 양해 없이 다인 체인 신청 불가.
- **승인 (원자)**: 승인 트랜잭션에서 전 단계를 순서대로 재검증(가상 적용 누적 — computeChainSearch의 synthWith 로직 재사용) 후 **전 단계 change를 단일 트랜잭션으로 일괄 커밋**. 부분 성공 금지 — 체인은 단계 의존적이라 중간까지만 실행되면 시간표가 어정쩡한 상태로 남는다(직권 batch의 부분 성공 원칙과 다른 이유). 한 단계라도 재검증 실패 시 전체 승인 실패 + 실패 단계 사유 반환.
- **revert**: 체인 승인이 만든 change들은 공통 `chainRequestId`로 연결 — **체인 단위로만 취소**(교차 주 exchangeId 원자 취소 패턴 재사용).
- **알림**: 승인 시 신청자 + 전 관련 교사(parties와 동일 집합). 신청 생성 시 일과계 알림은 기존 규약.
- **일과계 직권 체인은 현행 유지**: 담기(pendingItems)→direct_commit_batch 경로 그대로 — 교사용 원자 승인과 별개(직권은 일과계가 화면에서 결과를 즉시 확인하므로 부분 성공+사유 표기가 낫다는 기존 결정 유지).

- **연산 정의**: 동시수업 그룹 G(SimulGroup — grade, classNums, subjectNames, slots)의 슬롯 (d₁,p₁) → (d₂,p₂) 이동. 성립 조건:
  ① G의 담당 교사 전원이 (d₂,p₂) 공강 — **주의: 이들은 `isBlockTeacher` 판정 대상이므로 기존 엔진 경로 재사용 불가.** 그룹 명시 이동 전용 엔진 `findSimulGroupMoveCandidates`를 신설하고, 블록 판정을 "이 그룹 자신의 동시 수업"에 한해 면제한다.
  ② 묶인 전 반(classNums)의 (d₂,p₂) 수업이 전부 "치울 수 있는 수업"(하드 제외 아님) ∧ 그 담당 교사 전원이 (d₁,p₁) 공강 — 즉 **반별 맞교환 n건으로 분해 가능**할 것.
  ③ 특별실: G의 room 요구가 (d₂,p₂)에서, 상대 수업들의 room이 (d₁,p₁)에서 성립(§2 조율 필요 분류 동일 적용).
- **change 표현 = 반별 swap n건 + 공통 `simulMoveId`** — 합성기(synthesizeWeeklyGrids) 무수정으로 표현 가능(교차 주 exchangeId 2문서 패턴의 일반화). revert는 simulMoveId 단위 원자 취소.
- **대상 슬롯이 전 반 공통 빈 교시**면 상대 없는 단순 이동(반별 이동 change) — 조건 ②가 공집합으로 자연 성립.
- **1차는 일과계 직권 전용**(direct 흐름 확장) — 상대 교사가 여러 명이라 양해 부담이 크고, 실사례도 일과계 개입 케이스. 양해 기록은 §3 모델 그대로(parties = 치워지는 수업 교사 전원 + G 담당 교사 전원). 교사 개방은 운영 후 판단.
- **UI**: 이동수업 관리 탭(SimulGroupTab)에서 그룹 선택 → 슬롯 선택 → 이동 가능 교시 하이라이트 → 확인 다이얼로그(치워지는 수업 목록 명시) → 양해 확인 → 반영.

## 6. 구현 순서·분업

| Phase | 내용 | 담당 | 비고 |
|---|---|---|---|
| **1** | ⓐ 엔진 이원화(includeCoordination) + ⓓ consent 모델·create/approve/direct 검증·알림 수신자 확장 | **Claude** (엔진·검증 = 위험 지점) | 체육 교체 전멸이 현재 실무 pain — 최우선 |
| **1** | 조율 필요 후보 섹션·양해 확인 다이얼로그·양해 카드 변형·요청대장 배지 | **Antigravity** | Claude 서버부 완료 후 |
| **2** | ⓑ requests `chain_search` + `chain` 신청 타입·원자 승인·revert | **Claude** | 트랜잭션·권한 = 위험 지점 |
| **2** | 공강 탐색 교사 포털 노출(추출 재사용) + 교사 체인 UX | **Antigravity** | 공강 UI는 서버 무변경이라 즉시 착수 가능 |
| **3** | ⓒ 통 이동 엔진·simulMoveId·직권 UI | Claude(엔진·커밋) + Antigravity(UI) | 착수 시점 사용자 판단 (9c와 조율) |

- 각 Phase 완료 시 기존 규약대로 Claude 표적 검수(엔진 출력 불변 검증 — 옵션 꺼짐 경로 diff 0 확인 포함) 후 사용자 push 승인.
- 검수 고정 항목 추가: **coordination·consent 필드가 정규화 조립(loadTimetableSettings 류)에 걸리는 신규 설정 필드는 없음** — swap_requests·후보 응답에만 존재. 다만 SwapCandidateSnapshot 소비처(요청대장·NEIS 목록·카드)가 신규 필드를 만나도 깨지지 않는지 확인.

## 7. 명시적 범위 제외 (v1)

- 특별실 외 충돌의 조율 후보화(복수교사·동시수업 단일 반 등) — 실수요 신호 후.
- 체인 탐색에 조율 필요 후보 포함 — 양해 눈덩이 방지(§2-3).
- 플랫폼 내 동의 수집(§13-3) — 오픈 게이트·인앱 알림 전제 불변.
- 통 이동의 교사 개방·교차 주 통 이동.
- 양해의 사후 검증(당사자에게 확인 요청 발송 등) — 기록·통지까지만. 허위 기재는 승인 알림이 당사자에게 가는 구조로 자연 노출된다.
