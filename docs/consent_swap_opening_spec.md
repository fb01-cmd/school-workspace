## 0. 설계 원칙 (사용자 확정 반영)

1. **차단 → 양해 게이트**: 물리적으로 불가능한 교체(겹강·가상 교사)만 하드 차단으로 남기고, **당사자 양해로 풀리는 충돌(특별실·구장)은 "조율 필요 후보"로 노출**한다. 시스템이 실무보다 엄격해서 실무가 시스템 밖으로 나가는 상황(체육 교체 전멸 실측, project_notes 2026-08-08)을 없애는 것이 목적.
2. **양해 기록이 책임 보호의 핵심**: 조율 필요 후보의 신청에는 "양해 받음" 확인이 필수이고, 누구에게·언제 양해를 받았는지가 **불변 원장(swap_requests)에 남는다**. 일과계는 이 기록을 보고 승인한다 — 조율 책임은 교사, 확정 책임은 일과계로 분리 유지.
3. **탐색은 모두에게, 확정 권한은 역할대로**: 공강 탐색·체인 탐색을 일반 교사에 개방하되, 교사는 신청→승인 경로만, 일과계는 직권 즉시 반영. 기존 상태 기계(§5)·승인 트랜잭션은 불변.
4. **기존 동작 보존**: 모든 신설 기능은 opt-in 파라미터/신규 액션 — 옵션 미지정 시 현행 엔진·체인·직권 경로의 출력이 바이트 단위로 동일해야 한다.

## 2. 축 ⓐ — 후보 이원화 (깨끗한 후보 + 조율 필요 후보)

### 2-1. 대상 (1차)

**특별실(§F) 충돌만.** 내 수업의 room이 목표 슬롯에서 점유돼 있거나, 상대 수업의 room이 내 슬롯에서 점유돼 있는 후보 — 현재 무언 제외되는 두 `isRoomFree` 검사가 정확한 전환 지점. 다른 하드 제외는 §1 표대로 유지(확장은 실수요 신호 후).

### 2-2. 엔진 (swap.ts — Claude 구현)

- `findSwapCandidates`·`findCrossSwapCandidates`에 옵션 `opts?: { includeCoordination?: boolean }` 추가. **기본 false = 현행 출력 불변** (체인 탐색·기존 호출 전부 자동 보존).
- true일 때: room 충돌 후보를 버리지 않고 후보에 포함하되 다음 필드를 채운다:

```typescript
coordination?: {
  kind: "venue";                       // 1차는 특별실만 — 확장 여지용 판별자
  conflicts: Array<{
    roomName: string;                  // 겹치는 특별실 (예: "탁구장")
    slot: { weekId: string; day: number; period: number };  // 충돌이 나는 슬롯
    occupants: Array<{                 // 그 슬롯에서 room을 점유 중인 수업 = 양해 필요 당사자
      grade: number; classNum: number;
      subjectName: string;
      teacherEmail: string; teacherName: string;
    }>;
  }>;
}
```

- 산출 방법: `isRoomFree` 실패 시 `SlotIndex.roomUse`에서 점유 학급을 얻고, 해당 학급 그리드의 그 슬롯 lesson에서 과목·교사를 역참조(추가 Firestore 읽기 0 — 이미 로드된 합성본만 사용). 점유 수업의 교사가 가상(이메일 없음)이면 그 후보는 **조율 불가로 계속 하드 제외**(양해 당사자가 없음).
- 감점 계산·scope 분류는 깨끗한 후보와 동일 적용. 정렬: **깨끗한 후보 전체 → 조율 필요 후보 전체** 2단 정렬(각 단 안에서는 기존 정렬 유지). `coordination` 유무가 곧 구분자 — 별도 배열로 쪼개지 않는다(스냅샷·대조 로직 단순 유지).

### 2-3. API·재검증 (server.ts — Claude 구현)

- `computeCandidates`/`computeCandidatesAllWeeks`에 옵션 전달. requests `candidates`·`candidates_all`, manage `direct_candidates`·`direct_candidates_all`은 **항상 켠다**(교사·일과계 화면 모두 조율 필요 후보를 봄 — §14-4 동등성 원칙). **체인 탐색은 켜지 않는다** — 체인 단계에 조율 필요 후보가 섞이면 양해 당사자가 눈덩이처럼 늘어 실무 성립 불가(1차 결정, 완화는 실수요 후).
- `createSwapRequest` 재검증: 매칭된 서버 계산 후보에 `coordination`이 있으면 → `params.consent.confirmed !== true`일 때 400 ("이 후보는 당사자 양해가 필요합니다. 양해를 받은 뒤 확인란을 체크해 주세요."). 스냅샷(`SwapCandidateSnapshot`)에 coordination 포함 저장.
- `approveSwapRequest` 재검증: includeCoordination 켜고 재계산 — 매칭 후보에 coordination이 있으면 request에 consent 기록이 있는지 확인(없으면 승인 실패 사유 반환). **승인 결과 특별실이 이중 점유된 합성본이 되는 것은 의도된 상태** — 장소 재조정(합반·교실 수업)은 오프라인 실행이고 시스템은 수업 배치만 기록한다. 이후 후보 계산에서 그 슬롯 room은 점유로 보이므로 3중 겹침은 자연 차단된다.
- `directCommit`(일과계 직권): 같은 규칙 — 조율 필요 후보 반영 시 `consent` 파라미터 필수(§14-4 동등성 — 일과계도 양해는 받아야 함).

## 3. 축 ⓓ — 양해 기록 (consent) 모델·워크플로

```typescript
consent?: {
  confirmed: true;
  parties: Array<{ email: string; name: string }>;  // 서버가 coordination.occupants에서 도출 — 클라이언트 값 불신

### 3-2. UI 흐름 (Antigravity 구현)

- **후보 표시**: 조율 필요 후보는 별도 섹션("🤝 양해가 필요한 후보")에 — 충돌 내용을 수신자 눈높이 문장으로("이 시간에 탁구장을 정동희 선생님(2-3 체Ⅱ)이 사용 중 — 장소 양보 양해가 필요합니다"). 개발 용어 금지 원칙 준수(“coordination”, “§F” 노출 금지).

### 3-2b. 마찰·시각 위계 보강 — v1.1 (2026-08-10 관리자 실기기 1차 피드백, 사용자 확정)

> 배경: ① 조율 후보(감점 2~3)가 부드러운 표시라, 깨끗한 후보의 높은 감점(예: 감점 7)이 오히려 더 위험해 보이는 **시각 위계 역전** ② 조율 후보가 경고 없이 그냥 눌러짐 — "원래 1차로 막혀 있던 것"이라는 성격이 전달되지 않음 ③ 직권 탭에서 양해 필수 체크가 담기 전(선택 시점)에 뜨는데, 양해 요청 카드는 담은 뒤에 생성됨 — 순서 모순.

1. **시각 위계**: 감점(품질)과 조율(장소 충돌)은 다른 축 — 색으로 위계를 분리한다. 조율 후보는 **감점 색보다 명확히 강한 경고 스타일**(빨간 계열·굵은 테두리, 라벨 "⚠️ 양해 필수")로 통일 — 인라인 그리드 셀(교사 포털)·후보 카드(직권 탭) 모두. 감점 후보의 기존 초록/주황/빨강(연한 톤)은 유지하되 조율 경고보다 약하게 보여야 한다.
2. **클릭 마찰(2단 진입)**: 조율 후보 클릭 시 즉시 선택/초안 저장하지 않는다 — 먼저 **경고 다이얼로그**(충돌 요지+양해 당사자 실명, "이 교환은 당사자 양해 없이는 반영할 수 없습니다. 그래도 검토하시겠습니까?" [취소]/[양해 전제로 검토]) → 진행 선택 시에만 기존 동작(직권: 후보 선택·사이드바 / 교사 포털: 초안 저장). 원래 하드 차단이던 것을 여는 만큼, 함부로 눌리지 않는 마찰을 명시적으로 둔다.
3. **양해 체크 위치 원칙 — "확정 직전"에만**: 양해 필수 체크박스는 시간표가 실제로 바뀌기 직전 단계에만 존재한다. 선택·담기·초안 저장 단계에서는 **정보 블록(충돌 내용·당사자)만** 표시.
   - 직권 탭: 사이드바에서 필수 체크 제거(정보만) → [담기]는 체크 없이 허용 → **[즉시 1건 반영] 클릭 시 양해 확인 다이얼로그**(체크+메모, 기존 confirm 대체) / 일괄 반영 모달은 현행 유지(이미 올바른 위치).

### 4-3. 체인 신청 — 신규 요청 타입 `chain`

체인 단계는 **다른 교사 명의의 수업 이동을 포함**하므로 기존 create(본인 수업 검증)로는 신청이 불가능 — 실측으로 확인된 구조 공백. 신규 타입으로 해소한다:

- **모델**: `SwapRequest.type = "chain"` 확장 + `chainSteps: ChainStepItem[]`(서버 재계산 스냅샷, 2~3단계). source = 신청자 본인의 원 수업(1단계 소스), candidate = 최종 목적지 요약(사람용). 상태 기계·중복 차단(같은 소스 셀 PENDING)·취소 규칙 전부 기존과 동일.
- **생성 검증**: 신청자 본인이 1단계(또는 이동 대상 수업)의 담당자인지 확인 → `computeChainSearch` 재실행 → 제출된 체인과 단계열이 일치하는 결과가 존재해야 성립(후보 위조 차단 — create 재검증과 같은 정신). **consent 필수**: parties = 체인의 전 관련 교사(각 단계의 counterpart + 단계 소스 담당자 중 신청자 본인 제외) — 서버가 재계산 결과에서 도출. 양해 없이 다인 체인 신청 불가.
- **승인 (원자)**: 승인 트랜잭션에서 전 단계를 순서대로 재검증(가상 적용 누적 — computeChainSearch의 synthWith 로직 재사용) 후 **전 단계 change를 단일 트랜잭션으로 일괄 커밋**. 부분 성공 금지 — 체인은 단계 의존적이라 중간까지만 실행되면 시간표가 어정쩡한 상태로 남는다(직권 batch의 부분 성공 원칙과 다른 이유). 한 단계라도 재검증 실패 시 전체 승인 실패 + 실패 단계 사유 반환.
- **revert**: 체인 승인이 만든 change들은 공통 `chainRequestId`로 연결 — **체인 단위로만 취소**(교차 주 exchangeId 원자 취소 패턴 재사용).
- **알림**: 승인 시 신청자 + 전 관련 교사(parties와 동일 집합). 신청 생성 시 일과계 알림은 기존 규약.
- **일과계 직권 체인은 현행 유지**: 담기(pendingItems)→direct_commit_batch 경로 그대로 — 교사용 원자 승인과 별개(직권은 일과계가 화면에서 결과를 즉시 확인하므로 부분 성공+사유 표기가 낫다는 기존 결정 유지).

## 5. 축 ⓒ — 동시수업 묶음 통 이동 (모델 확장, 대형)

> 실사례(체육교사 통화 ②)로 수요 확인. 이 스펙에서 연산·모델을 확정하고, **구현은 Phase 3**(§6) — 착수 시점은 9c 일정과 함께 사용자 판단.

- **연산 정의**: 동시수업 그룹 G(SimulGroup — grade, classNums, subjectNames, slots)의 슬롯 (d₁,p₁) → (d₂,p₂) 이동. 성립 조건:
  ① G의 담당 교사 전원이 (d₂,p₂) 공강 — **주의: 이들은 `isBlockTeacher` 판정 대상이므로 기존 엔진 경로 재사용 불가.** 그룹 명시 이동 전용 엔진 `findSimulGroupMoveCandidates`를 신설하고, 블록 판정을 "이 그룹 자신의 동시 수업"에 한해 면제한다.
  ② 묶인 전 반(classNums)의 (d₂,p₂) 수업이 전부 "치울 수 있는 수업"(하드 제외 아님) ∧ 그 담당 교사 전원이 (d₁,p₁) 공강 — 즉 **반별 맞교환 n건으로 분해 가능**할 것.
  ③ 특별실: G의 room 요구가 (d₂,p₂)에서, 상대 수업들의 room이 (d₁,p₁)에서 성립(§2 조율 필요 분류 동일 적용).
- **change 표현 = 반별 swap n건 + 공통 `simulMoveId`** — 합성기(synthesizeWeeklyGrids) 무수정으로 표현 가능(교차 주 exchangeId 2문서 패턴의 일반화). revert는 simulMoveId 단위 원자 취소.
- **대상 슬롯이 전 반 공통 빈 교시**면 상대 없는 단순 이동(반별 이동 change) — 조건 ②가 공집합으로 자연 성립.
- **1차는 일과계 직권 전용**(direct 흐름 확장) — 상대 교사가 여러 명이라 양해 부담이 크고, 실사례도 일과계 개입 케이스. 양해 기록은 §3 모델 그대로(parties = 치워지는 수업 교사 전원 + G 담당 교사 전원). 교사 개방은 운영 후 판단.
- **UI**: 이동수업 관리 탭(SimulGroupTab)에서 그룹 선택 → 슬롯 선택 → 이동 가능 교시 하이라이트 → 확인 다이얼로그(치워지는 수업 목록 명시) → 양해 확인 → 반영.

### 5b-0. 실측 교정 2건 (§5 전제 수정 — 2026-08-15 코드 대조)

1. **"합성기 무수정" 불성립.** `applySwap`(weekly.ts)은 양쪽 슬롯 모두에서 lesson 실재를 요구한다(`findLesson` 실패 시 경고+건너뜀) — 대상 슬롯이 빈 학급의 "상대 없는 단순 이동"은 기존 swap change로 표현할 수 없다. **신규 ChangeType `"move"`가 필요**하며, 합성기(정방향·취소 역방향)·revert 재검증 분기·NEIS 평탄화가 함께 확장돼야 한다(§5b-1).
2. **`simulMoveId` 불요.** 직권 경로도 SwapRequest 문서를 만들고(`directCommit` 실측 — direct:true 신청 생성 후 즉시 승인) change에 `requestId`가 실린다. revert는 이미 **requestId 묶음 전량 취소**를 chain 타입에서 구현·검증 완료(LIFO 역순 오프셋 포함, `9d79ef0`) — 조건에 신청 타입 하나를 추가하는 것으로 충분하다. 신규 연결 필드 대신 **신청 타입 `"simul_move"`를 신설**해 기구현 패턴에 정렬한다.

### 5b-1. 모델 (types.ts·weekly.ts — Claude 구현)

- `ChangeType`에 `"move"` 추가 + `TimetableChange.move`:

  to: { day: number; period: number };

- `WeeklyLessonChange.type`에 `"move"` 추가 — 학생·교사 카드의 변경 셀 렌더(U8 sky 계열)는 type 무관 `changed` 존재로 이미 동작하나, 소비처 전수 확인은 §5b-6.

simulMove?: {
  groupId: string; label: string;         // SimulGroup 참조 + 사람용 라벨 스냅샷
  grade: number; classNums: number[];
  from: { day: number; period: number };
  to: { day: number; period: number };

  kind: "swap" | "move";

```

- `candidate`(SwapCandidateSnapshot)는 chain 패턴대로 사람용 요약만: targetDay/Period = to, counterpartName = 그룹 라벨, penalties = 반별 요약 문장. 상세는 simulMove가 원본.

### 5b-2. 엔진 `findSimulGroupMoveCandidates` (swap.ts 순수 함수 — Claude 구현)

- **입력**: `(grids, week, settings, group: SimulGroup, source: {day, period})`. 추가 Firestore 읽기 0 — 호출부가 이미 합성한 주간 그리드와 로드된 등록부만 사용(읽기 예산 규율).
- **소스 해석**: classNums 각 반의 (d₁,p₁) 셀에서 `lesson.simul === group.label`인 수업을 수집. 검증 — ⓐ 전 반에 그룹 수업 실재(누락 반 발견 시 후보 0 + 사유 반환: 등록부·그리드 불일치는 조용히 일부만 옮기면 안 됨) ⓑ 그 셀에 그룹 외 다른 lesson 혼재 시 동일하게 중단(데이터 이상). simul 스탬프는 기초 위치 기준이지만 swap 적용 시 lesson과 함께 이동하므로(실측), 앞선 교체가 있어도 합성본 탐지가 정확하다.
- **후보 열거**: 그 학년 요일별 운영 교시(`periodsForGradeDay`) 전수에서 ⓐ 소스 슬롯 ⓑ 그룹의 다른 현행 슬롯(자기 충돌) 제외.
- **반별 판정 (조건 ②의 구현)** — 각 반 c의 (d₂,p₂) 셀:
  - 빈 셀 → 그 반은 `kind: "move"` (상대 없음).
  - lessons 2개 이상 → 후보 전체 하드 제외.
  - 단일 lesson: `lesson.simul` 존재(타 그룹 포함) · 복수교사 · 가상 교사(이메일 없음) 중 하나면 하드 제외. 통과 시 `kind: "swap"` + counterpart 기록.
- **공강 판정은 "이동분 제거 후" 의미론** — 기존 `isTeacherFree`를 그대로 쓰면 안 되는 지점 2곳:
  - 그룹 담당 교사는 정의상 `isBlockTeacher` true(§5 ①) — 블록 판정을 **이 그룹 자신에 한해 면제**.
  - 상대 교사가 그룹 교사이기도 한 자기맞물림(같은 교사의 수업이 양방향으로 함께 움직이는 경우)은 성립 가능한데 소박한 점유 검사로는 탈락한다. 판정식: **(d₂,p₂) 검사 = 기존 점유 − 이번에 빠져나가는 상대 수업들의 교사 집합에 그룹 교사가 없을 것**, (d₁,p₁) 검사는 대칭(기존 점유 − 그룹 수업 교사 집합에 상대 교사가 없을 것).
- **특별실 (조건 ③)**: 그룹 수업의 `lesson.room`(VenueGroup 스탬프)이 (d₂,p₂)에서, 상대 수업 room이 (d₁,p₁)에서 — `isRoomFree` 실패 시 §2와 동일하게 `roomOccupants` 역참조로 조율 필요 분류(가상 점유는 하드 유지). 자기 학급 제외 판정 시 **이번 이동으로 비워지는 이동 반들의 점유도 제외**해야 한다(그룹이 쓰던 특별실을 그룹 자신이 따라가는 정상 케이스가 충돌로 오판되지 않도록).
- **감점**: 기존 함수 재사용 — 반별로 `classDuplicatePenalty`(그룹 과목 @ d₂ / 상대 과목 @ d₁) + `teacherDayPenalties`(그룹 교사=이동 방향, 상대 교사=역방향; 같은 요일이면 removePeriod 상쇄). 직권 전용 화면이므로 `thirdPerson` 실명 표기. score = 총합, 정렬 = 깨끗한 후보 → 조율 필요 후보 → score 오름차순(§2-2 규약).
- **연속시수 경고**: `group.consecutive`가 있고 소스 슬롯이 같은 요일 인접 그룹 슬롯과 짝을 이루고 있었는데 이동으로 깨지면 후보에 `warnings: string[]`로 눈높이 경고("이 그룹은 2시간 연속 수업으로 등록돼 있습니다 — 이동하면 연속이 끊어집니다"). **차단하지 않는다** — 직권 화면이고 실사례(체육 통화 ②)가 곧 예외 승인이므로 판단은 일과계 몫.

### 5b-3. 커밋 `commitSimulGroupMove` (server.ts — Claude 구현)

- **재계산 대조**: 커밋 직전 주간 재합성 → `findSimulGroupMoveCandidates` 재실행 → 요청된 (groupId, from, to)와 일치하는 후보가 존재해야 성립(후보 위조 차단 — create·chain_create 재검증과 같은 정신). steps는 **서버 재계산 값을 저장**(클라이언트 값 불신).
- **consent 필수 (§3 모델 그대로)**: `params.consent.confirmed !== true`면 400. parties 서버 도출 = **그룹 담당 교사 전원 ∪ 치워지는 상대 교사 전원 ∪ 특별실 조율 당사자(coordination.occupants)** − 중복. 상대·충돌이 없는 전 반 빈 교시 이동도 그룹 교사 전원이 당사자이므로 consent는 항상 필수(§5 결정 유지).
- **원장·커밋 (원자)**: SwapRequest(type "simul_move", direct: true, requesterEmail = 일과계 관리자, status APPROVED 즉시) + change 문서들(반별 swap 또는 move, 전부 같은 requestId, `appliedAt = now + i` 순서 보존)을 **단일 트랜잭션 일괄 커밋. 부분 성공 금지** — 반별 분해는 표현 형식일 뿐 연산은 묶음 하나다(반쯤 이동된 동시수업 그룹은 성립 불가 상태 — 체인 원자 승인과 같은 이유). reason은 기존 `validateReason` 규약.
- **revert**: `revertTimetableChange`의 requestId 묶음 확장 조건을 `type === "chain"`에서 `type === "chain" || type === "simul_move"`로 — 어느 change를 클릭해도 그룹 전량 LIFO 취소(기구현 재사용, 신규 로직 0).
- **알림**: 반영·취소 모두 수신자 = parties 전원(revert의 consent.parties 합류는 기구현이라 자동). 발신자 hmnotice@ 규약 불변. 문구는 반별 전개를 눈높이로("2학년 3·4·5반 화 3교시 일본어Ⅰ/중국어Ⅰ 수업이 목 5교시로 통째로 이동" + 치워진 수업 안내).
- 커밋 후 `bumpTimetableCacheVersion` + 감사 로그(action "simul_move_commit", 그룹·슬롯·양해 인원 요약) — 기존 규약.

### 5b-4. API (manage 라우트 전용 — 일과계 게이트 자동)

- `simul_move_candidates`: `{ weekId, groupId, source: {day, period} }` → `{ candidates }`. 후보에는 steps·coordination·warnings·score 동봉(UI가 하이라이트·다이얼로그를 이것만으로 구성).

3. **기존 출력 불변**: 옵션·신규 액션 미사용 경로의 엔진 출력 diff 0. `verify_chain_phase2.ts` 양식의 실데이터 검증 스크립트(알림 억제·원장 흔적 하드 삭제·합성 원복 대조) — 검증 항목: 반별 혼합(swap+move) 커밋, 자기맞물림 케이스, 원자성(중간 단계 위조 실패 시 change 0건), revert 전량 원복, parties 도출 정확성.

### 5c-8. 교차 주 통 이동 (2026-08-15 사용자 지시 — §7 v1 제외 항목 철회)

> *"이동 수업 묶음 이동 설마 같은 주에서만 구현되도록 만든 거 아니지??"*
>
> §7의 「교차 주 통 이동 제외」는 **사용자가 정한 것이 아니라 v1 축소 때 적어 둔 가정**이고, §5c 재설계에서 같은 목록의 「교사 개방」만 뒤집히고 이 항목은 재검토 없이 남아 있었다. **철회한다.**

**현행(제약 지점 3곳)**: `computeCandidates`가 `targetWeekId ≠ weekId`면 명시 거부 · `computeCandidatesAllWeeks`가 소스 주에만 후보를 채우고 나머지 주는 빈 배열 · 엔진 `findSimulGroupMoveCandidates`가 단일 주(grids·week·idx 하나)만 받는다.

1. **엔진 — 재작성 금지, 내부 일반화**: `findSimulGroupMoveCandidates`의 **시그니처·동작을 보존**하고(기존 호출부 4곳 무수정 = 회귀 관문), 본문을 `(srcGrids, srcWeek, tgtGrids, tgtWeek, …)`를 받는 내부 구현으로 옮긴 뒤 같은 주 호출은 **같은 객체를 두 번 넘겨** 통과시킨다. 신규 export `findCrossSimulGroupMoveCandidates`가 두 주를 받는다. **로직 두 벌 금지**(§5c-2와 같은 정신) + **AGENTS.md ①-1**(재작성 금지) 양쪽을 동시에 만족하는 유일한 형태.
   - 판정의 주 귀속: 그룹 교사 공강·목적지 셀·그룹 수업 특별실·학급 중복(목적지 과목) = **목적지 주**. 상대 교사 공강·상대 수업 특별실·학급 중복(상대 과목) = **소스 주**. 「이동분 제거 후 의미론」은 그대로 성립한다(그룹이 소스 주 슬롯을 비우고, 상대가 목적지 주 슬롯을 비운다).
   - **교차 주에는 같은-요일 상쇄가 없다**: `teacherDayPenalties`의 `removePeriod`와 `classDuplicatePenalty`의 제외 교시에서 `source.day === d2` 분기를 끈다(`findCrossSwapCandidates`가 `removePeriod=null`로 두는 것과 같은 이유).
   - 자기 슬롯 제외(`groupSlots`)는 **목적지 주** 기준, 연속시수 경고는 **소스 주** 기준으로 분리한다(같은 주면 두 집합이 일치해 기존 출력 불변).
2. **커밋**: 반별 change는 이미 `assembleSimulMoveChanges` 한 곳에서 조립된다 — 교차 주에서는 **그룹 수업 쪽 change는 소스 주, 상대 수업 쪽 change는 목적지 주**에 기록(교차 주 맞교환의 changeA/changeB 방향 규약 계승). 원자성·`requestId` 묶음·되돌리기 전량 취소는 **무변경으로 그대로 적용**된다.
3. **재검증**: 승인 시 재계산 대조가 두 주를 모두 재합성해야 한다(`steps` 서명 대조·양해 당사자 확장 검사는 그대로).
4. **범위 유지**: 다른 학기 주는 계속 금지(기존 `termId` 일치 규칙 계승).
5. **완료 판정**: ① 교사가 다른 주 교시로 묶음 이동을 신청해 승인·되돌리기까지 완주 ② 같은 주 후보 출력이 **바이트 동등**(회귀 0) ③ 단건 교체·체인·보강 출력 불변 ④ 두 주에 걸친 change가 원자 커밋·전량 원복.

## 5c. Phase 3 재설계 — 진입 전환 + 교사 주 경로 (2026-08-15 사용자 반려 → 확정)

> ⚠️ **먼저 §5c-7을 읽을 것.** 같은 날 사용자 지시로 설계가 한 번 더 단순해졌다 — 통 이동은 **별도 기능이 아니라 기존 「조율 필요 후보」의 종류 하나**로 편입된다. §5c-1~3의 별도 진입·별도 화면 서술은 §5c-7이 대체한다(권한·방어 결정 §5c-2·4·5는 그대로 유효).

> **§5b 구현은 반려됐다.** 엔진·커밋·모델은 전부 유효하나 **진입 설계가 틀렸다.** 이 절이 §5·§5b의 진입·권한 결정을 대체한다(엔진 §5b-2·커밋 §5b-3·모델 §5b-1은 그대로 계승).

### 5c-0. 무엇이 틀렸나 (사용자 반려 사유)

> *"구현 자체가 '묶여있는 수업을 기존으로 다른 곳으로 이동하기'야. 이게 아니지. 교사가 자신의 수업을 수요일 3교시로 이동하고 싶어. 근데 그 수업이 일본어야. 이런 경우 중국어 선생님까지 한꺼번에 이동시키는 로직을 같이 잡아서 총 소요 파악하고 양해대상 다 확인하고 고칠 땐 한번에 다 고치지. 사용자 입장에서 이렇게 만들면 못 써."*

1. **진입점 역전**: §5b-5는 "그룹 드롭다운 → 슬롯 선택"으로 만들었다. 그러나 현장의 사고 단위는 **"내 이 수업을 저기로"**이지 "이동수업 그룹 3번"이 아니다. **묶음 정보는 이미 수업 칸에 실려 있다**(`lesson.simul` 스탬프) — 사람이 고를 이유가 없다.
2. **막아 놓고 옆에 새 메뉴**: 현행은 묶음 수업 클릭을 두 곳에서 튕긴다(`server.ts` `resolveDirectSource`·`swap.ts` `resolveSourceLesson`). 옳은 구조는 **막힌 자리를 여는 것**이다.
3. **권한 전제 오류 — §5의 "1차 일과계 직권 전용" 폐기.** 사용자 확정 원칙: **"복잡할수록 일과계에게 넘기면 책임 전가다. 일과계가 특별히 더 할 수 있는 기능은 보강 정도."** §5가 "양해 대상이 여럿이라 부담이 크다"를 직권 전용의 근거로 삼은 것이 오판이다 — **부담이 크다는 것은 일과계에게 넘길 근거가 아니라 시스템이 그 부담을 줄일 근거다**(§5c-5).

### 5c-1. 진입 전환 — 수업을 클릭하면 시스템이 묶음을 펼친다

- **신규 서버 해석기 `resolveSimulMoveSource(grids, groups, slot, requesterEmail?)`**:
  - 입력 슬롯의 lesson에서 `simul` 라벨을 읽어 **그룹을 서버가 특정**한다(사람이 고르지 않는다). 라벨→그룹은 `(grade, label)` 일치로 찾고, 중복 일치 시 데이터 이상으로 중단.
  - `requesterEmail`이 주어지면 **소유 검증**: 그 교사가 이 슬롯의 그룹 수업 중 하나의 담당이어야 한다(실데이터 예: 2학년 제2외국어 밴드는 2-2반 일화=김진만, 2-3반 중화=이경호 — **어느 쪽이든 시작 가능**).
  - 반환: `{ group, source, groupTeachers }` 또는 눈높이 사유.
- **기존 두 해석기는 손대지 않는다** — `resolveDirectSource`·`resolveSourceLesson`의 simul 차단 분기는 **다른 경로(단건 교체·체인·보강)가 의존**하므로 그대로 둔다. 대신 **호출부에서** "simul이면 통 이동 경로로 분기"한다. 시그니처 무변경 = 기존 출력 불변(회귀 관문).
- **화면 문구**: 클릭 시 차단이 아니라 안내 — *"이 수업은 2-3반 중국어회화와 함께 움직입니다. 두 반을 한 번에 옮깁니다."* (개발 용어 금지, 그룹 라벨 대신 **무엇이 함께 움직이는지**를 쓴다.)

### 5c-2. 교사 신청 경로 (주 경로) — requests 라우트

- **액션 2종 신설**: `simul_move_candidates`(본인 소유 검증 후 §5b-2 엔진 실행) · `simul_move_create`.
- **`SwapRequest.type = "simul_move"`가 이제 PENDING을 가진다.** §5b는 직권 즉시 APPROVED만 존재한다고 보고 여러 곳에 방어를 깔았으므로, **아래 5c-4를 반드시 함께 이행**해야 조용히 깨지지 않는다.
- **생성 검증**: 서버 재합성 → 엔진 재실행 → 제출된 `(groupId, from, to)`와 일치하는 후보 존재 필수(위조 차단). `simulMove.steps`는 서버 계산값 저장.
- **중복 차단**: 같은 `(groupId, from)`에 대한 PENDING 1건. 그룹은 여러 교사가 공유하므로 **신청자별이 아니라 그룹·슬롯 단위**로 막는다(김진만이 낸 신청을 모르고 이경호가 또 내는 것을 방지). 기존 단건 교체의 "같은 소스 셀" 규칙과 다른 축임에 주의.
- **consent 필수**: parties = 그룹 담당 교사(신청자 제외) ∪ 치워지는 상대 교사 ∪ 특별실 조율 당사자 — 서버 도출(§5b-3 동일).
- **승인(일과계)**: `approveSwapRequest`에 `simul_move` 분기 신설 — 트랜잭션 안에서 재합성·엔진 재실행·`(from,to)` 대조 후 **반별 change 원자 커밋**. 커밋 조립부는 `commitSimulGroupMove`와 동일하므로 **공용 함수로 추출해 양쪽이 공유**한다(로직 두 벌 금지 — 이 저장소의 반복 사고).
- **취소·되돌리기**: 기존 그대로(PENDING 취소는 신청자, 승인 후 되돌리기는 requestId 묶음 전량 — 기구현).

### 5c-3. 일과계 직권 경로 (보조)

- `commitSimulGroupMove`(즉시 반영) **유지**. 다만 **주 경로가 아니다** — 일과계의 고유 권한은 보강 중심이고, 통 이동 직권은 "교사가 못 하는 예외 상황"의 뒷문이다.
- 직권 탭 진입도 §5c-1대로 **수업 클릭**으로 통일한다. 그룹 드롭다운 방식은 제거하거나 등록부(SimulGroupTab)에서 들어오는 보조 진입으로만 남긴다.

2026-08-15 검수에서 "오늘은 도달 불가"를 근거로 넣은 방어들이 **이제 도달 가능해진다.** 착수 시 전건 확인:

| `createSwapRequest`의 `simul_move` 명시 거부 | 전용 경로 강제 | **유지** — 전용 생성 함수(`createSimulMoveRequest`)를 쓴다 |
| `validatePendingSwapRequests`의 조기 `{ok:true}` 반환 | PENDING이 없다는 전제 | **진짜 재검증으로 교체** — 그룹 로드 → 엔진 재실행 → `(from,to)` 후보 존재 확인 |
| `approveSwapRequest`에 `simul_move` 분기 없음 | `status!=="PENDING"` 가드로만 차단 | **분기 신설**(5c-2). 없으면 substitute 분기로 새어 오작동 |
| `buildVirtualChanges`의 `simul_move` 조기 return | what-if 오버레이 대상 아님 | **유지 + 화면 보완** — 반별 n건이라 단건 오버레이로 표현 불가. 대신 "대기 중인 묶음 이동 신청 있음"을 그리드에 배지로 알린다 |
| 승인 알림 수신자 `filter(Boolean)` | `counterpartEmail=""` 방어 | 유지 |

### 5c-5. 양해 부담은 시스템이 줄인다 (일과계에게 넘기지 않는다)

교사 1인이 3~5명의 양해를 받아야 하는 것은 사실이다. 이것이 §5에서 직권 전용의 근거였으나, 사용자 원칙에 따라 **해법의 방향을 뒤집는다**:

- **지금(v1)**: 현행 수동 체크(`consent.confirmed`) 유지 — 교사가 밖에서 양해를 구하고 체크. 다만 화면이 **누구에게 무엇을 물어야 하는지**를 명단·문장으로 완성해 준다(엔진이 이미 parties와 반별 전개를 계산한다).
- **다음(v2)**: 로드맵 §2 「알림 센터 — 수락 창구」가 이 자리다. 도입되면 `SwapDraft.consentStatus`(NONE→REQUESTED→CONSENTED)가 실제 전이하며 수동 체크를 대체한다 — **모델은 이미 호환되게 설계돼 있다**(§13-3). 통 이동이 이 기능의 가장 강한 실사용 근거다.

### 5c-7. 확정 개정 — 별도 기능이 아니라 **조율 후보의 종류를 하나 늘린다** (2026-08-15 사용자)

> *"지금도 특별실 이동은 일반 교사가 할 수 있지만 경고도 뜨고 양해도 무조건 받았는지 확인하잖아. 이 방식을 그대로 이 케이스에도 적용하면 될 것 같아. 난이도 때문에 순차적으로 개발한 거지 수업 교체 루틴은 같은 것 같아."*
>
> **맞다. 그리고 모델이 처음부터 그렇게 설계돼 있었다** — `CandidateCoordination.kind`는 `"venue"` 하나뿐이지만 주석이 *"1차는 특별실만 — **확장 여지용 판별자**"*이고, §7이 확장 대상으로 *"특별실 외 충돌의 조율 후보화(복수교사·**동시수업** 단일 반 등)"*를 명시해 뒀다. 순차 개발이 맞았고, 이제 그 확장을 쓸 때다.
>
> **이 절이 §5c-1~3의 "별도 진입·별도 화면" 부분을 대체한다.** 통 이동 전용 모드·메뉴는 **만들지 않는다**(기존 것도 걷어낸다).

**개정 골자**: 교사는 평소처럼 **자기 수업을 클릭하고 후보 목록을 본다.** 그 수업이 묶음이면, 갈 수 있는 교시가 **조율 필요 후보(⚠️ 양해 필수)로 같은 목록에 섞여 나온다.** 클릭 마찰(§3-2b-2)·양해 체크 위치(§3-2b-3)·신청·승인·알림 전부 **현행 루틴 그대로**.

1. **조율 종류 확장**: `CandidateCoordination.kind`를 `"venue" | "simul" | "venue+simul"`로 넓힌다. 특별실 겹침은 기존 `conflicts` 유지(묶음 이동에도 특별실 겹침이 함께 날 수 있다 — 실측 21건), 묶음 정보는 신규 `simul` 블록(그룹 라벨·함께 움직이는 반·반별 전개 `steps`)에 담는다. **`kind === "venue"` 등호 비교를 하는 소비처 전수 확인이 필수**(§5b-6 검수 항목에 합류).
2. **후보 모양**: 일반 후보는 상대가 1명인데 묶음 이동은 반마다 다르다. `counterpartName`은 chain 전례대로 **사람용 요약**(그룹 라벨)을 넣고, 실제 상대 목록은 `coordination.simul.steps`가 원본이 된다. 화면은 steps로 렌더한다.
3. **엔진 배선**: `resolveSourceLesson`의 simul 차단은 **그대로 둔다**(단건 교체·체인·보강이 의존). 대신 `computeCandidates` 호출부에서 "소스가 묶음이면 §5b-2 엔진으로 분기 → 결과를 후보 모양으로 매핑"한다. 기존 함수 무수정 = 회귀 0.
4. **신청 타입은 내부적으로 `simul_move` 유지**: 되돌리기가 requestId 묶음 전량 취소에 의존하고(기구현), 요청대장이 반별 전개를 보여줘야 하기 때문. **다만 교사 화면에서는 "교체 신청"일 뿐 다른 이름을 노출하지 않는다.**
5. **🔴 양해의 성격이 다르다 — 문구를 구분할 것**: 특별실 양해는 *"장소를 양보해 주세요"*(상대 수업은 **안 움직인다**). 묶음 양해는 *"선생님 수업도 함께 옮겨집니다"*(상대 수업이 **움직인다**). **루틴은 같지만 문장은 같을 수 없다.** 확인창은 "무엇이 함께 움직이는지"를 반별로 보여야 한다(U1 플랫화 규약 유지, 처방 표현 금지).
6. **일과계 직권**: 별도 모드를 없애고, 직권 탭에서도 같은 방식(수업 클릭 → 조율 후보)으로 통일한다. `commitSimulGroupMove`는 직권 즉시 반영 경로로 유지.

**이 개정으로 줄어드는 것**: 통 이동 전용 모드·그룹 드롭다운·전용 확인창(전부 제거) → 교사·일과계 양쪽에서 배울 개념이 하나 줄고, §3-2b~c에서 이미 실기기 검증을 통과한 경고·양해 상호작용을 그대로 물려받는다.
