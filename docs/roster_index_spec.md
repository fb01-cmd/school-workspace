## §0 문제와 해법

`teacher_profiles` 89건을 **전수로 읽는 화면이 5개**다 — 조직도 트리, 조직도 빌더, 쪽지 수신자 선택, 업무 수신자 선택, 프로필 승인. 여기에 「쪽지·업무」 화면이 더해지면 **하루에도 여러 번 여는 상주 화면**이 된다.

**해법**: 같은 내용을 담은 **문서 1건**을 서버가 만들어 두고, 화면은 그것만 읽는다. **89 read → 1 read.**

**이 안이 쪽지 쪽 같은 계열 아이디어(레버 ②·②')와 다른 점**: 사용자별 사본이 아니라 **전원이 같은 것 하나를 읽는** 소형 문서다. 팬아웃이 없고, 파기 전파 의무가 없고(현재형 데이터라 덮어쓰기로 소멸), 회수·삭제 의미론이 없다. 그래서 데이터 모델 변경의 위험 없이 넣을 수 있다.

## §1 데이터 모델 — `org_index/{domain}` (신설 컬렉션, 문서 1건)

```ts
{
  schemaVersion: 1,
  domain: string,
  builtAt: number,          // ms — 낡음 판정 기준
  builtBy: string,          // "daily-sync" | "write" | "manual" — 진단용
  count: number,            // profiles.length (읽는 쪽 무결성 확인용)
  profiles: TeacherProfile[] // teacher_profiles 문서 원문 배열
}
```

**`settings/{domain}`에 얹지 않는 이유**: `settings`는 규칙상 `isSchool()` 읽기 — **학생도 읽는다.** 명단에는 내선번호·담임 배정이 들어가므로 학생에게 열어서는 안 된다. 별도 컬렉션에 `isTeacher()` 읽기를 건다.

**`profiles`는 문서 원문을 그대로 담는다 — 필드를 골라 담지 않는다.**
- 이유: 골라 담으면 나중에 `teacher_profiles`에 필드가 하나 늘 때마다 여기도 고쳐야 하고, **안 고치면 그 필드만 조용히 사라진다.** 소비자는 색인을 쓰는지 원본을 쓰는지 구분할 수 없어야 한다.
- 크기 대가는 무시할 만하다 — 1건 약 250~300바이트 × 90건 ≈ **30KB, 1MiB 한도의 3%**. 목표 규모에서도 `teacher_profiles`는 교직원만 담으므로(학생 800명은 이 컬렉션에 없다) 건수가 늘지 않는다.

**크기 가드**: 직렬화 결과가 **700KB를 넘으면 쓰지 않고 실패시킨다.** 조용히 자르지 않는다 — 잘린 명단은 "그 사람이 퇴직한 것"처럼 보인다. 초과 시 관리자 알림(알림 센터 원장)과 함께 색인을 갱신하지 않고 두어, 소비자가 낡음 판정(§3)으로 원본 폴백에 들어가게 한다.

## §2 갱신 시점 — 「쓸 때마다 + 하루 1회 보정」

### §2-1 쓸 때마다 (주 경로) — **쓰기 경로 전수 대조 결과 반영 (2026-08-19)**

> **초안의 전제가 틀렸다.** 초안은 *"프로필을 고치는 화면은 전부 쓰기 직후 `invalidateTeacherProfilesCache()`를 부르므로 그 헬퍼 하나에 얹으면 된다"* 고 썼다. **전수 대조 결과 거짓이다** — 아래 B3·B4·B5(전출 삭제·취소 복원·명퇴 삭제)는 `teacher_profiles`를 서버에서 지우거나 되살리면서 **`teacher_profiles:all` 무효화를 아예 부르지 않는다**(호출부 `TeacherLifecycle.tsx`가 `users:all`만 무효화). 헬퍼 하나에만 얹었다면 **하필 삭제 경로에서 색인이 안 갱신되어 떠난 교사가 명단에 남았을 것이다** — 이 설계에서 가장 비싼 실패다(2026-08-07 조직도 유령 실사고와 같은 형태).

쓰기 경로는 **13곳**이고 성격이 셋으로 갈린다. 각각 다른 장치로 잡는다.

| 갈래 | 경로 | 재조립 방법 |
|---|---|---|
| **① 클라이언트 쓰기 (4)** | ManualProfileEditor · MyProfileModal(내선) · OrgChartBuilder(일괄 반영) · ProfileApprovals(승인) | `invalidateTeacherProfilesCache()`에 재조립 발화를 얹는다. 넷 다 이 헬퍼를 (직접 또는 `loadTeacherProfiles(true)` 경유로) 이미 부르고, **넷 다 쓰기 `await` 이후**임을 확인했다 |
| **② 서버 쓰기 (5)** | handover(담임·부서 이관) · lifecycle 전출 삭제 · 전출 취소 복원 · 명퇴 삭제 · name_sync(야간) | **서버에서 직접 `await buildRosterIndex(domain, {force:true})`.** 클라이언트 헬퍼에 기대지 않는다 — ②는 애초에 그 헬퍼를 지나지 않고, 셋은 무효화조차 없다 |
| **③ 일회성 스크립트 (D1~D6)** | 부서명 마이그레이션·전출 정리·계정 정리·복원 등 | 별도 장치를 만들지 않는다. **하루 1회 보정(§2-2)이 흡수한다.** 급하면 `scripts/verify_roster_index.ts --rebuild`로 손으로 돌린다 |

```
① 프로필 쓰기 → (await 완료) → invalidateTeacherProfilesCache()
                                    ├ 로컬 캐시 무효화 (기존 동작)
                                    └ POST /api/org/roster {action:"rebuild"}  ← 신설, fire-and-forget

② 서버 쓰기 → (await 완료) → await buildRosterIndex(domain, {force:true})
```

- ①은 실패해도 화면 동작을 막지 않는다(fire-and-forget). 실패분은 하루 1회 보정이 흡수한다.
- **②의 삭제 3경로(전출·명퇴·복원)는 이 스펙에서 가장 중요한 접합점이다.** 여기서 재조립을 빠뜨리면 떠난 사람이 조직도·쪽지 수신자·업무 수신자에 유령으로 남는다.
- **곁가지 결함 동반 수정**: `TeacherLifecycle.tsx`가 전출·복원·명퇴 후 `users:all`만 무효화하고 `teacher_profiles:all`은 안 한다(전수 대조에서 발견). 서버 재조립과 별개로 **열려 있는 화면의 로컬 캐시도 5분간 유령을 들고 있으므로** 같이 고친다.
- **비원자 다중 문서 쓰기가 4쌍 있다**(handover 담임 승계 2건, 명퇴 보관→삭제, 전출 삭제→pending 삭제). 재조립은 **그 묶음이 전부 끝난 뒤 한 번만** 부른다 — 중간에 부르면 반쪽 상태가 색인에 박힌다.

### §2-2 하루 1회 보정 (백스톱)

`daily-sync` 크론의 마지막 작업으로 **조건 없이 전수 재조립**한다. 신규 크론 슬롯을 쓰지 않는다(무료 플랜 2개 한도).

이 보정이 흡수하는 것: ⓐ §2-1 호출이 실패한 경우 ⓑ 새 쓰기 경로가 생겼는데 호출을 빠뜨린 경우 ⓒ `scripts/*.ts` 일회성 관리 스크립트의 직접 수정.

### §2-3 순서·경합 계약 (**이 절이 Claude 직접 구현 사유다**)

1. **재조립은 프로필 쓰기가 확정된 뒤에만 호출한다.** `await setDoc(...)` **이후**다. 앞이나 동시에 부르면 **옛 값으로 색인이 만들어지고, 그 색인이 다음 보정까지 진실 행세를 한다.** 평소에는 안 드러나고 바쁜 날에만 틀리는 종류다.
2. **재조립은 언제나 전수다. 증분 갱신(그 사람만 고쳐 넣기)을 금지한다.** 두 관리자가 동시에 다른 사람을 고치면 나중 증분이 앞의 변경을 지운다. 전수 재조립은 **누가 이기든 결과가 Firestore 원본과 일치**하므로 경합이 무해해진다.
3. 동시 재조립이 겹쳐도 안전하다(둘 다 원본 전수를 읽어 같은 결과로 수렴). 마지막 쓰기가 이기고, 그 값이 옳다.
4. **재조립 안에서 `teacher_profiles`를 읽는 것은 admin SDK(서버)다.** 클라이언트가 89건을 읽어 올려 보내는 형태를 금지한다 — 클라이언트가 색인 내용을 정할 수 있으면 한 사람이 전원의 명단을 오염시킬 수 있다.

### §2-4 남용 방지

`rebuild`는 1회당 서버 89 reads + 1 write다. 내선번호 수정은 **일반 교사도 할 수 있는 쓰기**이므로(firestore.rules의 `extension` 2계층 허용) 호출자가 수퍼어드민만은 아니다.

- 자격: 로그인한 교직원(소속 등록자). 
- **디바운스**: 마지막 `builtAt`이 **10초 이내**면 재조립하지 않고 그대로 성공 응답한다(연타·동시 편집 흡수).
- 클라이언트도 재요청을 5분간 억제한다(`clientCache`에 요청 마커).

## §3 읽기 경로 — 낡음 판정과 폴백

`loadTeacherProfiles()`(`src/lib/org/roster.ts`) **한 곳만 고친다.** 5개 화면은 이미 이 함수를 쓰므로 호출부 변경이 없다.

```
① 로컬 캐시(clientCache, 기본 TTL) 있으면 그대로 — 지금과 동일
② 없으면 org_index/{domain} 1건 읽기
③ 색인이 쓸 만하면 → 그것을 캐시에 넣고 반환        (1 read)
④ 쓸 수 없으면 → teacher_profiles 전수 읽기 + 재조립 요청  (89 reads, 지금과 동일)
```

**색인을 쓸 수 없는 조건 (= 낡음 판정)**

| 조건 | 뜻 | 동작 |
|---|---|---|
| 문서 없음 | 아직 한 번도 안 만들어짐 | 원본 폴백 + 재조립 요청 |
| `schemaVersion` 불일치 | 구조가 바뀜 | 원본 폴백 + 재조립 요청 |
| `count`와 `profiles.length` 불일치 | 쓰다 만 문서 | 원본 폴백 + 재조립 요청 |
| **`builtAt`이 48시간 초과** | 하루 1회 보정이 **이틀 연속** 실패 = 진짜 고장 | 원본 폴백 + 재조립 요청 |
| 그 외 | 정상 | **색인 사용 (1 read)** |

**왜 24시간이 아니라 48시간인가**: 크론 1회 실패는 배포·타임아웃으로 흔히 생긴다. 24시간으로 자르면 정상 운영 중에도 전원이 폴백으로 떨어져 색인이 무의미해진다. 게다가 **실사용 중이면 §2-1이 매 쓰기마다 갱신하므로 `builtAt`은 훨씬 신선하다** — 48시간을 넘겼다는 것은 "이틀간 아무도 프로필을 안 고쳤고 크론도 두 번 실패했다"는 뜻이고, 그때는 색인을 믿지 않는 편이 맞다.

**폴백 스탬피드 방지**: 폴백에 빠진 클라이언트가 전부 재조립을 요청하면 서버 89 reads × N이 된다. 클라이언트는 5분 요청 마커로, 서버는 §2-4 디바운스로 이중 억제한다.

## §4 보안 규칙

```
match /org_index/{domain} {
  allow read: if isTeacher();
  allow write: if false;      // 서버(admin SDK)만 — 규칙을 우회하므로 실제로 쓸 수 있다
}
```

- **쓰기를 클라이언트에 절대 열지 않는다.** 열면 교사 1명이 전원의 명단을 바꿀 수 있다(원본은 승인제로 잠겨 있는데 사본이 뒷문이 되는 형태).
- 읽기는 `teacher_profiles`와 동일 등급(`isTeacher()`)이다 — 같은 내용이므로 더 열지도, 덜 열지도 않는다.
- 학생은 읽을 수 없다(`isSchool()`이 아니라 `isTeacher()`).

## §5 개인정보

- **인벤토리에 행을 추가한다**: `org_index` — 교직원 이름·소속·직위·담임 배정·내선번호의 **사본**. 원본(`teacher_profiles`)과 동일 등급·동일 열람 범위.
- **파기 대상이 아니다.** 현재형 데이터이고 재조립이 통째로 덮어쓴다. 별도 파기 크론을 만들지 않는다.
- **삭제 전파는 자동이다** — 원본에서 사라진 사람은 다음 재조립에서 색인에서도 사라진다. 단 **전출·삭제 경로가 재조립을 부르지 않으면 그 사이 유령이 남는다**(§2-1의 필수 조항인 이유).
- 처리방침 문안 갱신은 불필요하다 — 새로운 항목을 수집하는 것이 아니라 이미 고지된 항목의 내부 저장 형태다.

## §6 비용

| 사건 | 지금 | 색인 후 |
|---|---|---|
| 화면 진입(캐시 미스) | 89 reads | **1 read** |
| 프로필 수정 1회 | 0 (읽기 없음) | 서버 89 reads + 1 write |
| 하루 1회 보정 | — | 서버 89 reads + 1 write |

**역전이 일어나지 않는 이유**: 색인이 손해가 되려면 프로필 수정이 화면 진입보다 잦아야 한다. 프로필 수정은 인사 변동 때 몰리는 연 수십 건 규모이고, 화면 진입은 교사 70명이 매일 반복한다. **최악의 날에도 지금과 동등하고, 평시에는 89배 싸다.**

목표 규모(교사 70·학생 800)에서도 이 문서는 커지지 않는다 — 학생은 `teacher_profiles`에 들어가지 않는다.

## §8 구현 순서 (전부 Claude)
