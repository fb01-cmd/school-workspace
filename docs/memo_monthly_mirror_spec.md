## §0 무엇을 바꾸는가 — 한 문장

**받는 사람마다, 달마다, 자기 쪽지 사본을 한 벌 더 둔다.** 화면은 그 사본을 읽고, 원본은 발신자용 상태와 파기의 근거로만 남는다.

---

## §1 지금 무엇이 비싼가 (실측 기반 — 이것이 이 설계의 근거다)

| 화면 | 지금 | 읽기 |
|---|---|---|
| 받은쪽지함 열기 | `array-contains recipientEmails` + `orderBy createdAt desc` + `limit(50)` **실시간 구독** | **최대 50** |
| 홈 카드 | **같은 쿼리를 따로** 구독 | **또 최대 50** (둘 다 열려 있으면 2배) |
| 보낸쪽지함 | `senderEmail ==` + 같은 모양 | 최대 50 |
| 검색(3개월) | 기간 내 **받은 전량 + 보낸 전량**을 `limit(300)` 페이지네이션으로 **끝까지** | **그 기간 문서 수 전부** |
| 모바일 | 위와 같은 구독을 또 | 최대 50 |

**세 가지 구조적 낭비가 확인됐다.**

1. **같은 문서를 여러 구독이 각각 읽는다** — 홈 카드와 쪽지 화면이 동시에 열리면 같은 쪽지를 두 번 센다.
2. **감춘 쪽지가 자리를 계속 차지한다** — `hiddenBy`는 클라이언트에서 거르므로 서버 `limit(50)` 안에서는 여전히 한 자리다. **되돌리는 경로도 없다**(감추면 영구).
3. **검색은 기간 전량 스캔이다** — 캐시(5분)가 있으나 만료되면 다시 전량이다.

## §2 새 구조

### §2-1 문서 배치

```
memos/{domain}/items/{memoId}                      ← 원본 (지금 그대로 존치)
memo_mirror/{domain}/users/{email}                 ← 사용자 색인 (달 목록)
memo_mirror/{domain}/users/{email}/months/{YYYY-MM}        ← 그 달 사본
memo_mirror/{domain}/users/{email}/months/{YYYY-MM}#2      ← 분할분 (§4)
```

### §2-2 ⭐ 역할 분리 — 무엇이 어디에 사는가

**이 표가 이 스펙의 핵심이다.** 어긋나면 읽음 확인이 깨지거나 파기가 새어 나간다.

| | 원본 `memos/…` | 월 사본 `…/months/…` |
|---|---|---|
| 제목·본문·서식(`md1`) | ✅ 정본 | **사본(불변)** |
| 발신자 이메일·발송 당시 이름 | ✅ 정본 | 사본(불변) |
| 첨부 **참조**(`driveFileId`·이름·크기) | ✅ 정본 | 사본(불변) — **파일 실체는 Drive 한 곳뿐. 사본이 파일을 복제하지 않는다** |
| `createdAt` | ✅ | 사본 |
| **`reads` (누가 언제 읽었나)** | ✅ **정본** — 발신자의 「읽음 현황」이 이것을 본다 | ❌ 두지 않는다 |
| **내 읽음 여부** | (원본 `reads`에 내 키가 있는지) | ✅ **내 사본에만** — 목록 렌더가 이것만 보면 된다 |
| **내 감춤·별표** | 현행 `hiddenBy`·`starredBy`는 **원본에서 제거** | ✅ **내 사본에만** |
| `recipientEmails`·`recipientCount`·`recipientSummary` | ✅ 정본 (회수가 이것을 줄인다) | ❌ 두지 않는다 |
| `recalledAt`·`recalledCount` | ✅ | ❌ (회수되면 사본에서 **항목이 사라진다** — §3-3) |
| `expireAt` | ✅ **파기의 유일한 근거** | ❌ (원본 파기가 사본을 따라 지운다 — §3-4) |

**원칙**: **남이 보는 상태는 원본, 내가 보는 상태는 내 사본.** 읽음 확인이 원본에 남는 이유는 **수신자가 발신자의 문서에 쓸 권한을 갖게 하고 싶지 않기** 때문이다(서버가 쓰므로 권한 문제는 없지만, 정본이 흩어지면 「읽음 현황」의 진실이 여러 곳이 된다).

### §2-3 사용자 색인 문서

`memo_mirror/{domain}/users/{email}` 본문:

```
months: {
  "2026-08": { shards: 1, bytes: 45231, lastAt: 1755... },
  "2026-07": { shards: 2, bytes: 812004, lastAt: 1753... }
}
unreadTotal: 3
```

- **읽기 1회로 "어느 달이 있고 몇 조각인지"를 안다.** 검색·과거 열람이 이걸 먼저 본다.
- **받은쪽지함 첫 화면은 색인 없이** 이번 달 문서를 바로 읽는다(경로가 날짜로 결정되므로).
- `unreadTotal`은 배지용 — 목록을 열지 않고도 안 읽은 수를 안다.

### §2-4 월 문서 본문

```
items: [
  { memoId, senderEmail, senderName, title, body, contentFormat,
    attachments: [...], links: [...], createdAt,
    readAt: null | ms,      ← 내 읽음
    hiddenAt: null | ms,    ← 내 감춤
    starred: false }
]
bytes: 45231        ← 근사치, 분할 판정용 (§4)
```

**정렬은 저장하지 않는다** — `createdAt` 내림차순은 클라이언트에서 한다(한 달치라 비용 무시).

## §3 각 동작이 어떻게 바뀌나

### §3-1 발송 (fan-out on write)

1. 원본 1건 생성 (지금과 동일)
2. **수신자 수만큼** 각자의 이번 달 문서에 `arrayUnion`으로 항목 추가 + 색인의 `bytes`·`lastAt`·`unreadTotal` 갱신

**쓰기 증폭은 수용한다.** 80명 공지 = 81 writes. 무료 한도 20,000 writes/일 대비 여유가 크다(목표 규모 교사 70에서 하루 수십 건 발송).

> **⚠️ 부분 실패를 삼키지 마라.** 사본 쓰기가 일부 실패하면 그 사람에게는 쪽지가 안 보인다. **실패한 수신자를 원본에 기록하고 재시도**한다(첨부 `permissionPending` 전례와 같은 방식). 조용한 실패 금지.

### §3-2 읽음

- **원본** `reads.{email} = ms` (지금과 동일 — 최초 시각 보존)
- **내 사본** `items[i].readAt = ms` + 색인 `unreadTotal` 감소

**쓰기가 2건이 된다.** 읽음은 목록 열기보다 훨씬 드물고, 대신 목록 열기가 50 → 1 read가 된다. **바꿀 만하다.**

### §3-3 회수 ⚠️

회수는 **미열람자만** 대상이다(현행 그대로).

1. 원본: 미열람자를 `recipientEmails`에서 제거, `recipientCount` 감소, `recalledAt`·`recalledCount` 기록
2. **그 사람들의 사본에서 해당 항목을 제거한다** — 회수의 의미가 "안 본 사람에게서 없앤다"이므로 **사본에 남으면 회수가 아니다**
3. 개별 공유 첨부는 Drive reader 권한도 회수(현행 그대로)

### §3-4 파기 ⚠️ — **이 절을 틀리면 개인정보 문제가 된다**

**파기의 근거는 원본 `expireAt` 하나다.** 사본에 만료일을 따로 두지 않는다.

파기 크론(`runMemoPurge`)이 만료 쪽지를 처리할 때:
1. Drive 첨부 파일 삭제
2. **모든 수신자의 해당 월 사본에서 그 항목 제거**
3. 원본 문서 삭제 (참조가 마지막에 사라지도록 — 현행 순서 유지)

> **왜 사본을 「월 단위 통째 만료」로 하지 않는가**: 한 달 안에도 쪽지마다 보존일이 다를 수 있다(설정 변경). 가장 늦은 것 기준으로 통째 두면 **기한이 지난 쪽지가 사본에 남고**, 가장 이른 것 기준으로 지우면 **아직 유효한 쪽지가 사라진다.** 둘 다 안 된다. **파기는 정확해야 하므로 항목 단위로 지운다.**
>
> 비용: 만료는 생성일 기준 롤링이라 **하루 만료량 ≈ 하루 발송량**이고, 항목 제거는 수신자당 1 write다. 하루 수십 건 × 수신자 = 수백 write. 한도 대비 여유.

> **⚠️ 2026-08-20 실사고를 반드시 승계한다**: 파기 소재지는 `runMemoPurge` **하나**다. 다른 크론이 만료 쪽지 문서를 지우면 첨부가 고아로 남았던 결함이 있었고(lifecycle 크론, 같은 날 제거), **사본이 생기면 같은 실수가 "사본만 남는다"로 재현된다.** 그 함수 밖에서 만료 쪽지를 지우지 마라.

### §3-5 감춤·별표

**내 사본에서만** 바꾼다(`hiddenAt`·`starred`). 원본의 `hiddenBy`·`starredBy`는 **제거한다.**

- **감춘 항목은 배열에서 실제로 빼도 된다** — 되돌리기가 없는 현행 동작을 그대로 승계한다면. **되돌리기를 넣을 거면** `hiddenAt`만 세우고 렌더에서 거른다.
- **현행 결함이 자연히 해소된다**: 감춘 쪽지가 `limit(50)` 자리를 차지하던 문제가 사라진다(내 사본이라 내가 뺀다).

## §4 ⭐ 1 MiB 하드월과 월 분할 규칙

Firestore 문서 상한은 **1 MiB**이고, 이건 색인과 달리 **발췌로 우회할 수 없는 실데이터**다. 넘으면 **쓰기가 실패하고, 그 실패는 조용하다**(그 사람에게만 쪽지가 안 보인다).

**규칙**

1. 월 문서에 `bytes` 근사치를 유지한다(항목 추가 시 직렬화 길이를 더한다).
2. **`bytes`가 700 KiB를 넘으면 다음 항목부터 새 조각**(`{YYYY-MM}#2`, `#3`…)에 쓴다. 색인의 `shards`를 올린다.
   - **700 KiB인 이유**: 항목 하나가 최대 얼마인지 상한이 없다(본문 1만 자 + 첨부·링크 메타). 여유 300 KiB는 **한 항목이 통째로 들어갈 자리**다.
3. **읽는 쪽은 색인의 `shards`만큼 읽는다.** 조각을 찾아 헤매지 않는다.
4. **한 항목이 700 KiB를 넘으면** — 본문 상한(1만 자)과 첨부 메타를 감안하면 정상적으로 불가능하다. 그래도 방어한다: **그 항목만 단독 조각**에 넣고 색인에 표시한다.

> **실사용 추산**: 월 45~75 KB(한도의 5~7%). 벽은 멀다. **그래도 규칙을 두는 이유는 넘칠 때가 조용하기 때문이다** — 이 저장소가 반복해서 당한 실패 유형이다.

## §5 firestore.rules — 단순해진다

**현행**: 검증된 `@hmh.or.kr` + 역할 `teacher|super_admin` + `teacher_profiles` 존재 + `departments.size()>0` + **(발신자이거나 `recipientEmails`에 있음)**

**사본 도입 후**

```
사본 읽기:  경로의 {email} == request.auth.token.email  (+ 도메인·역할 게이트)
원본 읽기:  발신자 본인만
쓰기:       전부 false (현행 그대로 — 서버 Admin SDK만)
```

**쪽지별 자격 증명이 통째로 사라진다.** "내 경로면 내 것"이라 규칙이 한 줄로 준다. 부수 이득이지만 작지 않다 — 보안 규칙은 단순할수록 틀릴 자리가 적다.

## §6 이 설계가 해결하는 것 / 새로 생기는 것

**해결**

| 지금 | 사본 도입 후 |
|---|---|
| 받은쪽지함 열기 = 최대 50 reads | **1 read**(이번 달 문서) |
| 홈 카드가 같은 쪽지를 또 읽음 | **같은 문서를 본다 — 중복 소멸** |
| 검색 3개월 = 기간 전량 | **3 reads**. 완결된 달은 불변이라 **캐시 영구**(실효 1) |
| 감춘 쪽지가 목록 자리 차지 | 내 사본에서 빼므로 소멸 |
| 보안 규칙이 쪽지별 자격 증명 | 경로 한 줄 |

**새로 생기는 것 (전부 §3·§4에서 다뤘다)**

1. 쓰기 증폭 — 수용
2. 1 MiB 하드월 — 분할 규칙 필수
3. 읽음 쓰기가 2건 — 수용
4. **회수·파기가 두 곳에 걸린다** — 이것이 가장 큰 위험이고, §3-3·§3-4가 다룬다

## §7 전환 (구현 착수 시)

1. **백필** — 기존 쪽지를 수신자별·월별로 사본에 채운다. 보존 365일이므로 최대 13개월치.
2. **이중 쓰기 기간** — 사본이 정답임을 확인할 때까지 원본 경로도 유지한다.
3. **읽기 전환** — 화면을 사본으로 돌린다. 이 순서를 뒤집지 않는다.
4. **원본 정리** — `hiddenBy`·`starredBy`를 원본에서 제거하는 것은 **맨 마지막**이다.

> **되돌릴 수 없는 순서**: 4번을 먼저 하면 사본이 깨졌을 때 돌아갈 곳이 없다.

## §8 착수 조건 (⑩-2 — 사건이 아니라 「누가 언제」)

| | |
|---|---|

**이 문서가 있으면 구현은 Claude가 아니어도 된다.** 그것이 지금 쓰는 이유다.
