## 1. 지금 즉시 — 판단만 하면 끝나는 것 (착수 전 반드시)

### 🔴 1-1. `isTeacher()`에 `isApproved == true` 추가 — **폐기한다**

`docs/coop_account_block_spec.md` §8의 "검토" 항목. **실행하면 전 교사가 전 기능에서 잠긴다.**

- `sync-user/route.ts:161,169` — 로그인할 때마다 `isApproved: isWorkspaceAdmin`으로 덮어쓴다.
  일반 교사는 **구조적으로 항상 `false`**다.
- `isTeacher()`는 `firestore.rules`에서 **20곳 이상**의 컬렉션을 문지킨다.
- 같은 착각이 쪽지에서 이미 사고로 터졌다(쪽지가 수퍼어드민 전용이 돼 있었음, 2026-08-13).
  그 교훈은 `firestore.rules:131` 주석에 적혀 있는데 **스펙 문서에는 반영되지 않아 살아남았다.**

→ **조치**: 스펙 §8에서 이 줄을 삭제하고 "폐기 사유"를 적는다. 자격 판정의 단일 원본은
`teacher_profiles`(소속 있음)이다. *문서와 코드가 다른 결론을 들고 있으면 문서를 고친다.*

### 🔴 1-2. 관리자 승인 화면이 다음 로그인에 조용히 무효화된다 — **사용자 결정 필요**

트리아지 중 발견(원목록에 없던 항목).

- `PendingApprovals.handleApprove` → `role: "super_admin", isApproved: true` 저장
- 그런데 그 사람이 **다시 로그인하면** `sync-user`가 `role`·`isApproved`를 GWS 관리자 여부로 되돌린다
- 즉 **승인해도 다음 로그인에 원상복구**. `admin/page.tsx:152`의 `hasAccess`가 조용히 꺼진다

되감기 구조가 내선번호 승인 건과 **똑같다**(그건 고쳤고 이건 남아 있었다).

→ **사용자 결정 ⓐ 확정 (2026-08-13) — 처리 완료.** 착수 전 폭발 반경 실측에서 **예상보다 이미 죽어 있었다**:

| 확인 | 결과 |
|---|---|
| `PendingApprovals` 마운트 지점 | **0곳** — 화면이 아예 렌더링되지 않는 고아 컴포넌트였다 |
| `hasAccess` 사용처 | **0곳** — 선언만 되고 어디서도 읽히지 않는 죽은 변수 |
| `firestore.rules`의 `isApproved` | **주석 한 줄뿐**, 규칙 판정에는 미사용 |
| `users.status` 읽는 곳 | 죽은 승인 화면 외 **없음** |
| 실데이터(users 29건) | `isApproved=true` 5건 = super_admin 4 + **학생 1** |

**즉 실사용 권한 사고는 없었다** — 관문으로 배선되지 않아 잠복해 있었을 뿐이다. 다만 **학생 계정도
`isApproved=true`**여서(sync-user), 누군가 나중에 `hasAccess`를 관문으로 이으면 **학생이 관리자 화면에
들어오는** 구조였다. `isTeacher()`에 붙이자는 §1-1 제안이 실제로 그 방향이었다.

**조치**: 승인 화면 삭제 / `hasAccess` 제거 / `sync-user`가 `isApproved`·`status`를 더 이상 쓰지 않고
**기존 문서에서도 `FieldValue.delete()`로 지운다**(로그인할 때마다 자가 정리) / `UserData` 타입에서도 제거.
**권한 판정의 단일 원본은 `role` 하나**다.

> 남아 있던 `status: "pending_approval"` 1건 — 볼 수 있는 화면이 없어 아무도 모른 채 대기열에 있었다.
> 아무것도 게이트하지 않으므로 그 사람은 정상 교사로 쓰고 있었고, 이번 정리로 필드째 사라진다.

   > **성격 정정**: cleanup 라우트에는 소유자 검증이 **없는 것이 아니라, super_admin을 명시적으로 면제**하고 있다 — 340행 `if (logDocData.teacherEmail && logDocData.teacherEmail !== teacherEmail && role !== "super_admin")` → 403 `"본인의 정리 기록만 원복할 수 있습니다."`. "미구현"이 아니라 **설계된 우회**다.
   > **실질 위험은 낮다(단, 조용히 깨진다)**: 우회로 통과해도 실행부는 `restoreClassroomCourse(teacherEmail, …)`처럼 **호출자 본인을 사칭**하므로(Phase 5.8 설계 결정 #4), super_admin이 남의 기록을 원복하면 구글 API 단에서 실패한다. 즉 이 우회는 "남의 것을 건드릴 수 있는 구멍"이라기보다 **통과시켜 놓고 엉뚱한 사용자로 호출하는 반쪽 경로**다.
   > **함께 확인된 것 1건**: 334행 `if (logId)` — `logId`가 없거나 문서가 없거나 345행 `catch`로 Firestore 조회가 실패하면 **소유자 검증이 통째로 건너뛰어지고**(로그만 남고 요청은 계속 진행) 그대로 원복 본문으로 내려간다. 위와 같은 이유로 실피해는 사칭 범위에 막히지만, **fail-open 형태**라는 점은 기록해 둔다.
   > **판단**: 잔여 큐에 등재하되 위험도는 🟡. 처방 후보 2가지 — (a) super_admin 면제를 없애고 "정리 기록 원복은 본인만"으로 일원화, (b) 면제를 유지하려면 실행부 사칭 주체를 `logDocData.teacherEmail`로 바꿔 반쪽 경로를 없앤다. **(a)를 권한다** — 관리자가 남 대신 실행하지 않는다는 Phase 5.8 설계 결정 #4와 일치하고, `catch` fail-open도 같이 닫힌다.

→ 셋 다 **잔여 큐에 정식 등재**하고, 못 할 것이면 "안 한다"고 명시적으로 닫는다. 대기로 두는 것만 금지다.
