## 0. 착수 전 설계 판단 2건

### 0-1. 🔴 **엑셀 업로드 경로를 만들지 않는다** (원 지시에서 축소)

> **⛔ [2026-08-14 폐기 — 아래 §0-1a로 대체]** 이 판단은 **틀렸다.** 컴시간 매뉴얼 실물 확인 결과
> 시수표는 학교가 **매년 따로 만드는 엑셀 파일**이고, 컴시간의 시작 절차 자체가 그 파일을 불러오는 것이다.
> 아래 원문은 오판의 기록으로 보존한다. **구현은 §0-1a를 따른다.**

백지 실험 §3 부수는 *"시수표 입력이 성명 기반이면 성명→이메일 매칭 단계가 필요하다"* 고 적었고, 원 지시도 *"엑셀 업로드 재사용, 성명→이메일 매칭 포함"* 이었다. **그 전제를 재검토했다.**

**실측**: 현행 2026-2 그리드에서 파생한 시수표는 **432행 전부 이메일로 식별된다**(가상 교사 60행 제외 372행). 동명이인 문제가 **구조적으로 존재하지 않는다.**

**다음 학기 시수표의 출처는 무엇인가**가 갈림길이다:

| 경로 | 언제 | 식별자 | 필요한가 |
|---|---|---|---|
| **전 학기 그리드에서 파생** | 2027-1부터 매년 | **이메일** | ✅ 이것만 있으면 된다 |
| 컴시간 엑셀 업로드 | 전 학기가 없을 때 | 성명 | ❌ 우리 학교엔 2026-2가 있다 |

**우리 학교는 이미 2026-2 그리드를 갖고 있다.** 2027-1을 짤 때 거기서 파생하면 되고, 그 뒤로는 매년 직전 학기에서 파생된다. **업로드가 쓰일 순간이 없다.**

- 업로드가 필요한 경우는 **타 학교 신규 도입**뿐이고, 그건 로드맵 "타 학교 도입용 위자드"의 일이다(D 갈래, 착수 미정).
- 업로드를 빼면 **성명→이메일 매칭·동명이인 확인 UI가 통째로 사라진다.** 오늘 부서장 명단에서 겪은 함정과 같은 종류를 애초에 만들지 않는 것이다.

> **판정: 파생 전용. 업로드는 만들지 않는다.** 필요해지는 날(타 학교 도입) 그때 만든다.

### 0-1a. ✅ **정정 — 업로드가 실전 경로다** (2026-08-14, 매뉴얼 실물 확인)

사용자 지적: *"매년 시수표는 따로 잡는 게 있을 거야. 저번 학기에서 끌어온다는 것은 좀 많이 위험해 보여."*

**지적이 맞다. 세 겹으로 틀렸다.**

**(1) 원 스펙이 이미 두 경로를 지정해 뒀는데 내가 뒤집어 읽었다.**

[`phase9c_spec.md:23`](./phase9c_spec.md#L23) 원문:
> **획득 경로 2개**: ⓐ 현행 2026-2 기초시간표에서 **역산**(그리드 → 시수 카운트) — **검증 단계의 기본 경로** ⓑ **신학기용 신규 입력 UI(엑셀 업로드 재사용)**

ⓐ는 **검증(실험)용**, ⓑ가 **신학기(실전)용**이라고 명시돼 있다. 나는 실험용 경로를 실전 경로로 승격시키고 실전 경로를 삭제했다.

**(2) 컴시간 매뉴얼: 시수표 준비가 신학기 작업의 1단계다.**

`archive/주간시간표설명서.pdf` §2 「기본적인 시간표 작성 순서」 (1):
> **"다음과 같은 형식의 교사별 시수표 엑셀파일을 준비합니다."**

절차 전체가 이렇다:

```
① 교사별 시수표 엑셀 준비  ← 학교가 교육과정 편성에서 만든다 (컴시간 밖)
② [파일]-[새 시간표 작성]
③ [기초자료]-[교사별시수표 불러오기] → 파일 선택 → 실행
④ 기본사항·교사명·학급·과목·요일별시수·시수표 등록부 확인
⑤ [시간표 작성하기]
```

**컴시간은 시수표를 만들어 주지 않는다. 불러올 뿐이다.** 전 학기에서 끌어오는 기능은 절차에 없다.

**(3) 컴시간도 「전량 교체」와 「부분 수정」을 둘 다 둔다.**

§5-가 (3):
> **"새로이 교사별 시수표 불러오기를 하면 기존 모든 자료가 초기화**되어 처음부터 작업하는 것이 됩니다. **일부만 수정하는 경우에는 [시수표 등록부]에서 수정**하시기 바랍니다."

| 컴시간 | 우리 | 쓰임 |
|---|---|---|
| 교사별시수표 불러오기 (전량 초기화) | **업로드** | 신학기 — 교육과정이 바뀐 해 |
| 시수표 등록부 (셀 편집) | ① 시수 조정 화면 | 부분 수정 — 전출입·학급 증감 |
| (없음) | 전 학기 파생 | **우리만의 편의 기능** |

**파생은 없애지 않는다. 셋 다 둔다.** 다만 **실전 기본값은 업로드**이고, 파생은 *"작년과 편성이 같으면 이걸로 시작해도 된다"* 는 선택지다.

> **정정 판정: 업로드 · 파생 · 화면 편집 3경로. 신학기 화면의 기본 진입은 업로드.**
> 성명→이메일 매칭 UI는 **필요하다**(시수표 엑셀에 이메일이 없다). 원 지시가 옳았다.

#### 0-1a-②. 매뉴얼에서 딸려 나온 소득 3건

**⒜ 「정식과목명」이 곧 NEIS 과목명이다.** §5-마 과목 등록부:
> *"정식과목명: **NEIS에 등록된 정식 과목명** / 과목명: 한글2자(영문5자)의 단축과목명"*

우리 `subjectName`/`subjectShort` 쌍과 정확히 대응하고, **`timetable_neis_map`(나이스 과목명 등재부)의 정체가 이것**이다. 시수표 업로드가 나이스 매핑까지 동시에 채운다 — 별도 입력 화면이 필요 없다.
> 같은 절 경고: *"동일한 과목을 교사에 따라 과목명을 달리하는 **과목 쪼개기를 하지 마시기** 바랍니다."* → 업로드 검증에 넣을 것.

**⒝ 「요일별 시수」 화면 = 백지 실험 누락 ⑤의 답.** §5-바는 학년 × 요일 격자다(1학년 월7 화7 수5 목7 금7 = 계 33). [`phase9c_blank_run_2026-08-14.md`](./phase9c_blank_run_2026-08-14.md) §3-⑤ *"학년별 요일별 운영 교시수"* 를 설정에서 역산할 게 아니라 **이 화면 그대로 만들면 된다.**
> 검증식도 매뉴얼이 준다: **요일별시수 계 == 시수표 계** 가 일치해야 정상. 우리 검사기에 그대로 넣는다.
> 창체 지침도 있다: *"자율과 창체는 가능하면 교사들에게 시수를 주고, 시수를 줄 수 없는 경우만 여기서 배정"* → 창체는 **원칙적으로 시수표 행**, 예외적으로 고정 슬롯. ②(코호트 등록부)는 그 예외를 담는 그릇이다.

**⒞ 「가상학급수」 = 우리 동시수업 그룹.** §5-나 기본사항 등록:
> *"가상학급수란 동시수업 등으로 가상으로 늘어나는 학급 수. **4개 반을 2+1로 수준별 수업 하는 경우 가상 학급 수는 2**"*

§5-마의 복수교사 과목 규칙도 함께: *"복수 과목으로 지정된 과목은 **반드시 2명의 교사가 동일한 시수로 배정**"* — 우리 검사기에 없는 규칙이면 추가 대상.

#### 0-1a-②′. 🔴 과목 식별자 규약 — 시스템 과목명 = **단축과목명** (2026-08-14 실전 저장 시험에서 확정)

실전 첫 저장이 "[행 246] 중복된 수업 행"으로 거부됐다. 원인 실측:

- 실물 시수표에 김동현 통합사회2가 **두 행**(단축 **통사A** 1·2반 3시간 / 단축 **통사B** 전 반 1시간) — 매뉴얼 규칙 2(정식·단축·교사명 모두 같을 때만 한 줄)에 부합하는 **정당한 분리**다.
- 그리드·과목 등재부 실측: 시스템의 `subjectName`은 **단축명 계열**("국어"·"통과"·"통사A"·"체ⅠA")이고 정식명("공통국어2")이 아니다. 분리 수업은 단축명 A/B가 곧 정체성이다.
- 업로드 변환이 subjectName에 **정식명**을 넣는 바람에 통사A·B가 같은 행으로 접혀 가짜 중복이 됐다.

**규약 확정**: 업로드 변환의 `subjectName` ← **단축과목명**(비면 정식명), `subjectShort` ← 단축과목명. 정식과목명은 나이스 정식명이므로(0-1a-②⒜) 버리지 말고 행에 보존해 장래 `timetable_neis_map` 자동 등재의 원천으로 쓴다. 파서 경고 추가: **같은 단축명이 서로 다른 정식명에 걸리면 경고**(2자 제한 탓 충돌 가능 — 식별자가 겹치면 행이 잘못 합쳐진다).

> **[2026-08-14 실전 2차 — 충돌이 실물에 실재]** 경고가 실물 파일에서 발화했다: 체육1·체육2의 단축명이
> 둘 다 "체Ⅰ"이고, 같은 교사가 같은 반에 두 과목을 다 가진다(정동희 1-6~10 각 1시간, 신동민 1-1~5 동일)
> — 단축명만으로는 이 두 행이 합쳐져 중복 거부가 재발한다. **규칙 보강: 충돌하는 단축명에 한해 그
> 과목들은 정식명으로 식별한다**(체육1·체육2). 그리드 역사 표기(체ⅠA·체ⅠB)와는 다르지만 신학기
> 등록부는 새 계획의 이름 기준으로 만들어지므로 자기 일관성이 유지되고, 원하면 표에서 수동 개명 가능.

- 전 셀 정수 (실물 0.5 없음)

**ⓒ 🔴 창체·SLAT 행이 없다.** 86행 · 과목 49종 전수 확인 — 창체/자율/동아리/SLAT 행이 **하나도 없다**(진로·스포츠 생활2는 실명 교사의 실과목). 매뉴얼 §5-바 지침("시수를 줄 수 없는 경우만 요일별 시수에서 배정")의 후자를 효명고가 택한 것.

→ **업로드 경로에서는 가상 교사 행이 0개다.** 파생 경로(가상 60행)와 달리, 창체·SLAT의 존재 자체가 시수표에 없다. **컴파일러가 시수표 행 없이도 코호트 등록부의 고정 슬롯을 점유 섹션으로 만들어야 한다** — 현행 `compileSectionsFromHours`는 시수표 행에서 출발해 고정 슬롯을 찾으므로(행이 없으면 슬롯이 그냥 버려짐) **구현 순서 4번(코호트 연결)의 필수 요구사항**이다. 정합성 검사도 이때 완성된다: 반별 열합(30) + 코호트 고정 슬롯 수 = 운영 교시수.

**ⓓ 시수표의 상류가 있다 — 일과계는 시수표를 손으로 만든다.** 실제 업무 흐름(일과계 증언):

```
교육과정부장: ① 과목별 배정표 ② 이동수업현황 ③ 창체수업 담당교사   (3개 파일)
     ↓  일과계가 손으로 편집·대조                     ← 지금 수동인 구간
교사별 시수표(.xls)  →  컴시간 입력
```

일과계가 짚은 함정 2건: **배정표에 오류가 있는 경우가 있다** · **1학기에는 담임 교체로 배정표의 담당반이 바뀌는 경우가 있다.** 3파일→시수표 자동 생성 + 오류 검출은 별건 아이디어로 로드맵 §2에 등재(이 스펙 범위 아님 — 업로드 파서가 먼저다).

### 0-2. 저장은 **파생 시점의 전체 사본**이다 (차분 아님)

편집분만 차분으로 저장하면 원본(전 학기 그리드)이 나중에 바뀔 때 조용히 어긋난다. **파생하는 순간 전체를 복사해 두고 그 사본만 편집한다.** 원본이 뭘 하든 영향받지 않는다.

# ① 시수 조정 화면

## 1-1. 무엇을 하는 화면인가

> **"작년 시수표를 불러와서 바뀐 것만 고친다."**

학교가 2월에 실제로 하는 일이다 — 백지에서 입력하지 않는다. 교사 전출입, 학급 수 변경, 과목 개폐만 반영하면 새 학기 시수표가 된다.

## 1-2. 저장 모델

```
timetable_hours_plans/{domain}/plans/{planId}
```

```ts

  id: string;
  label: string;              // "2027학년도 1학기 시수" — 사람이 붙임
  sourceTermId: string;       // 파생 원본 학기 (예: "2026-2")
  derivedAt: number;          // 파생 시각 — 이후 원본이 바뀌어도 이 사본은 불변
  rows: HoursPlanRow[];
  gradeDayPeriods: Record<number, Record<number, number>>;  // 부족정보 #5

  createdBy: string;
  updatedBy: string;
  updatedAt: number;
}

export interface HoursPlanRow {
  id: string;                 // 행 고유 id (편집 추적용)
  grade: number;
  classNum: number;
  subjectName: string;
  teacherEmail: string;       // "" = 가상 교사(창체·SLAT) — ②가 위치를 준다
  teacherName: string;        // 표시용 스냅샷. 판정은 email로만 한다
  hours: number;              // 주당 시수

  simulGroupId?: string | null;
  /** 부족정보 #4 — 이 시수 중 특별실을 쓰는 시간 수. null = 전 시수(보수) */
  venueHours?: number | null;

```

**왜 `rows`를 문서 안에 배열로 두나**: 실측 432행이고 학급이 늘어도 수백 행 규모다. 하위 컬렉션으로 쪼개면 읽기가 432번이 되고 편집마다 트랜잭션이 필요하다. **한 문서 1MB 한도 안에 충분히 들어간다**(432행 × ~150바이트 ≈ 65KB). 다만 **저장 시 크기를 검사**해 900KB를 넘으면 거부한다.

# ② 교육과정 코호트 고정 슬롯 등록부 (C2)

## 2-1. 왜 「학년」이 아니라 「교육과정」인가

질의 결과 §2-2에서 확정했다. 교육과정 개정은 1학년부터 들어오므로 **두 교육과정이 2년간 공존**하고, **「학년」은 해마다 뜻이 바뀌는 축**이다. "1학년: 금 5·6교시"로 적어 두면 **매년 3월에 한 칸씩 밀어야 하고 안 밀면 조용히 틀린다.**

→ **등록 단위는 교육과정, 학년은 역산으로 파생한다.**

```
학년 = 학년도 − 입학년도 + 1
```

입학년도 축은 이미 있다(학생 계정이 `{입학년도}{번호}@`).

## 2-2. 저장 모델

```
timetable_curriculum_cohorts/{domain}/cohorts/{cohortId}
```

```ts
export interface CurriculumCohort {
  id: string;
  label: string;                 // "2022 개정 교육과정" — 사람이 붙임
  startAdmissionYear: number;    // 이 교육과정이 처음 적용된 입학년도. 예: 2025
  fixedSlots: CohortFixedSlot[];
  active: boolean;
  createdBy: string;
  updatedBy: string;
  updatedAt: number;
}

export interface CohortFixedSlot {
  displayName: string;   // "창체" / "SLAT" — 화면·그리드 표시용
  day: number;           // 1=월 … 5=금
  period: number;
}
```

**설계 규칙 3가지**

1. **이름을 키로 삼지 않는다.** `displayName`은 표시용일 뿐이고 판정은 `(day, period)`로 한다. 교육과정이 바뀌면 이름도 바뀐다.
2. **연속 2시간은 두 줄로 적는다** (`금5`, `금6`). 블록 개념을 넣지 않는다 — 솔버는 이 슬롯을 **점유 불가**로만 다루고 배치하지 않으므로 연속성이 의미 없다(질의 2-2 부연: 사람이 나중에 채운다).
3. **학년을 저장하지 않는다.** 저장하는 순간 3월 함정이 돌아온다.

## 2-3. 학년 역산 — 단일 소재지

`src/lib/timetable/cohort.ts` 신설. **이 함수 밖에서 학년을 계산하지 않는다.**

```ts
/** 특정 학년도에 어느 학년이 어느 교육과정을 따르는가 */
export function cohortForGrade(
  cohorts: CurriculumCohort[],
  schoolYear: number,
  grade: number
): CurriculumCohort | null {
  const admissionYear = schoolYear - grade + 1;
  // 적용 시작 입학년도가 그 이하인 것 중 가장 최근 것
  return cohorts
    .filter((c) => c.active && c.startAdmissionYear <= admissionYear)
    .sort((a, b) => b.startAdmissionYear - a.startAdmissionYear)[0] ?? null;
}

  schoolYear: number,
  classList: Array<{ grade: number; classNum: number }>
```
