# 알림 센터 스펙 — "나에게 일어난 일"의 원장 + 수락 창구

- **근거**: development_roadmap.md §2 「알림 센터」(2026-08-13 사용자 재발상, Claude 안전망 판정 동의) + 2026-08-15 사용자 발상(수락 버튼 창구) + consent_swap_opening_spec §13-3·v2 예약석. 작성 2026-08-18.
- **성격**: 푸시는 초인종(휘발), 알림 센터는 원장(비휘발). 결보강으로 내 수업이 바뀐 것을 푸시 한 번 놓치면 복구 경로가 없는 현 구조의 안전망.
- **결정 확정: 2026-08-18 사용자 — 전 항목 권고안대로 수용** (MVP). 본문 `[권고]` 표시는 이력 보존을 위해 남긴다.
- **구현 노트 (2026-08-18, 코어 구현하며 확정한 세부)**: ① 푸시 편승(§3)은 **기존 발생 지점의 푸시 경로 유지**로 대체 — 이중 발송·순환 import 회피, "알림 없이 푸시만" 금지 원칙은 수업 변경 통지 함수에 원장 기록을 심어 충족 ② 수업 변경 원장은 **교사만** — 학생은 반 단위 인원수만큼 문서가 불어나 푸시(초인종)로만 유지 ③ 유형 ④(행정 처리)는 자리만 예약 — 프로필 승인 엔드포인트 배선은 후속 ④ 파기는 `expireAt`(Timestamp) + **Firestore 콘솔에서 `notifications` 컬렉션 그룹 TTL 정책 1회 설정 필요**(phase11 관례) ⑤ 목록 조회는 색인 없이 본인 전량 조회 후 정렬 — 보존 180일·4종 승격이라 1인당 수십 건, 커지면 복합 색인 도입.

## §1 데이터 모델 (결정 ⓑ — 별도 컬렉션)

`[권고]` **`notifications/{domain}/items/{id}` 신설 컬렉션.** `audit_logs` 재활용 금지 확정 — 감사 로그는 행위자 축·관리자 눈높이·전권 열람이고, 알림은 대상자 축·당사자 눈높이·본인 열람이라 축이 셋 다 다르다.

```ts
interface NotificationDoc {
  recipientEmail: string;        // 대상자 (본인만 열람 — 서버 라우트에서 강제)
  type: "lesson-changed" | "request-resolved" | "memo" | "admin-action" | "consent-request" | "consent-result";
  title: string;                 // 눈높이 한 줄 ("수요일 3교시 수업이 보강으로 바뀌었습니다")
  refType: string;               // 원본 종류 ("swap_request"·"memo"·"weekly" …)
  refId: string;                 // 원본 문서 id — 알림은 원본을 가리키는 손가락 (결정 ⓓ)
  createdAt: number;
  readAt?: number;
  /** 수락 창구 (§4) — 있으면 이 알림에 버튼이 붙는다 */
  actionable?: { kind: "consent"; state: "pending" | "accepted" | "declined"; decidedAt?: number };
  expireAt: number;              // 파기 크론 편승 (결정 ⓔ)
}
```

- **원본 포인터 원칙 (결정 ⓓ)**: 알림 문구는 요약 한 줄까지만, 상세는 원본 화면으로 딥링크. 원본이 파기·삭제된 뒤에는 문구만 남고 링크는 "지난 항목입니다" 처리 — 알림을 사본으로 키우지 않는다.

## §2 읽기 비용 (결정 ⓐ)

`[권고]` **배지 = `users/{uid}` 문서의 `unreadNotifCount` 카운터 필드.** 근거: 로그인 사용자 문서는 이미 전역 실시간 구독 중(AuthContext.userData)이라 **배지에 추가 읽기 0**. 알림 생성 시 카운터 `increment(1)`, 알림 센터 열람 시 일괄 0 리셋(+해당 알림 readAt 기록). 목록은 열 때만 `limit 30` 페이지 조회 — 실시간 구독 금지(무료 한도 규율). `count()` 집계보다 나은 이유: 집계도 호출마다 읽기인데 카운터는 기존 구독에 무임승차.

- 카운터 어긋남 대비: 알림 센터 열람 시 서버가 실제 미열람 수로 카운터를 재동기화(자가 치유).

## §3 승격 범위 (결정 ⓒ) — 전부 넣으면 소음

`[권고]` **1차 4종만.** ① 결보강으로 **내 수업·일정이 바뀜**(주간 확정·변경 적용 시) ② **내 신청이 처리됨**(교체·통 이동 승인/거절) ③ **내게 온 쪽지** ④ **나에 대한 행정 처리**(프로필 승인, 권한 변경). 공지·전체 안내·통계성 정보는 제외 — 원장의 신호 밀도를 지킨다. 유형 추가는 스펙 개정으로만(코드에서 임의 승격 금지).

- 생성의 단일 소재지: `server.ts`에 `emitNotification()` 헬퍼 하나 — 각 발생 지점(주간 적용·requests 처리·memo 발송·프로필 승인)이 이것만 호출. 푸시는 이 헬퍼가 기존 웹 푸시 인프라(webpush.ts)로 **편승 발송**(초인종) — 알림 없이 푸시만 가는 경로를 만들지 않는다(원장 우선 원칙).

## §4 수락 창구 — 양해 요청의 인앱 전이 (§13-3의 도입)

consent_swap_opening_spec §13-3·v2 예약석 그대로: 모델은 이미 호환된다 — `SwapDraft.consentStatus`(NONE→REQUESTED→CONSENTED→DECLINED)가 실제로 전이하기 시작하고, 현행 "양해 받았음" 수동 체크(`consent.confirmed`)를 대체한다.

- 흐름: 여러 교사가 얽힌 신청 저장 시 → 관련 교사에게 `consent-request` 알림(actionable) 생성 → 당사자가 알림에서 **[양해합니다] / [어렵습니다]** → consentStatus 전이 + 신청자에게 `consent-result` 알림 → 일과계 화면의 양해 표시는 전이 상태를 읽는다(수동 체크 소멸).
- **경계 (사용자 확정 원칙의 명문화)**: 수락 버튼은 당사자 본인의 의사표시이므로 「시스템은 정보 전달까지만」에 저촉되지 않는다. 단 **시스템이 대신 조르는 것은 금지** — 독촉·리마인드·재알림 자동 발송을 만들지 않는다. 무응답은 시스템이 해소하지 않고 사람 경로(신청자가 직접)로 남긴다.
- 수락 창구 세부 결정:
  - `[권고]` **기록의 무게 (ⓐ)**: 수락·거절 전이는 알림 문서(decidedAt)와 감사 로그 양쪽에 남긴다 — "양해를 받았다"의 책임 보호 근거가 원장이 된다. 수동 체크 시대보다 강한 증빙.
  - `[권고]` **거절·무응답 (ⓑ)**: 거절 = 즉시 신청자에게 결과 알림(신청은 자동 취소하지 않음 — 처리 판단은 사람). 무응답 = 만료 없음(독촉 금지의 귀결), 신청이 취소·처리되면 대기 중 수락 알림은 자동 무효화("이미 정리된 요청입니다").
  - `[권고]` **유형 확산 경계 (ⓒ)**: 수락 대상은 양해(consent)와 — 도입 시 — Phase 8 업무 수락 둘뿐. 그 외 유형에 버튼을 붙이려면 스펙 개정 필수(소음·경계 원칙).

## §5 보존·파기 (결정 ⓔ)

`[권고]` **180일 expireAt + 기존 파기 크론 편승.** 쪽지(365일)보다 짧게 — 알림은 원본의 포인터일 뿐이라 원본보다 오래 살 이유가 없다. 수락 기록(consent 계열)은 예외적으로 **원본 신청의 보존 기한을 따른다**(책임 보호 근거이므로 — §4ⓐ). 개인정보 인벤토리 등재: 필요(수신자 이메일 + 행위 사실) — personal_data_inventory.md에 한 줄 추가.

## §6 화면 (Antigravity — 스펙 확정 후 인계)

- 상단 바 벨 아이콘 + 미열람 배지(userData 카운터). 클릭 → 알림 목록 패널(최신순, 30개 + 더 보기). 항목 = 한 줄 문구 + 상대 시각 + 원본 바로가기. actionable 항목은 [양해합니다]/[어렵습니다] 버튼 인라인.
- 문구는 전부 눈높이(개발 용어·내부 참조 금지). 빈 목록: "새로 확인할 알림이 없습니다."
- 교사·학생 공통 레이아웃(학생은 승격 유형이 적어 자연히 조용).
