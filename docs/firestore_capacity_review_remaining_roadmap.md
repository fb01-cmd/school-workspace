# 남은 로드맵 전체 Firestore 용량 리뷰 — "기능을 더 얹으면 터지는가"

작성: Claude, 2026-08-08. 요청 배경: 개학 시점 채택이 0에 가까워 읽기량 실측이 당분간 불가 → 향후 기능 추가가 무료 한도를 위협하는지 **구현 전 사전 판정**. 기준 문서: development_roadmap.md §1·§2 미구현 전 항목 + phase9b_spec 잔여.

## 0. 전제 — 한도와 현재 기준선

- **무료(Spark) 한도**: 읽기 5만/일 · 쓰기 2만/일 · 삭제 2만/일 · 저장 1GB. 리셋 = 매일 KST 16:00.
- **현재 기준선 (주간 합성 캐시 적용 후)**: view 조회 ~2-4읽기/요청. **전원 채택 최악 가정**(교사 70 + 학생 800 전원이 하루 2회 조회)에도 ~7K/일 + 캐시 채움·기타 ≈ **총 1만 안팎 = 한도의 20%**. 캐시 전이었다면 이 가정은 15만/일로 즉사였다 — 용량 문제는 이미 한 번 해결됨.
- 판정 등급: **0**(Firestore 무관) / **하**(수백/일 이하) / **중**(수천/일 또는 스파이크성 — 설계 조건 붙음) / **구조적 주의**(수치가 아니라 구조 결정이 필요).

## 3. 대형 항목 — 조건부 판정 2건

### 3-1. Phase 7 학부모 소통 모듈 → **중 (설계 전제 지키면 안전)**

유일하게 **새 사용자군 900가구**가 추가되는 항목. 위험 지점 3개와 전제:

1. **발송일 스파이크**: 알림톡 발송 직후 1~2시간에 열람 집중. 통신문 본문을 학부모마다 Firestore에서 읽으면 900+ read 스파이크 — **본문은 버전 키 캐시(이번 주간 합성 캐시 패턴 재사용) 또는 정적 렌더**로 서빙하면 열람당 ~1-2읽기, 스파이크 ~2K로 무해. 학부모가 로그인 없는 토큰 링크 방식이면 인증 읽기도 0.
2. **서명·첨부 이미지**: Firestore 문서에 넣지 않는다 (문서 1MB 한계·저장 1GB 소진 경로). 터치 서명 재사용 시 저장처는 Drive(Workspace 무료)로 — 기존 서명 증빙 파기 크론 패턴 연동.
3. **열람 확인 write**: 900/발송 × 월 8 = 7.2K/월 — 쓰기 한도(2만/일) 대비 무시 가능.

→ 착수 시 스펙에 **"요청당 읽기 계수" 섹션 의무** (§4-2). 전제 지키면 월간 수만 read 수준 = 안전.

### 3-2. 범용 위자드 (타 학교 도입) → **구조적 주의 ⚠️ (유일한 "터질 수 있는" 구조)**

무료 한도는 **Firebase 프로젝트 단위**다. 타 학교를 지금의 school-sync-hub 프로젝트에 수용하면 학교 수에 비례해 한도를 나눠 쓰게 되고, 2~3개교면 초과가 현실화된다. 코드는 이미 domain 파라미터화돼 있으나 `adminDb`가 단일 프로젝트 고정.

→ **원칙: 학교당 별도 Firebase 프로젝트** (한도도 학교당 5만/일로 분리 — 무료 원칙이 오히려 강해짐). 위자드 착수 시점에 프로젝트 분리(환경변수로 프로젝트 선택) 설계 필요. 지금 결정할 것 없음 — 단독 학교인 한 무관.

## 4. 기능보다 위험한 것 — 구조적 위험 순위와 규칙

1. **실측·전수조사 스크립트 (실적 있는 1위 — 8/8 소진 사고 주범)**: 기능이 아니라 사람이 한도를 태운다. 기존 규율 유지 — 전수조사 전 읽기량 추산, 프로세스 내 재료 재사용.
2. **읽기 계수 없는 신기능** (재발 방지 규칙 신설): **새 API 라우트/화면 스펙에 "요청당 Firestore 읽기 계수" 1줄을 의무 기재**한다. 이번 캐시 사태의 교훈 — view가 ~85읽기인 걸 아무도 계수하지 않은 채 개학을 맞을 뻔했다. 계수가 두 자릿수면 캐시 패턴(버전 키) 적용을 검토한다.
3. **프리페치·폴링 실수**: AuthContext 프리페치에 Firestore 데이터를 추가하면 로그인마다 전 사용자가 읽는다 — 추가 전 계수. setInterval 폴링으로 Firestore를 감시하는 패턴 금지(웹 푸시로 대체).
4. **onSnapshot 남용**: 현재 실시간 구독은 schoolSettings·본인 userData 2개(소액)뿐. 대량 컬렉션 실시간 구독은 초기 스냅샷 전 문서 read + 변경마다 read — 새로 붙일 땐 문서 수를 계수.

## 5. 종합 판정

**남은 로드맵을 전부 구현해도, §4의 규칙을 지키는 한 무료 한도 안이다.**

- 전 항목 구현 + 전원 채택 + Phase 7 발송일까지 겹친 최악 시나리오: 평시 ~1만/일, 스파이크일 ~1.5~2만/일 = **한도의 30~40%**.
- "터질" 수 있는 경로는 기능 목록에 없다. 셋뿐이다: ① 스크립트 전수조사(규율로 통제 중) ② 계수 없는 신기능이 view 사태를 재현(§4-2 규칙으로 차단) ③ 타 학교를 같은 프로젝트에 수용(§3-2 프로젝트 분리 원칙으로 차단).
- 이미 확보한 무기: 버전 키 캐시 패턴(다수 읽기·소수 쓰기 자료 어디든 재사용 가능), 나이스·GWS 등 Firestore 밖 0원 데이터 소스 우선 관행, 파기 크론 패턴(저장 1GB 방어).
