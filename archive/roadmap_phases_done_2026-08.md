## Phase 8

### Phase 8. 교사 업무 Task 관리 시스템 (**완료 ✅ 2026-08-19~20 — 구현·배포·실기기 확인 종결**)

<!-- 서술 -->
* **배경·목적 (2026-08-08 사용자 구술)**: 현재 교사 업무는 쿨메신저(구식·별도 서버컴·유료) 기반 — 메시지와 업무 상태가 분리돼 있지 않아 "업무 놓친 것 없나" 메신저를 뒤적이는 구조를 근본 대체. 이 플랫폼 착수 전의 원 구상이 바로 이것(당시엔 캘린더·태스크 부가기능으로 계획).
<!-- 서술 -->
* **사용자 구상 흐름**: 조직도에서 대상 지정 → 업무명·기한·메시지·리소스 첨부(Drive 자동 업로드+링크) → 전송 → 수신자 수락 시 본인 캘린더 등록 + 플랫폼 할일 목록 편입 → 완료 체크가 발신자에게 실시간 반영(미수락·미완료자 파악).

* **Claude 의견 (2026-08-08, 채택 여부는 사용자 결정)**: ① **플랫폼 네이티브 구현 권장** — 어려운 재료(조직도·알림·권한·감사·Drive·설치 앱)가 전부 기구현, 애드온(Apps Script)은 재구축+UI 제약+모듈 결합 불가. 컴시간 대체와 동일 패턴. ② **Firestore 용량 무해** — 인간 생성 데이터라 증폭 구조 없음(쓰기 수백/일, 읽기 ~5천/일 상한, capacity review Phase 8 판정 '하' 유지). 첨부는 Drive 링크만 저장. ③ **캘린더 = 단방향 출력 채널로 격하, 구글 Tasks 동기화는 제외 권고** — 체크 상태가 두 곳에 살면 실시간 반영이 깨지고 폴링(진짜 읽기 낭비)이 필요해짐. 상태 단일 원본 = 플랫폼. ④ 승부처는 보드가 아니라 **발신자 화면의 사람별 수락/완료 실시간 현황**(재촉 대상 즉시 파악 — 좁은 구독이라 용량 무해). ⑤ 스펙에서 결정할 실무 설계: 수락 전 상태(거절·대리·재촉), 지시 권한 범위(전 교사 자유 vs 부장 이상), 알림 피로 설계, 캘린더 이벤트 취소 동기화.

* **단계별 구현 계획 (2026-08-09 Claude 제안 — 쪽지 아이디어(§2)와 통합, 착수 시점은 사용자 결정)**: 원칙 = "쪽지가 기반, 업무는 그 위의 구조화, 캘린더는 마지막 출력" — 각 단계가 단독 완결 가치를 내며 다음 단계의 기반이 됨 (9a→9b→9c 패턴). 순서 근거: ⓐ 업무 관리의 난부(도달·수신확인·알림) = 쪽지 인프라 그 자체 ⓑ 채택 곡선 — 쪽지는 메일 사본으로 비채택자에게도 성립하지만 업무 수락은 플랫폼 진입이 전제이므로, 쪽지로 유입을 만든 뒤 업무를 얹는 것이 전환 마찰 최소.
  - **1단계 — 쪽지 MVP (도달+수신확인)** — **스펙 확정·구현·시연 통과 ✅ (2026-08-13, [`docs/memo_spec.md`](./docs/memo_spec.md))**: 조직도/그룹 다중 선택 → 제목·내용·Drive 링크 → 발송. 원본·읽음 상태 = 플랫폼(Firestore), 발송 시 웹 푸시 (~~hmnotice@ 메일 사본~~ **2026-08-09 전면 철회** — 기관 채택 모델 확정으로 존재 이유 소멸, 아래 재검토 최종 결론 참조). 보낸 쪽지함에 수신자별 읽음 표시. 보존 기한 + 파기 크론.
  - **2단계 — 쪽지 완성**: 첨부는 **"링크 공유"가 아니라 "사본 수수" 의미론** (2026-08-09 사용자 지적 반영 — HWP 등 로컬 편집 파일은 링크로는 "실제로 가져가지"를 못함, 학교 업무 지배 패턴 = 양식 배포→로컬 한글 작성→제출): 첨부 파일은 Drive에 저장하되(파일 Firestore 저장 금지) 수신자 기본 동작 = **내려받기**(각자 사본). 플랫폼 내 답장·스레드, 대시보드 "안 읽은 쪽지 N건" 카드(기존 건수 카드 아이디어 부분 실현).
    - **[2026-08-15 사용자 발상] 첨부 Drive 폴더 체계화**: 쪽지 첨부가 본인 Drive에 쌓이므로 **전용 폴더를 자동 생성**하고 그 하위를 체계적으로 나눠 업로드하게 한다. 분류 축은 미정 — 후보: 기간별(월/주) vs 용도별 vs 파일형식별. 스펙 작성 시 결정 (사용자 원문: "별도로 폴더가 생성되고 그 안에 월단이든 주간이든 폴더를 만들고,(혹은 용도별? 혹은 파일형식별?) 체계적으로 업로드").
    - **[2026-08-18 사용자 관찰] GIF 첨부 미지원**: v1 화이트리스트(PNG·JPG·WEBP — attachment spec §0-2 실수요 기반 확장 구조)의 의도된 범위이나 사용자가 인지. 붙이려면 서버 화이트리스트+GIF 바이트 서명 추가와 **클라이언트 원본 통과 분기**(캔버스 리사이즈는 GIF 움직임을 죽이므로 3.5MB 이하 원본 통과·초과 거부)가 필요 — 소규모. 착수는 사용자 결정.

  - **3단계 — 업무 지시 (Phase 8 본체)**: 쪽지에 "업무" 타입 — 기한·수락/거절·완료 상태 머신, 발신자 현황판(사람별 수락/완료 실시간+재촉), 기한 임박 크론. **+ 제출형 업무 (2026-08-09 추가)**: 완료 = 작성본 파일 업로드 → 업무별 Drive 제출함 폴더 자동 생성(담당자만 접근) + **제출 파일명 자동 정규화("2학년3반_홍길동_양식명.hwp")** — 취합(파일명 난장판·미제출 파악)이 담당자 최대 고통이므로 이것이 쿨메신저 대비 킬러. 전송·알림은 1단계 재사용이라 신규는 상태 관리·현황판·제출함뿐. 실무 설계 결정(의견 ⑤)은 이 단계 스펙에서.

  - **[실측 2026-08-21] 지적이 맞고, 실제로는 더 어긋나 있다.** 학년부 판정이 **부서 이름 문자열 정규식**인데 **두 곳의 정규식이 서로 다르다**: 화면은 `/^([1-3])학년$/`(끝까지 일치, `OrgChartBuilder.tsx:632`·`OrgChartTree.tsx:256`), 정렬은 `/^([1-3])학년/`(끝 고정 없음, `src/lib/org/sort.ts:24`). ⇒ 부서 이름을 「1학년부」로 주면 **정렬은 학년부로 취급하는데 화면은 학년부가 아니게 되어 담임 반 선택이 사라진다.** 조용히 반쪽만 동작한다.
  - **핵심 — 답은 이미 저장돼 있는데 코드가 안 쓴다.** `SchoolSettings.gradesCount`(몇 학년까지)와 `classCounts`(학년별 반 수)가 이미 있고, 같은 화면이 **반 수는 `classCounts[gradeNum]`으로 읽으면서**(`OrgChartBuilder.tsx:635`) **그 부서가 학년부인지는 이름으로 짐작한다.** 사용자가 제안한 「몇 학년까지 있나요」는 새로 물을 것이 아니라 **이미 받아 둔 답**이다.
  - **부수 결함 2**: ⓐ `[1-3]` 하드코딩이라 **4학년 이상이 원천 불가** — 중학교·6년제나 학년 수가 다른 학교에 못 쓴다(`gradesCount`가 있는데도). ⓑ `teacher_profiles.departments`가 **부서 이름 문자열 배열**이라 부서를 개명하면 프로필 참조가 통째로 끊긴다(`src/lib/org/eligibility.ts:4`) — 자유 입력 목록에 학년부를 섞어 둔 현재 구조의 위험이 이름 짐작 문제와 같은 뿌리다.
  - **설계 방향(미확정, 사용자 결정 대기)**: 학년부를 자유 입력 목록에서 빼고 `gradesCount`에서 파생시킨다. 파생 부서는 이름 변경은 허용하되(「1학년」/「1학년부」 취향) **학년 번호를 이름이 아닌 필드로 들고 다닌다** — 그래야 개명해도 담임 반 선택과 정렬이 같이 따라온다. 선행 확인 = 기존 도메인의 `departments` 배열과 `teacher_profiles.departments`에 이미 박혀 있는 「1학년」 문자열 마이그레이션.
